## Signals and implications (observed)

- Reconnect: outputs are ordinary notifications and can be replayed by the owner; requests need the pending set (shim) plus the server's `serverRequest/resolved`; responses are first-answer-wins and stale ones are ignored by both shim and server. The three kinds do need different treatment, and only the pending set must be reconstructed on reconnect.
- The server imposes no deadline on a pending approval (6 s unattended here; 150 s unattended in the Claude long-hold earlier is the comparable datum).
- Suspension: closing stdin is clean at idle and with an approval pending (both leave a consistent rollout, the latter with `turn_aborted`). With an active command, `turn/interrupt` ends the turn and the server exits, but the sandboxed tool process can keep running; wait-until-idle is the only path that leaves no process behind. A suspend operation needs its own process check for `codex-linux-sandbox` children.
- `thread/resume` restores history and readiness (MCP startup) without model work; "reopen" and "activate" are separable.
- Steering: a default-mode async question can be answered in place with `turn/steer` using `expectedTurnId`; the answer becomes a `userMessage` item inside the active turn and cuts the model's sleep polling short. Roundhouse can treat an `agentMessage` with `questions[]` as an explicit question and route the reply through `turn/steer`, with `turn/start` as the fallback after the turn ends.
- Plan mode cannot be selected through the 0.166.0 app-server protocol, so no mode recommendation follows for planning agents.
