# CHANGELOG

## Unreleased

CHANGE: **Mega runs a project's activation only when something needs the environment, and workspace responses no longer carry `environment.resolving`.** (2026-11-25) Starting mega, registering a project and reading the workspace, from the page or the tray, no longer run any project's activation. The first thing that needs a project's environment, such as a start, the launch dialog or opening a conversation, resolves it and waits while the activation runs. Until then, as after every restart, the project's environment section says "Not resolved yet" and lists nothing missing, and the trust notice gives its reason itself. A result from an activation that is no longer the one that would run, as after the local override changes, reads as not resolved yet and no longer refuses a start. An unapproved, changed or malformed environment file still shows its refusal at once.

CHANGE: **A turn is what the harness says it is, and events no longer carry `after_turn`.** (2026-11-24) A conversation is working from the moment its harness starts a turn until that turn ends, and mega opens no turn of its own. A prompt shows at once and working follows a moment later, when the harness begins. A harness that never begins leaves the prompt and no activity, where before the conversation could show as working with no end. A turn the agent starts by itself, as Claude does when background work finishes, shows as working before its first output. No message opens a turn: a stray one, such as Claude's reply to a model switch on an idle runtime, and output from a turn that has ended leave the conversation idle. Output from an ended turn that arrives while the next one runs is taken for the running turn's own: a late Codex tool call shows a spinner, a late message ends the streaming text, and the first of them sets what the turn's line says it ran with. The history API's events no longer carry `after_turn`, so nothing there tells such output apart. Logs from earlier builds read as before, their `after_turn` ignored.

CHANGE: **Conversation responses drop `output_seq`.** Use `attention` for unread status. Recorded output can show as unread after Resume even if mega missed the turn's end, and adopted output is unread until acknowledged.

CHANGE: **Once mega has closed, it answers no read.** (2026-11-24) In the moment after an orderly stop has let go of the workspace and before mega stops answering, reads are refused as `unavailable`. A page whose workspace read or reconnect catch-up is refused then keeps what it last read, the shutdown banner included, and shows no read error.

CHANGE: **A write mega cannot make stops mega.** (2026-11-24) When the registry or a conversation's log cannot be written, mega logs why and exits at once, as if it had crashed. It no longer runs on refusing changes until a restart. Nothing is stopped on the way out: an agent at work goes on unwatched, and the page shows mega as unreachable, with the reason in mega's log. The next start treats it as the start after a crash. A conversation that was running is Unsupervised, and a request that was waiting is lost. A failed configuration snapshot still stops nothing.

CHANGE: **Release only stops a runtime.** (2026-11-24) Its confirmation says the runtime stops and that the next prompt or Start brings the conversation back on the same session. It no longer offers a command to continue the session in a terminal, or advice about closing one. Mega does not support working a session outside it while a conversation holds it, and neither marks nor shows work done there: leave the session alone outside mega to keep it intact in mega. To bring work done outside into mega, remove the conversation and adopt its session again.

CHANGE: **A conversation whose first launch failed is not launched again.** (2026-11-23) Whatever failed, the launch records one error, and a prompt or Start is refused with a message to remove the conversation and, if the harness made a session, adopt it under "Adopt a session". Before, a launch proven to have failed before any session existed could be retried in the same conversation. A conversation whose session never reached the registry is treated the same way: its session is no longer resumed, and can be adopted when discovery lists it. A failed launch of a conversation that has a session is recorded as an error, where before it could say "did not start", and can be launched again as before.

FIX: **A conversation's history no longer stays missing a stretch when the read after a reconnect fails.** (2026-11-25) When the stream reconnects, the page reads what the open conversation recorded while it was away. When that read failed, nothing tried it again on that connection, and the page said the workspace could not be read. Later events arrived on the stream, and what was recorded meanwhile stayed missing until the conversation was opened again or the stream reconnected. The read is now tried again, after 1 s and then doubling to at most 8 s, and the history's "Loading history:" line says what it waits for, as for the opening read.

FIX: **A launch from the new-conversation dialog no longer starts Claude in the default permission mode when the model list failed.** (2026-11-25) When the harness did not list its models, for any reason but a missing executable, a launch you had not picked a mode for was sent as `default`, as if you had chosen it, so a checkout whose Claude settings name `plan` started outside plan mode. It now sends no mode, and the conversation takes the one the settings name, as it does when the list answers. Until you pick a mode, the selector says "As your settings name it", and Ask stays a choice you can pick.

FIX: **An answer given while a conversation is starting no longer throws the request away.** (2026-11-23) A pi extension can ask before its runtime has finished launching. An answer given then was recorded as aborted, although pi never received it and was still waiting. It is now refused with "the runtime is starting". The card stays, and answers once the launch is done.

CHANGE: **Resume no longer imports native history.** Adoption starts with one snapshot. After a loss of supervision, the Unsupervised row marks where mega stopped watching. Resume acknowledges lost supervision and launches nothing. The next Start or prompt uses the bound session.

FIX: **Pi records replies as they arrive and reports the harness’s turn outcome.** Live replies can appear as soon as pi sends them, including when no file entries have been written yet.

CHANGE: **mega's default port is now 6342.** (2026-11-18) The old default, 8470, is registered with IANA to another protocol and is also used by NetFoundry's Agora. 6342 is unassigned. Nothing else about the listener changes: it is loopback only, and `listen` in the config or `--listen` still names another port. What an operator has to do:
- **With no `listen` in your config,** mega moves to `http://127.0.0.1:6342` at its next start.
- **Bookmarks, shares and tunnels that name 8470** need changing to 6342. Or keep the old port by putting `listen: 127.0.0.1:8470` in `~/.config/mega/mega.yaml`; a config that names a port keeps it.
- **The page's per-browser settings,** such as the side panel's width and which projects are folded, start fresh once, because a browser keeps them per port.
- **A new mega started while an old one still serves 8470** on the same data directory does not start a second one beside it. It is refused by the data directory's lock, which names the running mega at 8470, and `mega daemon` opens that one's page instead.

CHANGE: **A Codex question whose turn has ended is answered in the reply box.** (2026-11-19) While the turn that asked is running, the question's card answers it into that turn, as before. Once the turn ends, for any reason, the card goes and Codex's message stays in the conversation, to be answered with a reply that starts the next turn. A card answer never starts a turn.

FIX: **An answer Codex never confirms is no longer reported as settled before it arrived.** (2026-11-19) When an answer is sent into Codex's running turn and no reply comes, within a minute or before Codex's app-server goes, the card closes and the question's history says "Codex did not confirm whether it received your answer". mega does not send it again.

FIX: **An interrupt no longer stays shown under way once nothing is left to stop.** (2026-11-20) Pressed with no turn running while a request was still being settled, as a Codex answer awaiting its reply, it stayed shown until the next prompt.

FIX: **Nothing starts once a shutdown has begun, or in an environment file that changed while it was read.** (2026-11-19) A launch checks again after the version check. Adoption checks before reading native history. A shutdown that began meanwhile refuses it, and a shutdown waits for a launch already under way. An environment file changed meanwhile refuses it with `environment_changed`, as an edit before the start always did.

FIX: **A conversation's unread output is no longer lost to a failed registry write.** (2026-11-19) When a turn's end could not record its output as unread, the output stayed read for good. mega now counts it from the conversation's log at its next start, including the output of a Codex background command that finishes after its turn.

FIX: **A request Codex or pi settles while its answer is on the way is shown as settled, not answered.** (2026-11-19)

FIX: **Another session's history or output never reaches a conversation.** (2026-11-19) A history read back from Claude Code, Codex or pi is refused if it holds another session than the one asked for, and Codex output for another thread is left, even before Codex has confirmed which thread it opened.

FIX: **The shutdown banner says only what the page heard.** (2026-11-19) mega now tells the page when a shutdown has finished, as the last thing it sends. A page that heard it says mega was shut down, as before. A page that asked for a shutdown and then lost contact without hearing it says a shutdown was asked for and contact was lost, in the banner, the footer ("Shutdown asked, contact lost, retrying") and the rail.

FIX: **Releasing a Claude conversation now says when something it started is left running.** (2026-11-19) As for Codex and pi, anything still running in the Claude runtime's process group after it exits is named and the release shown as an error, and where the processes could not be listed the release says that could not be checked. An ordinary release reads as before. A Codex question that arrives once a stop has begun is no longer raised, and nothing more is written to the registry once mega has closed.

FIX: **A refused prompt no longer leaves a conversation working.** (2026-11-19) When Codex or pi refuses a prompt outright, the turn mega opened for it now ends, saying why, and the next prompt is taken. A runtime that turns out to be on another session than its conversation's no longer adds anything to that conversation before it is stopped, and a Claude runtime is checked at every report, not only its first, and a Codex command still running is no longer imported as a failed result.

FIX: **A wrong answer to a pi dialog no longer removes the dialog.** (2026-11-19) An answer pi refuses, such as a choice it did not offer, is now refused with its reason and the dialog stays, to be answered properly or dismissed.

FIX: **An answer no longer lets work go on after you stop a turn.** (2026-11-19) Once you have pressed Interrupt or Release, Allow, Allow for the session, and an answer to a question, pi's dialogs included, are held on the card and refused by mega, saying the turn is stopping. Deny and Dismiss still work, so an interrupt pi holds for a dialog still ends when you dismiss it. Codex can no longer start a turn from an answer just after a stop.

FIX: **A request stays on the page until its answer is recorded.** (2026-11-19) An answered request used to leave the page before mega had recorded the answer, so a failed record hid a request the agent was still waiting on. It now leaves once the answer is recorded, a moment later than before, and a second answer meanwhile is refused.

FIX: **What a conversation counts as unread after something goes wrong.** (2026-11-19) Output from a runtime that died mid-turn is now counted when it exits, instead of by a later turn.

FIX: **After a reconnect or a restart, the page waits to say what it knows.** (2026-11-19) "Live" waits until no further workspace read is queued, and the shutdown banner no longer reports a shutdown from before a restart as under way until the restarted mega has confirmed it.

FEATURE: **pi is the third harness.** (2026-11-16) Conversations on pi (`@earendil-works/pi-coding-agent`, tested with 1.5.2) are launched, prompted, answered, interrupted, released, resumed by their exact session, discovered and adopted, as Claude Code and Codex conversations are. pi runs as it does in its own terminal, which differs from the other two in ways the page says plainly.
- **pi asks for nothing unless an extension asks.** It has no permission model and runs its tools without asking. The launch dialog and the conversation say so, and that it runs its own MCP servers, which mega cannot list.
- **A pi conversation lacks what pi lacks.** It has no permission mode control and no MCP menu item, and no effort control where the model takes one thinking level or none.
- **Its model and thinking level** come from pi's own settings, whatever provider they name, local or hosted, so a model pi is set up for works under mega unchanged.
- **Every pi dialog is a question.** pi marks none of its extensions' dialogs as an approval, so none is shown as one or allowed for the session. Each has **Dismiss**, which sends pi's own cancel, as Escape does in its terminal, and only when you press it.
- **mega never trusts a project for pi.** It never passes `--approve` and never writes pi's trust, so a project you have not trusted in pi's terminal runs without its extensions, and its conversations say so when they start.
- **Releasing with a pi dialog waiting ends pi's process**, since the dialog holds pi open, and the command it gates does not run; the release dialog warns you first. An interrupt with a dialog waiting says which dialog it waits on. A dialog's row in the history now ends "expired" when its own time limit ran out, or "never answered" when a release ended pi with it waiting.
- **Configuration snapshots** include pi's settings, models, MCP servers, extensions, skills, prompts and themes. Never its credentials, trust decisions, caches or sessions.
- **`make e2e`** has pi round trips, run on pi's own default model and skipped when it does not answer.

FEATURE: **mega keeps snapshots of each harness's configuration.** (2026-11-15) Claude Code and Codex update themselves and rewrite their own files, and nothing kept a copy from before. Now mega does, in its data directory under `snapshots/`, readable only by you, so a settings file an update rewrote or removed can be put back.
- **What is copied:** your settings, instructions, rules, skills, agents, commands and prompts, the plugin lists, the version and migration markers, and `~/.claude.json`. It follows `CLAUDE_CONFIG_DIR` and `CODEX_HOME` from your shell. A credential, transcript, session, history, database or cache is never copied, nor anything the list does not name. A link stays a link and is never followed.
- **When:** in the background at start-up when the configuration changed, and when a harness reports a new version, which is when a migration may just have run.
- **What it costs:** a file unchanged since an earlier snapshot is stored once, so a month of daily starts takes about 10 MB.
- **How many:** 10 ordinary snapshots and 20 taken at a version change are kept, set by `snapshots.keep` and `snapshots.keep_at_version` in the config file. `keep: 0` takes none.
- **Where to see them:** `mega version` and the version panel say when the newest was taken and where they are.
- **Restoring is yours.** `mega snapshots` lists them, and `mega snapshots diff NAME` names the files that differ from your live configuration and prints the copy commands. mega never writes into a harness's configuration.

FIX: **An interrupted turn no longer comes back with a reply of "No response requested."** (2026-11-15) After a turn is interrupted, Claude Code writes that line to its own transcript the next time the session is resumed and prompted. It never arrived live, so a later resume imported it as if the agent had said it, and after an unclean restart it could mark the conversation unread. mega now recognizes it by how Claude marks it in its transcript: a message written by no model that is not an API error. It is kept among the native events, hidden unless shown, and is never a reply and never attention. An API error, which Claude also writes with no model, is still shown as a reply, live or read back; so is any such message whose transcript mega cannot read.

CHANGE: **mega follows the installed Claude Code, and says where each harness's version stands.** (2026-11-14) mega no longer expects one exact build of each harness.
- **Claude Code** is `claude` on your `PATH` by default, the native installer's link to its newest build, in place of the fixed `~/.local/share/claude/versions/2.1.318`. With no `claude` on the `PATH`, as a desktop launcher's shell may have, mega runs the newest build in `~/.local/share/claude/versions/`. A `claude.executable` that names a versioned build keeps working while the build is installed. Once the installer prunes it, mega names the builds installed beside it and how to follow the installed one, and never says to install Claude Code while one is there.
- **The tested ranges** are Claude Code 2.1.318 to 2.1.325, with the shim's pinned Agent SDK 0.3.318, and Codex 0.163.0 to 0.169.0. mega reads each harness's `--version` at start-up and before each launch, giving up after two seconds. The start-up log, the first page, `mega version` and the version panel say each version found against its range. Nothing is refused for its version.
- **A newer build is the normal state.** Claude Code releases every day or two, so the installed build is usually above the range. It is said in plain words wherever versions are shown, never in the notice colour or as a warning, and the "Runtime started" line, which already names the version, gains nothing.
- **An older build is marked.** The Agent SDK expects the Claude Code of its own patch or later, so an older build is marked in the notice colour wherever versions are shown, with a sentence saying so. On the "Runtime started" line, the range follows the version and the sentence is its title. A version that cannot be read is called unknown, and is marked the same way everywhere but that line.
- **The first page says each harness in one short line:** its build, where it was found, and the range. Node and the shim are named in the start-up log.
- **Codex must be installed whole,** with npm or from the release's `codex-package` archive. The release's lone binary answers a turn but cannot run a shell command, so mega now names it as a lone binary wherever it names a missing harness, and names any helper program a package is missing.
- **`probes/versions/`** runs every call mega makes against a named build, through a scratch mega on the disposable fixtures. It is how a tested range is extended.
