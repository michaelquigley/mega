### Shape

- `shim/claude/shim.mjs`: the probe with the scenario machinery removed and the relay promoted to stdio. `run`, `messages`, `list`. `permissionMode: 'default'`, default setting sources, `includePartialMessages: true` for deltas. On `close` it waits for an interrupt in flight before ending input. The script exports `main(argv, sdk, io)` so `shim.test.mjs` round-trips the protocol against a fake SDK.
- `internal/harness`: `Harness` (`Name`, `Launch`, `History`), `Runtime` (`NativeID`, `Prompt`, `Answer`, `Interrupt`, `Close`), `Sink` (`Event`, `Delta`, `Request`, `Resolved`, `Exited`). Model types only. The adapter asks the sink for a service request id and keeps the SDK's `requestId` private, holding its own lock across that call so an answer cannot overtake the mapping.
- `internal/harness/claude`: process management, frame handling, the SDK-to-event mapping (shared by the live stream and history so both yield the same `NativeID`), sanitized marker-only testdata.
- `internal/harness/harnesstest`: a scriptable fake whose request numbers restart at 0 in every runtime, for the service and server tests.
- `internal/service`: `live` per conversation (the open log, the native ids it holds, the runtime and its incarnation, transient state, turn flag, facts, pending set), the sink, the operations in `conversation.go`, and `recovery.go` (start-up settlement, `Shutdown`, `Close`).
- `internal/e2e` (build tag `e2e`): C1 to C4 and a C6-style resumed turn against `claude-rt1`, with an import that must add nothing. Runs in about 17 s.

### Choices the work order left open, and deviations to review

- `Conversation.LastSeq` is no longer persisted (`dd:"-"`, read from the log), so recording an event never rewrites the registry.
- Model additions: `Conversation.Runtime` (`none`, `running`, `unsupervised`); `Event.NativeID`, `Status`, `Tool`, `ToolUseID`, `Facts` (`RuntimeFacts`). Runtime event states are `model.Status*`, since `model.Runtime*` names the recorded conversation states.
- The service reports transient states beside the recorded ones: `starting`, `stopping`, `resuming`.
- Native history is also imported when a prompt starts a runtime for a conversation with no runtime, not only on the explicit resume. Otherwise a prompt after release and a terminal visit, without pressing resume, would resume the session with the terminal turns missing from the cache. Import after a clean stop is safe because the service saw the runtime exit; `unsupervised` still refuses prompts until resumed.
- One turn at a time: a prompt while a turn is in flight is refused with 409, rather than queued in the SDK.
- `workspace_changed` now also fires for in-memory changes (runtime state, turn flag, pending set), so browsers re-read the workspace instead of the service inventing a second frame type.
- `not_pending` is its own error code (409).
- A runtime that reports a different session from the one it was bound to is recorded as an error and stopped.
- Removing a project is refused while any of its conversations has a runtime.
- Release has no deadline: the service owns the process and keeps reporting `stopping` until exit. Shutdown waits 30 s, then leaves stragglers recorded `running`, which come back `unsupervised`.
- The shim's location is stamped into the installed binary by the Makefile (`-ldflags -X ...config.defaultClaudeShim=$(CURDIR)/shim/claude`); `claude.node`, `claude.shim` and `claude.executable` override it. The shim runs in its own process group.
- A denial without a reason is sent as `the operator denied this in roundhouse`.

### Stage 2 transition helper (after Michael's review of round 4)

Michael asked for a structural fix rather than three more spot fixes: rounds 2, 3 and 4 each found one more place where displayed runtime state and the announcement ran ahead of the recorded event. The canon alternative was declined.

- `Service.transition(l, ev, state, apply)` records the runtime event first; only on success does it set the displayed `state`, run `apply` (turn flag, facts) and announce. `grep "l.state = "` finds only its body (`move`). Every runtime state change goes through it: `starting` (`beginStartLocked`), `running` (the harness's `started` report, in `sink.started`), `stopping` (`beginStopLocked`, used by release, shutdown, the wrong-session stop, and a session that could not be recorded), `stopped` and `error` (`sink.Exited`, and import failures), `resuming` and `resumed` (`Resume`).
- New runtime statuses `starting`, `resuming` and `resumed`, so each transition has an event to record. `running` now waits for the harness's own `started` report instead of following `Launch`; before it the conversation shows `starting`. `resumed` records how many messages the import added.
- Process actions do not depend on the record. `beginStopLocked` stops the process whether or not `stopping` was recorded. Operator actions that only change display (a start, a resume) are refused when their event cannot be recorded, before anything is read or launched.
- Internal guards sit apart from the displayed state: `busy` (a start or a resume is under way) and `releasing` (the current runtime has been asked to stop, reset when it exits). Release, shutdown, the prompt and resume checks, and project removal use them, so a refused `stopping` event cannot let `releaseRuntime` run twice. A mutation that drops the `releasing` check makes the process get asked to stop three times in `TestUnrecordedReleaseStillStopsTheProcessOnce`.
- Left as they were, per Michael: a failed launch shows no runtime even if its `error` event cannot be recorded (`failedLaunch`, the one forced transition); an answer leaves the pending set before delivery. `recordOrLog` had no callers left and was removed.
- New tests: an unrecorded release still stops the process once, with the state unchanged and nothing announced; an unrecorded wrong-session report still stops the runtime and never shows it running; an unrecorded resume is refused before history is read. The e2e now skips runtime events when checking that an import adds nothing, and asserts `resumed` reports 0 messages added.
