## Batch: the panel shows the request, the turn shows what ran (implementation agent)

Built to `docs/future/roadmap/the-panel-shows-the-request-the-turn-shows-what-ran.md`. The card's state is left as Michael set it. The header batch of 2026-11-12 was still uncommitted in the tree when this began.

### Established first

**1. The runtime events are not enough; the turn's own events must carry what it ran with.** The log has `started` (model, version, mode, and Codex's effort), `model_changed` and `mode_changed`. Four gaps:

- **The recent tail.** A conversation opens on its last ten turns. The `started` or `model_changed` that set a turn's state can be far behind them, so the page cannot rebuild a turn's state from what it loads.
- **Requests are not in the log.** `SetModel` and `SetPermissionMode` rewrite only the registry's current choice; no event records what was asked. So nothing in the log says what a past turn requested, and a mismatch cannot be judged for it.
- **Claude's effort is nowhere.** Claude never reports effort (`init` has none; capability report, 2026-11-10), and the effort sent is only the current choice, overwritten by the next change.
- **Claude's init is mostly native.** Claude re-sends `init` at every turn, but the adapter records a `model_changed` or `mode_changed` only when it differs from the last report. Most turns have no runtime event of their own.

So the service records, with each turn, what it asked and what the harness reported for it. Turns recorded before this carry neither, and show nothing.

**2. Copying Claude's settings.** `Inherited` reads the first `model` and `effortLevel` the settings layers name, and `InheritedPermissionMode` the first usable `permissions.defaultMode`. Neither reads per-model `modelSettings` or environment variables.

- **The model.**
  - A value the list holds as a row's `value` (`opus`, `claude-fable-5-2`) copies as it is.
  - A missing value, or one no row holds (an alias the list lacks, or a full id such as `claude-opus-5-5` that is only some row's `resolvedModel`), takes the list's default row, `default`, "Default (recommended)". It resolves to `claude-opus-5-5` in 2.1.318. Passing it is concrete for Claude, though Claude's own default moves with its versions.
  - Checking against the list needs the list, which means running the shim in the project's environment. Without it, the value can only be checked for form, as `checkModelChoice` does today.
- **The effort.** Claude's list carries no default effort: each row has only `supportedEffortLevels`, and Claude never reports what it runs. A settings `effortLevel` the chosen model offers copies as it is. A model with no levels (Haiku 4.5) takes none, which is that model's only value, not an unset one.
  - **A missing `effortLevel` has no concrete value to copy.** Any value mega picks is a guess at Claude's own default. This is the card's stop-and-ask case.
- **The mode.** A settings mode mega offers copies as it is. A missing one, or one mega never passes (`bypassPermissions`, `dontAsk`), becomes `default`, per the amended `permissions-never-weakened`.
  - `dontAsk` denies what is not pre-approved, so `default`, which asks instead, offers the operator approvals `dontAsk` would have refused. The canon names that case and accepts it.
- **Codex.** `config/read` gives `model` and `model_reasoning_effort`, and the model list has an `isDefault` model with its `defaultReasoningEffort`, so Codex always has concrete values. Asking needs an app-server in the project's environment.
- **Michael's own settings**, checked by key only: `~/.claude/settings.json` names `model` and `effortLevel`, and no `defaultMode`. `~/.codex/config.toml` names both. His own copy is concrete.

**3. A mode switched during a turn.**
- **What shows today.** Claude confirms a switch with `permission_mode_set`, and the adapter records `mode_changed`, which draws a "Permission mode X" row in the history where it happened. A report that only confirms the mode the launch requested is marked `mode_confirmed` and draws no row.
- **The turn's line** names the mode the turn started in: the mode Claude reported at the turn's start, which is in effect when its first output arrives. A switch later in the turn keeps its own row; that row says the change, and the next turn's line names the new mode.

### Michael's calls

Two of the card's stop-and-ask cases came up; Michael chose both recommended answers.

- **Claude's missing effort: choose at launch.** When the Claude settings name no `effortLevel` the copied model offers, the launch dialog preselects none and Launch waits. The service refuses such a launch as `invalid`. The checks' scratch settings name `effortLevel: medium`, so their conversations copy one.
- **The fill-in's corner: fill at the next launch.** The start-up fill takes what each log reported. What it cannot fill, Claude's effort above all, is filled at that conversation's next launch or Start, from the settings, before anything is passed, as the same kind of recorded change.

### What was built

- **The request is concrete from creation.** `service.copyFor` completes a request from the harness's `Settings` and model list. The rules are in `docs/current/mega.md` under "What a conversation requests". `StartConversation` copies once, before the conversation exists, and checks the result against the list. **Adoption copies too:** it creates a conversation, and the card's rule is "copied once at creation". A Claude adoption whose settings name no effort is adopted without one, and its first launch is refused until one is chosen on the bar. That applies Michael's effort call to the one creation path with no dialog.
- **The fill.** At start-up, `fillChoicesLocked` runs in `service.New`, after `recover` and before the server answers. At launch, `fillAtLaunch` runs in `startRuntime` before `prepareLaunchLocked`. Each records a `choice_filled` runtime event before writing the registry. On a rerun, a recorded fill is re-applied from its event, with nothing recorded again. The start-up fill reads whole logs (`Since(0)`) under `s.mu`, once per conversation that lacks something; none lacks anything after the first run.
- **The turn record.** `turn_end` events carry `turn` `{asked, ran, differs}`. `asked` is taken when the prompt is sent (`beginTurnLocked`). `ran` is taken at the turn's first non-user output (`ranLocked`). `differs` compares models through the cached list. The list is prefetched in the background after every successful launch, so a mismatch is found even on a conversation whose models nobody has listed. The live view carries `turn_asked`, `turn_ran` and `turn_differs` for the turn in flight, so the UI never compares aliases itself.
- **Removed.**
  - The project's `inherited_permission_mode`, and the service option behind it.
  - From `RuntimeFacts`: `ModeInherited` and `ModeRequested`. `ModeConfirmed` stays for old logs.
  - From the conversation's read: `permission_mode_inherited`, `permission_mode_requested`, `model_next`, `effort_next`, `model_next_inherit` and `effort_next_inherit`.
  - The live state behind them: `next*` and `pendingSetting`.
  - Claude's `launchMode` and `Inherited`. The adapter keeps `settingsMode`, as part of `Settings`.
  - Codex's `config/read` before launches and turns, and its `Inherited`.
  - `SetModel`'s inherit rule.
  - The models read's `inherited` field, now `copy`.
  - In the UI: `next.ts`, the bar notes, every inherit label in `models.ts`, the "Not chosen" options, the launch dialog's inherit options and `App`'s `inheritedMode`.
- **A full id resolves to its alias.** A Claude conversation filled from its log holds the full id Claude reported, such as `claude-opus-5-5`. The list holds that only as an alias's `resolved`, so checking it would have refused any effort chosen for it. `catalogRow` matches an id first, then a non-default row that resolves to it, then the default row, for the effort lookup, `checkModelChoice` and `offersEffort`. The settings copy still takes the default row for a full id, as question 2 settled.
- **The UI.**
  - `ShortSelect` lays a transparent native select over a short value. The open list is the browser's own, with the full descriptions. Playwright's `selectOption` works on it, since opacity 0 counts as visible.
  - `EventList` groups each turn's blocks, through its end, into a `.turn-block`, a flex column with the same 16px gap, so the layout is unchanged. The line is absolutely placed over the separator's right end.
  - The turn in flight gets a `.turn-end.pending` placeholder with an unseen separator, so its line has space. That adds the separator's footprint below the turn in flight, which the turn's end then fills.
  - A `choice_filled` event draws as "Request filled in from …: model · effort · mode".

### Gotchas

- **The e2e package did not compile** before this batch. `server.New` gained its `About` argument in an earlier batch, and `go vet ./...` never builds the `e2e` tag. Fixed with the new fields. Vet it with `go vet -tags e2e ./internal/e2e/` after changing anything it calls.
- **The UI bundle crossed Vite's 500 kB warning,** at 500.20 kB against 492.64 kB at HEAD for the committed tree. The uncommitted header batch and this one together pushed it over.
  - **Michael chose to split it.** `ui/vite.config.ts` sets rolldown's `output.codeSplitting` with two groups: `react` (react, react-dom and scheduler, priority 2) and `vendor` (the rest of `node_modules`).
  - The result is `react` at 218.74 kB, `vendor` at 174.38 kB, mega's own `index` at 107.30 kB and a 0.72 kB rolldown runtime, with no warning.
  - All load with the page; the split is for size, not laziness. `advancedChunks` is the deprecated name for the same option in rolldown 1.2.19.
- **A `has:` locator in Playwright is relative** to the element it filters, so `filter({ has: page.locator('.events .x') })` never matches inside a block below `.events`. Write the inner selector alone.
- **The turn line overhangs the separator** by a few pixels into the gap below, so an element screenshot of a turn block clips it. The conversation suite clips its turn shots with an 8px margin.

### The review

- **Round 1 was not clean,** with one blocking finding under `permissions-never-weakened`. A permission mode changed with no runtime wrote only the registry, with no event, though the quality says a mode change "is recorded as an event and shown in the conversation". The stored path predates this batch, and earlier reviews had passed it.
- **Michael chose to record stored changes.** The service records a service-origin `mode_requested` event, then writes the request to the registry (`storeModeLocked`).
- **Round 2 was not clean,** again under `permissions-never-weakened`. The first version wrote the registry first, so a crash between the two writes left a stored change with no event. The order is now event first, as the fill's is:
  - A log that cannot record the event refuses the change.
  - A failed registry write is recorded by a second event putting the request back.
  - A crash between the two leaves the request as the log's last event. `s.mu` is held across both writes, so nothing else is appended in between. `recover` applies the request from that event at the next start (`settleModeRequestLocked`), before anything else is recorded, and records nothing more. Every log is already open there, so the check is one `Tail(1)`.
- **Round 3 was not clean.**
  - **The blocking finding:** a live switch still wrote the registry before any event, relying on Claude's confirmation, so an unconfirmed or interrupted switch was stored unrecorded.
  - **Michael chose to record live requests too.** Every change now goes through `requestModeLocked`, event first: stored, live ("asked of Claude"), and a refusal putting it back ("Claude refused X, so the request goes back").
  - **The history hides a confirmed request.** A request row is drawn only when the next mode event after it is not Claude's report of the same mode, so a confirmed live switch shows Claude's row alone.
  - `TestUnrecordedReportKeepsTheLastConfirmedMode` now closes the log during the switch, since a switch whose request cannot be recorded is refused before Claude is asked.
  - **The non-blocking finding:** a stale API paragraph in `docs/current/mega.md` still named the removed fields. It is fixed.
- **Round 4 (`b6d40402c883`) was clean.** Its one non-blocking finding, a comment naming `service.fillChoices` for `fillChoicesLocked`, is fixed. The event never raises attention, since attention follows `output_seq`. `lastReported` ignores it, so the fill never takes it for what ran. The history draws it as "Permission mode X requested: the next launch passes it". A live change is recorded twice over, as round 3 settled: the service's `mode_requested` first, then the harness's own `mode_changed` as the report.
