## Piece 1, streamlined (implementation agent)

Michael: "streamline and simplify the code where possible", keeping the behaviour he approved.

### What went

- **The steering map, its per-steer channels, and the exit's copy of them.** One `sync.WaitGroup`, `steering`, replaces them.
  - `Answer` counts a steer with `Add` in the same hold of `r.mu` as the stop checks and `begin`, so the count is taken before the write lock is let go.
  - `Done` is deferred, so it runs after the `Resolved` of whichever settlement the reply produced.
  - `watch` takes `r.mu` before it calls `Wait`. So every steer written is counted before the wait starts, and after the connection has closed `begin` fails and nothing more is counted.
  - The replies and the settlements are awaited outside `r.mu`.
- **`answerDelivered` and the second map.** The service now keeps one map, `reserved`. It holds `answerInFlight` while an answer is on its way, or else the outcome of a settlement that could not be recorded yet; `live.unrecorded` reads it.
  - **Rewritten on it:** the answer's entry check, `holdsRequests`, `retireRequestsLocked` and `settleLocked`.
  - **The answer's tail now settles once.** It records a crossed settlement's outcome if there was one, or else the outcome that follows from the answer's result. It then says what it must. The three duplicated settle-and-log branches and the second `not_pending` message are gone.
- **`takeQuestions`, and the four take-and-report sequences built on it.** Interrupt, a release's fence, a turn's end and the exit now each call `abortQuestions`, which holds `aborting` from taking to reporting. Each caller makes its own state change first, in its own hold of `r.mu`.
- **Answer no longer drops a question it refuses.** The question leaves the adapter only once its steer is written, in the same hold. A refused one stays for the abort that ends it.

### What a later session would rediscover

- **On macOS 26, Control Center draws every status item,** the application's own included. A window list by the daemon's pid finds nothing even when the item shows. `probes/macos/menubar.c` counts items before and after instead.
- **A shell script as `CFBundleExecutable` hides the menu bar item.** It did so with a login shell and with a bare `exec`. Hence no launcher: the binary is the executable, and project environments do the operator's shell. Do not "fix" this with a wrapper script.
- **`open` from a terminal passes the terminal's environment to the application.** To see what Finder gives (`PATH=/usr/bin:/bin:/usr/sbin:/sbin`, `SHELL`, no `LANG`), start it with `env -i … open`, as `probes/macos/app.sh` does. Reading `ps -E` of an application Finder started confirms it.
- **`LSEnvironment` (`MEGA_APP=1`) is how a bare launch becomes `daemon`.** `launchArgs` reads it, and `main` clears it. A test holds `cmd/mega/macos/Info.plist` to `appID` and `appLaunchEnv`.
- **Everything mega starts is "mega" to macOS's privacy controls,** and an ad-hoc signature changes each build. On the first start of each build, `ssh-add --apple-load-keychain` in Jens's zsh start-up brought up a dialog and held the shell 34 to 35 seconds, past the 10-second default. The start-up harness check then fell back to mega's own `PATH` and found nothing. Answered, the next start took under 2 seconds. Outside the application the same shell takes about 1 second, with `setsid` and the agent socket alike, so the identity is the cause. Jens did not notice the first dialog and did not say what it read.
- **webview_go's WKWebView UI delegate is freed as soon as it is set.** So no file chooser, and new-window links were dropped. dfw now holds its own delegate. Mega's UI has no file input today; its Markdown links are `target="_blank"` and now open in the browser.
- **The window's activation needed a retry.** Opened from a tray menu, it lost the focus back to the previous app as the menu closed. dfw activates again at 800 ms if not active. LaunchServices spawning was tried and is not needed.
- **`go mod tidy` adds webview_go to `go.mod`** although only `window_darwin.go` imports `dfw/webview`. tidy counts every platform's imports, and Linux never compiles it.
- **The window process logs nowhere kept.** It uses `initLogging(false)`, so it never rotates the daemon's log, and the application's stdout is not kept. A window that fails to open is seen only as no window.
