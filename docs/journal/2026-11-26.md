## The adoption limit is a plan: the cut goes (design and planning agent)

Michael, on a session the adopt dialog's list does not reach: "if i don't have the id, it's probably just lost? not sure what the right answer is there." It is not lost: the session is in its harness's own store, and what cannot reach it is mega's cut at the 50 newest. The card `adoption-reaches-any-session-in-the-checkout` removes the cut for Codex and pi, and is in building.

- **Claude already lists the whole checkout.** The shim's `list` passes no limit, one Claude checkout on this machine holds 436 session files, and the dialog has a filter on the first prompt. So the page should need nothing new for a long list. Files were counted, not rows in the dialog, and the card has the implementer confirm the SDK has no cap of its own.
- **The exposure is real for pi.** One pi checkout here holds 183 sessions, counted as files only, so 133 cannot be adopted today. The inventory's "no real checkout is past 50" was a count of Codex alone.
- **The first version of the card was wrong and was replaced before anyone built from it.** It had adoption take an exact id past the list, with a field for it, and a "Show more" control. Reading the adapters showed the list is the only thing that says a session belongs to a checkout: pi's read by id falls back to any checkout's folder, and Codex's `thread/read` takes no checkout. Adoption by id would have added a check to each adapter. Removing the cut adds none.
- **An id still has a use.** The dialog's filter is to match the id as well as the first prompt, so an id copied from a conversation's header finds its session.
- **Not yet known:** whether Codex's `thread/list` pages. The card's first step asks it for a page of two against the fixture checkout.
