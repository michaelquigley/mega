## A failed write stops mega (implementation agent)

The card `a-failed-write-stops-mega` was built from the card alone.

**The listing came first.** The service had nine registry writes and sixteen log writes. Every branch that handled a failure of one did one of four things. It stopped a runtime anyway, which the card rules out on the way down. It kept an `unrecorded` outcome, or put a mode request back, both named for removal. Or it left state the next start already settles: a conversation recorded running becomes unsupervised, the unread marker is rebuilt from the log, a mode request is applied from its event. None did something the next start would not put right, so none was brought to Michael before removal.

**The shape.**

- **The two wrappers are the one place.** `update` wraps the function it is given, so its own refusal (a conversation that does not exist) is told apart from a write that failed, and `failUpdate` runs inside, after that function. `appendEvent` runs `failRecord`, then the append. A failure in either calls `failed`, which calls `Options.Exit` and panics if that returns.
- **The exit comes from `cmd/mega`.** It is `exitAtFailedWrite` in `cmd/mega/startup.go`: an error line and `os.Exit(1)`. `New` refuses options with no `Exit`. The other packages' test services pass one that panics.
- **The stores decide nothing.** `registry.Update` returns a failed write or directory sync, and memory stays where it was. `events.Log.Append` returns a failed write or sync, with nothing confirmed. Both uncertain states and the rollback are gone.
- **Creating a log is its first append,** so there was no third place to meet a failure. `events.Open` of a log that does not exist writes nothing and reads as empty. A closed log takes no append, so a dropped conversation's log is never made again.
- **The refusal after close stays.** `update` refuses as before. `appendEvent` drops the event once the logs are closed, because a closed file would otherwise fail the append and end the process during an orderly stop.
