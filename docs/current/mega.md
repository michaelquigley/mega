# mega as built

build your constellation.

The words used here and across the cards are fixed in `docs/current/glossary.md`.

This describes what exists now: the whole first slice, whose work order was retired when its last stage gated (git history holds it; the spec is `docs/future/mega.md`). That is the environment service with projects; Claude Code, Codex and pi conversations launched, prompted, answered, interrupted, released for a terminal, and resumed; native sessions discovered and adopted; and attention, with a needs-you list, reading positions, and a next-waiting shortcut. Polish since then: conversations can be removed, and a conversation opens at its latest activity.

## Shape of the code

One Go binary, `mega`, in the module `github.com/michaelquigley/mega`, with `github.com/michaelquigley/df/dl` for logging and `df/dd` for YAML and JSON. The name is lowercase `mega` everywhere, the page's title included; "metawoo mega" appears only in the README's first sentence, never in the running interface. The tagline, "build your constellation", is provisional and kept in one constant on each side, `tagline` in `cmd/mega/main.go` (the root command's help, the launcher's comment) and in `ui/src/brand.ts`, beside `productName`, which the page's title and its notifications use. Changing the tagline is those two lines, and the prose that quotes it. The name stays out of data and identifiers, except the binary and the XDG directory names, which follow one constant. TypeScript appears only in the Claude shim and the UI. The project was called roundhouse until 2026-11-11.

internal/config/         mega.yaml; defaults; path expansion
internal/model/          Project, Conversation, Event, Request, attention, MCP servers; no I/O, no protocol

                         history, discovery, the trust notice, and a fake pi for tests and checks

Dependencies point inward. `server` depends on `service`; `service` on `harness`, `registry`, `events` and `model`; the adapters on `model` and `harness` only; `registry` and `events` on `durable`; `model` on nothing. Everything protocol-shaped (SDK messages, JSON-RPC methods, the shim's frames) lives inside its adapter package or the shim.

## Running it

`make` builds the UI, installs the Claude shim's pinned dependencies (`npm ci` in `shim/claude`), and installs the `mega` binary into the project's `GOBIN`, stamped with the shim's location in the checkout. `mega` (or `mega serve`) runs the service; `mega daemon` runs the same service with a tray icon (below); `mega version` prints build information, where the log file is, what this mega is called and why ("name: fortyfive, the machine's hostname"), each harness's tested range with the version it finds in mega's own environment, and when the newest configuration snapshot was taken and where the snapshots are. `mega snapshots` lists the configuration snapshots, and `mega snapshots diff NAME` compares one with the live configuration (below). `make clean` removes only what the project builds: `ui/dist`, `ui/node_modules`, `shim/claude/node_modules`, and the `mega` binary in `GOBIN`. `--config PATH`, `--data DIR`, `--listen ADDR` and `--verbose` apply to `serve`, `daemon` and the bare form.

| Item | Default | Override |
| --- | --- | --- |
| Config file | `$XDG_CONFIG_HOME/mega/mega.yaml` (`~/.config/...`), optional | `--config`, which must exist |
| Data directory | `$XDG_DATA_HOME/mega/` (`~/.local/share/...`) | `data` in the config, then `--data` |
| Listener | `127.0.0.1:6342`, 8470 before 2026-11-18 | `listen` in the config, then `--listen`, held to loopback the same way |
| What this mega is called | the machine's hostname, up to its first dot | `name`, at most 64 characters, none a control character |
| Node | `node` on the project's `PATH` | `claude.node` |
| Claude shim | `shim/claude` in the checkout `make` ran in | `claude.shim` |
| Claude Code | `claude` on the project's `PATH`, else the newest native build in `~/.local/share/claude/versions/` | `claude.executable`, a native build (a script is refused); a path is checked before anything runs |
| Codex | `codex` on the project's `PATH`, installed whole | `codex.binary`; a path is checked before anything runs |
| pi | `pi` on the project's `PATH`, with the `node` its `#!/usr/bin/env node` line names | `pi.binary`; a path is checked before anything runs |
| Shell for project environments | the absolute path `SHELL` names, else `/bin/sh` | `environment.shell` (absolute) |
| Resolution timeout | `10s` | `environment.timeout`, a Go duration |
| Configuration snapshots kept | 10 ordinary, 20 taken at a version change | `snapshots.keep` (0 takes none) and `snapshots.keep_at_version` |
| Directories the `@` search reaches beyond the checkout | none | `path_search.directories`, each from `~` or `/` (a relative one is refused) |
| Where the register dialog's folder picker starts | the home directory | `projects_root`, from `~` or `/` |

**Finding Claude Code.** The default executable is the bare name `claude`, which is looked up on the `PATH` mega uses for the project, as the native installer's link to the build it last installed. A launch takes whatever build the link names at that moment, and a running runtime keeps the build it started with until it is released.
- **The fallback.** With no `claude` on that `PATH`, as the shell a desktop launcher starts may have, mega runs the newest native build in `~/.local/share/claude/versions/`, under the `HOME` that environment names. It reads that folder and nowhere else. A build is a regular executable file named for its version that is not a script. The start-up line and the first page say the build is "the newest build installed, with no 'claude' on the PATH". With none there either, the reason names the folder: "'claude' was not found on the project's PATH, and no build is installed in '…/versions'; install Claude Code, or set claude.executable … to where it is".
- **A configured versioned path** keeps working while the build exists. The installer prunes old builds, keeping the two newest, the linked one and any a session runs (its documentation, read 2026-11-14). Once the path is gone, the reason names the builds installed beside it, newest first, and how to follow the installed one: "'…/versions/2.1.318' is not installed; the builds installed beside it are 2.1.325, 2.1.322. to follow the installed Claude Code, set claude.executable to claude in '…/mega.yaml', the config file mega read, or remove it from there; or name one of those builds". With no config file read, nothing named the path in one, and the reason says "use claude in its place" instead. It never says to install Claude Code while a build is there; with none beside it, it does.

`listen` must be a loopback address, from the config or from `--listen`; the service refuses to start otherwise, because this slice has no login. A data directory that does not exist is created at start-up; mega does not look for a workspace under its former name, roundhouse. The service binds its port before reading any data, so a second instance on the same port exits without writing. It then takes an exclusive hold on `<data>/lock` before loading the registry, so a second instance on another port that shares the data directory also exits, and the directory has one writer. The hold is released by the kernel when the process exits; the file itself stays. The holder writes its address into the lock file. The default port moved from 8470 to 6342 on 2026-11-18. A build with the new default started while an older mega still serves 8470 on the same data directory binds 6342, finds the directory held, and exits naming the running one at 8470. It never runs beside it. Either refusal names the mega already running:
- on the port, mega asks what is listening there. If it answers mega's workspace read, the message reads "another mega is already running at 'http://…'; open it there, or stop it"; otherwise the port is said to be in use by another program.
- on the directory, "another mega is running on the data directory '…', at 'http://…'". An instance from before the record is refused without the address.

`serve` reports either refusal and exits non-zero. The daemon instead hands over when the other instance answers as mega, as the desktop launcher does when mega is already up. That holds on the port, by the same probe, and on the data directory, by probing the address its holder recorded. The daemon opens that instance's page, logs that it did, waits up to two seconds for the opener, and exits 0. A port held by something that is not mega, a recorded holder that does not answer, or a page that cannot be opened is refused as before. So is a mega that has closed and not yet stopped, since it refuses the workspace read the probe makes.

`serve` and `daemon` share this start-up, in `cmd/mega/startup.go`, and one orderly stop: every runtime released and waited for, each conversation recorded with no runtime, subscriptions closed. They differ only in who serves and how the end is announced.

### The daemon

`mega daemon` runs the service as `serve` does, under a tray icon, through `github.com/michaelquigley/dfw/tray` (v0.1.6; the tray needs no native packages, so the build stays cgo-free). The app id is `com.michaelquigley.mega` and the tray title `mega`. It opens no window of its own: the browser is mega's window. dfw writes its runtime file under `$XDG_CONFIG_HOME/com.michaelquigley.mega/runtime/` while the daemon runs, and removes it at the end.
- **The tray menu.** "open mega" opens the page in the default browser (`xdg-open`). "shut down when idle" arms the gate and opens the page, so the operator sees what it waits for; while the gate is armed, from the tray or from any page, the item reads "cancel shutdown" and lifts it. dfw adds Quit.
- **Quit goes through the gate.** Quit arms the gate and asks the service to shut down, which it accepts only if the workspace is idle at that moment, the same acceptance a page's Shut down has. Then the orderly stop runs and the tray goes. Otherwise the gate stays armed, the page opens on what it waits for, and the daemon keeps running: a stray click can never interrupt an agent, answer a request or release a runtime. dfw is always told not to quit by itself, so the page is served until the stop is done.
- **Every way out is the orderly stop.** A shutdown accepted from the page, Quit on an idle workspace, and SIGINT or SIGTERM each run the stop `serve` runs, then end the tray with `Control.Stop`. dfw then closes the server, and mega exits 0. If the tray itself fails, the stop still runs before mega exits.
- **The icon is live.** The tray follows the service's own `workspace_changed` updates. While the needs-you list is not empty, it shows the needs-you mark (`cmd/mega/tray-icon-needs-you.png`), with the tooltip "mega: 1 needs you" or "mega: 3 need you". Otherwise it shows the mark (`cmd/mega/tray-icon.png`) and "mega". The list holds unread output as well as requests, as the page's tab does. Nothing is re-sent when nothing changed.

### The desktop launcher

`mega desktop integrate` installs a launcher that runs the daemon; `mega desktop remove` takes it away. Both follow ranger's.
- **The entry.** The desktop id is the app id the tray uses, so GNOME ties the launcher, its icon and the tray together. `integrate` writes `com.michaelquigley.mega.desktop` in `$XDG_DATA_HOME/applications` (for an absolute `XDG_DATA_HOME`, else `~/.local/share/applications`), with:
  - `Type=Application`, `Name=mega`, `Comment=` the tagline;
  - `Exec` starting the daemon through the operator's interactive shell (below);
  - `Icon=com.michaelquigley.mega`, `Terminal=false`, `Categories=Utility;Development;`;
  - no `StartupWMClass`, since the browser is the window.
- **The icons.** The mark goes into the hicolor theme at 32, 48, 192 and 512 pixels, under the same basename, from the PNGs in `cmd/mega/` embedded in the binary.
- **Idempotence.** Each command prints every file it wrote or removed. `remove` deletes exactly the files `integrate` writes and nothing else, skipping any already gone, and both are safe to run twice. Running `integrate` again after the binary moves repoints the launcher.
- **No autostart.** mega starts when the operator starts it.

- **Through the operator's shell.** A desktop launcher starts programs with the desktop session's environment. That lacks whatever the operator's shell start-up files add, such as a `PATH` with `node`, `codex` and the toolchains the agents run, and before project environments every agent inherited mega's. So `integrate` writes an `Exec` line that runs the shell named by `SHELL` at the time, as an interactive shell, executing the binary with `daemon`: `"/bin/bash" -i -c "exec '/path/to/mega' daemon"`. mega then has the environment a new terminal has. Each project's work now runs in that project's own resolved environment (see project environments), so this matters less than it did, but a mega started either way resolves the same. The binary's path is quoted twice: for the shell (POSIX single quotes for bash and zsh, fish's own escapes for fish), then by the desktop entry's quoting rules.
  - bash, zsh and fish are known. An unset `SHELL`, a relative one, or another shell falls back to the direct form, `Exec="/path/to/mega" daemon`, with a printed warning.
  - `--plain` writes the direct form on purpose.
  - `integrate` prints the `Exec` line it wrote and one sentence on why.
  - An interactive bash started without a terminal prints "no job control" to the launcher's stderr. That is harmless.

### The log file

At start-up mega logs its own `PATH`, once, and the shell and timeout project environments resolve through. Its own `PATH` reaches nothing it starts in a project's name. When `serve`, `daemon` or the bare form runs with no terminal on stdout, as when the launcher starts the daemon, `dl` output is appended as JSON lines to `$XDG_STATE_HOME/mega/mega.log` (for an absolute `XDG_STATE_HOME`), else `~/.local/state/mega/mega.log`. The directory is private (`0700`) and the file `0600`. "No terminal" means no real TTY: `/dev/null` counts as none. On a terminal, output goes there as before. `mega version` prints the path. The file is capped at start-up: one larger than 10 MB is renamed to `mega.log.1`, replacing any earlier one, and a fresh `mega.log` begins. A running mega's log grows until its next start.

## Data

The data directory holds `registry.yaml`, the authority for projects and conversations, and `conversations/<id>/events.jsonl`, one append-only event history per conversation. Only the service writes either, and only removing a conversation or a project deletes a log. Both are private to the operator (mode `0600`, directories `0700`).

The registry is plain YAML, readable with the service stopped. It is written to a temporary file, synced, and renamed, and the directory is synced after the rename; the service's in-memory state only advances once all of that succeeds, so what a browser sees is what a restart would read. The registry keeps the reading position for each conversation. The newest agent output lives in the event log. A version 1 registry from an earlier build can still carry `output_seq`. The reader ignores that key, and the next registry write drops it. A registry with an unknown `version` is refused. Every directory the service creates under the data directory, including the data directory itself, has its parent synced, so a new workspace or conversation cannot vanish in a crash while its synced contents would have survived.

An event log assigns each event the next `seq`. An append returns only after the line is synced, so an event a browser has been sent survives a crash. A log is created by its first append; opening a log that does not exist yet writes nothing and reads as empty. Before the first event is written, the directory that names the log is synced, whether the append created the file or found it empty, as a crash or a failed sync after its creation leaves it, so no event lands in a file whose name a crash could still lose. Only completed events are logged; streaming text is never written, so this costs a few syncs per turn. On open, an unterminated final line is a write torn by a crash and is dropped; any other unreadable line stops the open and leaves the file alone.

**A failed write stops mega.** The registry and the event logs are the record, and a write to it that fails, a write, a sync, or the creation of a log, ends the process at once, the way a crash would leave things. It is met in one place, the service's two write wrappers, `update` for the registry and `appendEvent` for a log; the stores return the error and decide nothing, and the process is ended by a function `cmd/mega` supplies, which logs the reason at error level and exits with status 1. Nothing is stopped on the way out: no runtime is released and no page is told. Whatever a harness was doing goes on unwatched until its own pipes close or its turn ends, a command already under way may finish what it was sending, and the page shows the service as unreachable. The next start is the start after a crash: a conversation that was running is unsupervised, a request that was pending is `lost`, and a mode request whose registry write never landed is applied from its event. Nothing else under the data directory is the record: a configuration snapshot is best effort, mega's own log file and the tray's runtime file are diagnostics, and a log directory that could not be deleted is left behind. Once the service has closed, nothing more is written to either: a registry change is refused as `unavailable` and an event is dropped, whatever was still in flight. A command still in flight then goes on as if its event were written, and changes nothing a read can show: an answer that returns after the shutdown deadline, for one, takes its request out of a live record the service has let go of and no read reaches, and the next start, finding the request still pending, resolves it `lost`.

Each open log keeps an index in memory (`internal/events/index.go`). It is built by the scan an open already makes, kept on every append, and never written, so a restart rebuilds it. It holds where every 256th event begins (a seek point) and where each turn starts. A read seeks to the nearest point at or before where it starts, so it parses what it returns and at most 256 events more, never the log from its top. A read that returns nothing new costs about a millisecond on a 55 MB log. Before the index it parsed the whole log, about 0.4 s.
- **Where a turn starts.** At the log's first event, and at the event after each `turn_end`, so the events between two turns (runtime lines, an init) travel with the turn that follows them.
- **Imported history.** History read from a harness carries no `turn_end`. A prompt in it (a `user` event of origin `native`) also starts a turn, once the turn before holds a prompt, reply, tool call or request and no tool call in it waits for its result. That turn then starts at the first event after the previous turn's last such event.
- **A call is never split from its result.** A call in an adoption snapshot or an older import stays with its result. An Unsupervised entry is also a paging boundary. It keeps an unfinished turn apart from the next one while leaving its outcome unknown.

An event is `{seq, at, kind, origin, text, native_id, status, tool, tool_use_id, req, facts, raw}`. `kind` is `runtime` (with `status` starting, started, stopping, stopped, unsupervised, resuming, resumed, error, mode_changed, model_changed, mode_requested or choice_filled; a `started` event carries the runtime's `facts`: session, model, effort where the harness reports it (Codex), version, permission mode, cwd; a `mode_changed` event carries the new permission mode; a `model_changed` event carries the model, and for Codex the effort, as the harness reported them; a `mode_requested` event, `service`-origin, carries a permission mode the operator requested, or a request put back, never a report of what runs; a `choice_filled` event, `service`-origin, carries what the one-time fill wrote, with where it came from in `text`), `user`, `assistant`, `tool_use`, `tool_result`, `request`, `request_resolved`, `turn_end` (`status` success, error or interrupted, and `turn`, what the turn asked for and ran with, below), or `native` (anything else the harness emits, kept in `raw`). `origin` is `managed` for what a runtime managed by the service produced, `native` for entries read from the harness’s own history into the timeline, and `service` for the service's own bookkeeping. `native_id` is the harness's identity for the message an event came from; adoption preserves it in the snapshot. A live event with an ID the log already holds, including an echo of a snapshot row, is suppressed. Builds before 2026-11-24 marked output that arrived after its turn ended with `after_turn`; a log that has it reads as any other, and the key is ignored.

`text` is recorded whole for user prompts, assistant text, tool results and native events, in both adapters. The one bounded text is a `tool_use` summary line, such as `Bash sleep 3` or `shell printf x > f`, which is a title: it is cut at 200 bytes, on a character boundary, with an ellipsis, and the full call stays in `raw`. Logs written before this cut every `text` at 4000 bytes, and they are not rewritten: events already recorded keep their clipped `text`, with the whole message in `raw`.

### Configuration snapshots

mega keeps dated copies of each harness's configuration under the data directory, in `snapshots/`, away from the places the harnesses and their updaters manage, so a file an update rewrote or removed can be put back by the operator. It only ever reads a harness's configuration (`internal/snapshot`).

- **What is copied.** Each adapter owns an include list (`harness.Configurer`), so another harness adds its own. A file the list does not name is never copied, so whatever a new harness version adds stays out until someone decides.
  - **Claude Code,** in `CLAUDE_CONFIG_DIR`, else `~/.claude`: `settings.json`, `CLAUDE.md`, `keybindings.json`, `skills/` without `skills/synced/`, `agents/`, `commands/`, `output-styles/`, and `plugins/installed_plugins.json`, `known_marketplaces.json` and `blocklist.json`. Also `.claude.json`, in `CLAUDE_CONFIG_DIR` when that is set, else in the home directory.
  - **Codex,** in `CODEX_HOME`, else `~/.codex`: `config.toml` and the `*.config.toml` beside it, `AGENTS.md`, `rules/`, `skills/` without `skills/.system/`, `prompts/`, `version.json`, `.sandbox_migration` and `.personality_migration`.
  - **pi,** in `PI_CODING_AGENT_DIR`, else `~/.pi/agent`: `settings.json`, `models.json`, `mcp.json`, `keybindings.json`, `AGENTS.md`, `AGENTS.override.md`, `CLAUDE.md`, `SYSTEM.md`, `APPEND_SYSTEM.md`, and `extensions/`, `skills/`, `prompts/` and `themes/`. Never `auth.json` or `mcp-auth.json` (credentials), `trust.json` (trust decisions), `models-store.json`, the MCP cache, onboarding and log files, `npm/`, `bin/`, `tools/`, `tmp/` or `sessions/` (capability report, 2026-11-16).
  - **A secret inside a configuration file is copied with it.** A file on a list is configuration, and copied whole, even when it holds a secret: an `env` block in a settings file, an MCP server's `env` in `mcp.json`, or an API key for a custom provider in pi's `models.json`, which Michael's holds. A snapshot is a private copy beside the original and is treated as one (Michael, 2026-11-16).
  - **Never:** a credential or token file, a transcript, a session store, a history, a database or a cache. The skills a harness syncs or bundles itself (Claude's `skills/synced/`, Codex's `skills/.system/`) are the harness's to restore (Michael, 2026-11-15). A file over 16 MB in an included tree is recorded as skipped.
- **Where the configuration is.** `CLAUDE_CONFIG_DIR`, `CODEX_HOME` and `HOME` are read from the operator's shell environment, as the start-up check of the harnesses resolves it.
- **The store.** `snapshots/` and each snapshot in it are `0700`.
  - **Objects.** Each content is kept once, in `objects/<2 hex>/<sha256>`, read-only (`0400`).
  - **A snapshot** is a folder, `<UTC time>-<reason>`, holding `manifest.json` and `<harness>/<label>/<path>`. Each file is a hard link to its object, so a file unchanged since an earlier snapshot costs a directory entry, not its size. If the store cannot hard link, it copies.
  - **The manifest** records names, digests, sizes, modes and link targets, the roots and include lists, the reason, and the harness versions. It holds no content.
  - **Links.** A symbolic link is recorded and recreated as a link, with its target, and never followed, in or out of the configuration directory. A configuration directory that is itself a link is read where it points.
  - **Writing.** A snapshot is written beside the store and renamed into place, so `mega snapshots` never reads half of one.
- **When.** Always in the background, never holding up start-up or a launch:
  - **after the start-up check of the harnesses,** when the configuration differs from the newest snapshot (`start-up`);
  - **when a harness reports a version no snapshot has recorded** (`version`), at start-up or in the version read before a launch. It is taken even if nothing differs, which costs only directory entries. A harness seen for the first time is not a version change.
  - **never** when the configuration holds nothing on the include lists, and never after the service has begun to close: `Close` waits for a snapshot under way, so nothing is written in the data directory once it is let go.
- **How many.** Ordinary and version snapshots are bounded apart: `snapshots.keep`, 10 by default, and `snapshots.keep_at_version`, 20 by default. Claude Code updates every day or two, so most starts meet a new version, and those are kept longer. The newest is never removed, and an object no snapshot links to any more is removed with the last one. `snapshots.keep: 0` takes none, as the version probe's scratch megas do.
- **What it costs.** `~/.claude.json` changes at nearly every start (about 340 KB on Michael's machine), so most starts store one snapshot whose only new content is that file. A month of daily starts, with a Claude update every other day, keeps 24 snapshots in about 10 MB.
- **What it says.** A snapshot taken logs its name, reason, file count and the new bytes, never a file's name or content. `mega version`, `GET /api/version` (`snapshots: {dir, count, newest: {name, taken, reason}}`) and the version panel, which reads it again as it opens, say when the newest was taken and where the snapshots are.
- **Restoring is the operator's.**
  - **`mega snapshots`** lists each snapshot's name, time, reason, file count and harness versions.
  - **`mega snapshots diff NAME`** (or `newest`) compares a snapshot with the live configuration where it was taken, under the include lists it was taken with. It names each file that changed, is only in the snapshot, or is only live. For each the snapshot holds, it prints the command that would put it back: `install -D -m <mode> <copy> <live path>`, or `ln -sfn` for a link.
  - **It writes nothing,** into a harness's configuration or anywhere else.

## Conversations and runtimes

A conversation is bound to one native session. Launching starts a runtime for a new session, records the session id, and sends the opening prompt. A conversation holds exactly one native session for its whole life. Only `StartConversation` starts a new session, once, when it creates the conversation, and the id that launch returns is saved in the registry, which alone binds a conversation to its session. A `started` event in the log still carries the id, as history, and nothing reads it back. If the registry write fails, the runtime is stopped with an `error`, and the service shows no session it could not confirm. A first launch that fails, whatever failed (mega's own check before the harness starts, the harness itself, or the write that saves the session), records one `error`, and nothing gives the conversation a session afterwards. At the next start the registry on disk alone decides: a write that failed only after reaching the disk, as when its directory could not be synced, leaves the session bound there, and it is resumed like any other. A conversation with no session in the registry is refused a prompt or Start as `conflict`, across restarts, with a message to remove the conversation and, if the harness made a session, adopt it under "Adopt a session" if discovery lists it. That includes a session the log shows started but the registry does not hold, as after a power loss between the launch and the write: it is not resumed, and can be adopted when discovery lists it (Michael's rulings 4 and 7, 2026-11-23). A failed launch of a conversation that has a session records `error` too, and the conversation can be launched again on the same session. Every later runtime resumes exactly that id; nothing picks a session by recency, forks one, or starts a fresh one in its place. A runtime that reports a different session than the one it was launched for is recorded as an error and stopped. Every report is checked, not only the first: Claude carries a session id on each SDK message and hook, and the adapter checks each one against the session it holds, so a session that changes partway through a runtime's life is caught at its first frame, and that frame and everything after it are dropped. Its requests honour the same latch. Codex's frames are checked the same way, each by the thread it names: until Codex confirms the thread, only the thread a resume asked for is taken, and a frame of another thread is never mapped, before the identity check or after it. pi holds every frame until `get_state` has confirmed the session. On a fresh launch, what the runtime reports is delivered as it arrives, and the session is recorded from the ID the runtime returns once the launch returns. A start report during a fresh launch is not compared with that ID, since no adapter can report another session then: Codex and pi report the one ID they return, and Claude names no session before the opening prompt, which is sent only after the launch has returned and the session is bound. From then on every report is checked against the bound session, as on a resume (Michael's call, 2026-11-23). From the moment it reports the other session, nothing more it reports is recorded or offered: no output, no streamed text, no request, no background job or MCP list, since all of it belongs to a session the conversation does not hold. Only its exit, and the settling of what it had raised, still count.

Runtimes are long-lived: a runtime starts at launch, with the first prompt after an adoption, a release, a clean restart or a resume, or when the operator starts it with no prompt (Start, below), and stays up between turns until the operator releases it, the service stops, or the harness exits by itself. There is no per-turn mode and no suspension operation; restarting the service is the way to put everything down. The service never looks for or kills processes it did not start, or ones it lost track of: an orphaned runtime after an unclean restart, or a sandboxed command that outlived Codex, is reported, not stopped.

The registry records each conversation's `runtime` as the service last confirmed it: `none`, `running` (written before the process starts), or `unsupervised`. The service also reports transient states: `starting` until the runtime reports the session it holds and `stopping`.

Runtime transitions are shown and announced once their `runtime` event is recorded. Resume acknowledges supervision loss with a registry write. A launch that failed shows no runtime once its `error` event is recorded. Operations are guarded internally, apart from what is displayed, so a runtime is asked to stop at most once, however many releases or shutdowns ask.

- **Prompt** records the text as a `user` event with a service-minted uuid and passes that uuid to the harness, which records it as the message's identity (observed with Agent SDK 0.3.318), so a live echo can be suppressed. It opens no turn: the turn opens when the harness starts it (**Turns**, below). One turn at a time: a prompt while a turn is in flight is refused. A prompt the harness answers with a refusal (`harness.ErrPromptRefused`: a JSON-RPC error reply to Codex's `turn/start`, or pi answering `success: false`) starts no turn, and neither does one the harness handles itself (`harness.Handled`: pi running an extension command). For each the service records a turn end after the prompt, an error saying why for a refusal and a success saying it was handled, so the prompt does not run into the next turn on the page. Each row is a record only and closes nothing in memory, whatever turn the harness has open, and the next prompt is taken. A handled prompt is no failure: the command succeeds and the page shows no error. These two rows are the only turn ends mega writes; the only turn end that reaches the service from an adapter is the harness's own. A prompt whose fate is unknown, such as one that timed out, records nothing more. A prompt to a conversation with no runtime launches the runtime on the exact bound session.
- **Turns.** A turn is what the harness says it is. It opens when the adapter reports the harness's own start (`Sink.TurnStarted`): Claude's `system/init`, sent at the start of every turn, one Claude begins by itself included; Codex naming the turn, by `turn/started` or by its reply to `turn/start`, whichever comes first; pi's `agent_start`. That report is a signal in memory and nothing is recorded for it. A start while a turn is open changes nothing, as pi's `agent_start` for each retry inside one run. The turn closes on the harness's recorded turn end, or at the runtime's exit. No message opens a turn: a user message outside one, as Claude answers a model switch on an idle runtime with, and output reported after its turn ended, such as a Codex background command finishing, are recorded and open nothing.
  - **Between the prompt and the start** the prompt shows and the conversation is idle: the activity line, the shutdown gate and Interrupt all see no turn, and a second prompt is taken. A harness that never starts the turn leaves the prompt and no activity. If two prompts are sent inside that moment and the harness refuses the second while the first turn runs, the refusal's row ends that turn on the page as a turn's end would, while the turn stays open in memory until its own end. A prompt pi handles inside that moment records its row and leaves the turn pi started open.
  - **A runtime's exit ends a turn in memory and not in the log.** No turn end is recorded for it, so the page and the paging join that turn to the next and count the next turn's time from the old prompt.
- **Start** starts a runtime for a conversation that has none, sending nothing: the operator's gesture to have it running, with its MCP servers connected and its settings taking changes at once. It takes a conversation with no runtime that is not unsupervised and has a known session.
  - It runs exactly as a prompt to a stopped conversation does, without the prompt. It records `starting` and launches through the same path, resuming the session by its exact id, and records `started` once the runtime reports the session it holds. Nothing else differs: the launch passes the stored mode, model and effort, and the session binding rules are unchanged.
  - A release asked for before the runtime reports keeps the `stopping` it recorded when the report arrives late; only the exit settles it.
  - It is refused as `conflict` while the conversation is unsupervised (Resume settles that first), starting, stopping or already running. A conversation with no session is refused, as a prompt is, since only its creation starts one.
  - The adapter is told no prompt follows (`harness.Spec.Idle`). Codex needs nothing more: `thread/resume` reports the model, effort, policy and version with no turn, and holds the thread idle. Claude sends no `system/init` until a turn starts, so the shim is run with `--idle` and reports what Claude answers without a turn. That is the version from the initialize reply and the model from `getContextUsage`'s summary. The adapter shows the runtime started from that report. The report carries no session, since Claude has reported none. From the launch on, before or after that report, the first message Claude sends with a `session_id` (a hook frame, a `system/status`, or the first turn's `system/init`) is checked against the session resumed. A different one is reported as the runtime's session, so the service records the error and stops it, as it does for a first `system/init` that disagrees.
  - Claude reports no permission mode without a turn. The started facts therefore carry the mode the launch passed, which is always the conversation's requested mode. The first turn's `system/init` reports Claude's mode; one that differs, like a confirmed switch to another mode, is a `mode_changed` event, and one that names the mode passed records nothing. Logs from before every launch passed a mode may hold a first-turn report marked `mode_confirmed`; the history draws no row for it. A prompted launch is unchanged: the first `system/init` is still the `started` fact.
  - A started conversation with no turn is idle with a runtime. Its mark stays idle, no turn is in flight, and nothing is unread. The next prompt goes to the running runtime on the same session. Nothing starts a runtime without a prompt on its own: not opening or selecting a conversation, and not a service start.
  - An idle runtime costs memory, measured in the capability report's 2026-11-10 follow-up as proportional set size (PSS). Claude's CLI takes about 145 to 180 MB, plus about 50 MB for the shim's Node process. A Codex app-server takes about 165 to 215 MB. Each also runs the operator's MCP servers, about 5 to 30 MB apiece.
- **Requests** (a permission or an `AskUserQuestion`) get a service-minted id, unique across every runtime the conversation has had, and join the conversation's pending set, which lives only in memory. The harness's own request id stays inside the adapter, so a stale card can never match a newer request that reused a native number (Codex's restart at 0 for every app-server). A request ends `answered`, `aborted` (the harness settled it, or its runtime exited), `lost` (the service restarted while it was pending), or `unconfirmed` (a Codex answer sent into its turn whose reply never came, under the Codex adapter). A runtime can raise a request before its launch has returned, as pi does for an extension's dialog at session start. An answer that arrives then, with no runtime yet to carry it, is refused as `conflict`, "the runtime is starting", before anything is reserved, and the request stays pending for an answer once the launch has returned, as the model and mode controls are refused in that window. An answer reserves the request while it is delivered: the request stays in the pending set every reader sees, and a second answer meanwhile, from any browser, is refused as `conflict`, "already being answered". The request leaves the pending set only once its resolution is recorded. Every move out of the pending set goes through one step, `settleLocked`, for an answer, for the harness's own settlement, and for the aborts every end of a runtime makes (`retireRequestsLocked`: its exit, and a launch that failed after it raised a request): record the resolution, then take the request out. Each adapter lets go of a request and writes its answer in one step under its lock, so a settlement the harness reported and the adapter read first is never lost to an answer written after it: Claude's shim then rejects the answer, and in Codex and pi the request is already settled, so the answer is `not_pending`. An answer the harness refuses without settling the request (`harness.ErrInvalidAnswer`, such as a choice pi did not offer) records nothing: it is refused as `invalid`, and the request stays answerable. Once settled, a later answer gets `not_pending`, as does an answer the harness settled first, for example on an interrupt; a resolution the harness or an exit recorded while the answer was in flight is never recorded twice.
  - **After a stop begins,** an interrupt or a release, an answer that would let work go on is refused as `conflict`, the request still pending: Allow, Allow for the session, and a chosen or written answer to a question, pi's dialogs among them. Every stop also fences the runtime first (`Runtime.Stopping`), and Release does so before it returns. The fence latches in each adapter: from then on no answer that would let work go on (`harness.CarriesWork`, anything but Deny or Dismiss) is delivered, even one the service accepted before the stop, so no tool runs and no Codex answer is steered once Release has returned. The service's own refusal and the adapters' fence share that one test. The message says the turn is stopping and that Deny or Dismiss can still be pressed, since those only settle the request toward the stop: pi holds an interrupt until its dialog is dismissed. An interrupt counts as under way while a turn, or a pending request, is outstanding: until the turn ends, no request is pending with no turn running (as when a Codex answer whose steer awaited its reply after its turn ended settles), or the runtime exits; the workspace read carries it as `interrupting`. A denial without a reason is sent as `the operator denied this in mega`.
- **Interrupt** stops the active turn; the harness aborts any pending request.
- **What a conversation requests.** Every conversation holds a concrete request: a model, an effort wherever the model takes one, and for Claude a permission mode. Every launch passes all three, and for Codex every turn passes the model and effort. There is no unset state, and the harness's own settings never choose them at launch.
  - **Copied once.** A new conversation's request is copied once, at creation, from the harness's current settings, for whatever the operator left unchosen in the launch dialog; an adopted conversation's is copied at adoption. Later changes to the settings reach only conversations created after them. The copy (`service.copyFor`) takes:
    - the model: the settings' when the model list holds it as a row's id; else the list's default row (Claude's `default`, Codex's `isDefault` model); else the list's first. A full id the list holds only as an alias's resolved model (`claude-opus-5-5`), or an alias the list lacks, takes the default row. With no list to be had, a settings model of the right form is copied as it is.
    - the effort: the settings' when the model offers it; else the model's default level, which Codex's list names and Claude's never does; none for a model that takes none (Claude's Haiku 4.5). A Claude model that takes levels, with settings that name no `effortLevel` it offers, has nothing to copy: any level would be a guess at Claude's own. The launch dialog then preselects no effort and Launch waits for one, and the service refuses a launch without one as `invalid` ("the Claude settings name no effort level, so choose one for this conversation"). An adopted conversation in that case is adopted without an effort, and its first launch is refused the same way until one is chosen on the control bar (Michael's call, 2026-11-13).
    - the mode (Claude): the settings' `permissions.defaultMode` when mega offers it; else `default`. A mode mega never passes (`bypassPermissions`, `dontAsk`) becomes `default`: never a bypass mode (`permissions-never-weakened`).

    For Claude the settings are the first `model`, `effortLevel` and `permissions.defaultMode` in the settings layers below, read, never written. Per-model `modelSettings` overrides and environment variables are not read. For Codex they are its own effective config for the checkout through `config/read`, which can differ from the catalog's `isDefault` model.
  - **The one-time fill.** Conversations recorded before every one held a concrete request may lack part of it. Each is filled once, as a recorded change: a `choice_filled` runtime event, written before the registry write, so a fill interrupted between the two is applied again from its event at the next start, and recorded no second time.
    - At start-up, before the service answers, each conversation lacking a model, a Claude mode or a Codex effort takes what its log last reported, from the `started`, `model_changed` and `mode_changed` events in order ("filled in from what the harness last reported"). A Claude model so filled is the full id Claude reported, which the list's lookups resolve to its alias's row. A reported mode mega never passes becomes `default`. It reads only the logs, and a second start finds nothing to fill and writes nothing.
    - What the log cannot give is filled at the conversation's next launch or Start, from the settings, by the same copy, before anything is passed ("filled in from the harness's settings"). That is Claude's effort, which Claude never reports, and any field of a conversation that never reported. A Claude conversation whose settings name no effort is refused there, as a new one would be, after the rest is filled.
    - The history draws the fill as one row: "Request filled in from …", with what was filled.
  - **What each turn ran with.** A turn's `turn_end` carries `turn` `{asked, ran, differs}`. `asked` is the conversation's request when the harness started the turn, so a Codex model or effort changed between the prompt and Codex naming its turn shows as a mismatch, since the prompt went with the old one. `ran` is what the harness had reported when the first output arrived while the turn was open: the model and, for Codex, the effort from its reports, and for Claude the mode; Claude never reports effort, so its effort is the one sent. A mode switched later in the turn keeps its own "Permission mode X" row. `differs` names the fields where the two are not the same, comparing models through the model list, so an alias and the full id it resolves to are one model; with no list, a model is never called different. The list is fetched in the background once a runtime starts. A turn with no report carries no `turn`, and turns recorded before this carry none. The runtime events alone could not say this: a conversation opens on its last ten turns, requests were never logged, and Claude's effort is reported nowhere. While a turn is in flight the conversation's read carries the same as `turn_asked`, `turn_ran` and `turn_differs`.
- **Permission mode** (Claude only) is the conversation's requested mode: `default`, `auto` (a classifier approves routine calls), `acceptEdits` or `plan`. The bypass modes, `bypassPermissions` and `dontAsk`, are never offered, and the service refuses them. It is copied at creation, or chosen at launch, and every later launch passes it with `--permission-mode`, so it survives a release, a resume and a restart. A terminal visit never changes it. Claude's own fallback when no mode is given may become `auto` in a later version, which is one reason a mode is always passed. The copy reads the settings the way Claude Code 2.1.318 resolves them for a session in the checkout (observed; capability report, 2026-11-09). Highest precedence first:
    - managed settings (`/etc/claude-code/managed-settings.json`);
    - `.claude/settings.local.json` at the git repository's root, then the checkout's own;
    - the checkout's `.claude/settings.json` (never the repository root's, which Claude does not read for a session below the root);
    - the user's `settings.json` (`$CLAUDE_CONFIG_DIR`, else `~/.claude`).

    The local file stays in the checkout instead of the root when the checkout is outside a repository or is a worktree (Claude would use the main checkout's root, which mega does not resolve), when the root is the home directory, or when the root, its `.git` or its `.claude` belongs to another user. `auto` and `bypassPermissions` named in a project or local file are skipped, as Claude ignores them there. The lookup then continues to the lower layers. That is an assumption, not an observation: what Claude does when a project file names `auto` and the user's settings name another mode was not probed. An unreadable layer is skipped with a warning. Any difference from Claude's own lookup can only fail toward the manual mode.
  - The operator can set the mode for any Claude conversation that is not unsupervised. One that is starting or stopping is refused until it settles. Every change is the operator's gesture, recorded as a `mode_requested` event before the registry write (`requestModeLocked`), with or without a runtime, so the registry never holds a request the log does not (`permissions-never-weakened`; Michael's calls on the review, 2026-11-13).
    - The event never raises attention, and nothing reads it as what runs.
    - A crash between the two, or a registry write that fails and so ends mega, leaves the request as the log's last event, since `s.mu` is held across both. The next start applies it from there (`settleModeRequestLocked`, in `recover`), recording nothing more.
    - The history draws a request as "Permission mode X requested: …", unless the next mode event after it is Claude's report of the same mode. A confirmed switch so shows only Claude's "Permission mode X" row.
  - With no runtime, the request is all there is to change: the event, one registry write and no harness call, with the outcome `stored` ("Permission mode X requested: the next launch passes it"). There is no live mode to report, and the next launch's `system/init` is the report.
  - While the runtime runs, the request is intent: it is recorded and written on the conversation first, as the mode the next launch passes ("asked of Claude"), and then the harness is asked. The reply carries the harness's answer, and the service records no mode change of its own:
    - confirmed: Claude has switched, and the adapter has already reported it;
    - refused: the request goes back to its previous value, recorded the same way ("Claude refused X, so the request goes back");
    - unconfirmed: Claude did not answer within 30 seconds; the request stands, and the live mode is whatever Claude last reported, which a turn's line shows where it differs.

    One switch runs at a time. The new mode applies from the next tool call, even within the turn in flight. A pending request stays pending and answerable; nothing in a switch touches the pending set.
  - The live mode has exactly one writer: what the adapter reports, in the order Claude reported it. That covers a confirmed switch (reported before the switch call returns), a confirmation that arrives after the timeout, and a different mode in the `system/init` that Claude re-sends at the start of every turn, such as plan mode being left. Each is a `mode_changed` runtime event, recorded through the same transition as every other state change, and shown only once recorded. None of them changes the request.
  - In auto mode, the requests that still arrive are the residue: calls that a checkout `ask` rule holds back, or that the classifier did not approve on its own. Each request's payload carries the mode it was raised in.
- **Model and effort** are the conversation's requested model and effort, for either harness, recorded beside the permission mode and passed on every launch, so they survive a release, a resume and a restart. The model lists come from the harness and are cached per harness for the service's life, with the version they came from; asking for them starts no conversation and costs no turn (capability report, 2026-11-10). A launch or a change is checked against the cached list when there is one: a model the harness does not offer, or an effort the chosen model does not take, is refused as `invalid`. A full id the list holds only as an alias's resolved model is checked against that alias's row. The models read (`GET …/models`) also says what a new conversation would copy there, read afresh on every ask.
  - A model is always required, and an effort for a model that takes one; a change without them is refused as `invalid`. With no runtime, a change is stored and nothing else, with the outcome `stored`.
  - While the runtime runs, the request is intent, written first as it is for the permission mode. Claude switches at once through the SDK (`setModel`, then `applyFlagSettings({effortLevel})`, each sent only if it differs) and the outcome is `confirmed`, `refused` (the request goes back) or `unconfirmed` (no answer within 30 seconds; the request stands). If Claude accepts the model and then refuses the effort, the outcome is `refused`: the new model stays requested, the effort reverts to the last accepted one, and the live model is what Claude reports. Codex takes a model and an effort per turn, so the change replaces the request for the next `turn/start` and nothing is sent now, with the outcome `next_prompt`. One change runs at a time, sharing the guard with the permission mode.
  - The live model has one writer: the harness's report. Claude reports the resolved id (`claude-sonnet-5-5` for `sonnet`) in the `system/init` it sends at every turn start; the first is the `started` fact, and a later one with another model is a `model_changed` event. Codex reports the model and effort in the `thread/start` or `thread/resume` response, and both again in `thread/settings/updated` when a turn's override takes effect, which is a `model_changed` event. Claude never reports effort on the stream, so its effort is only ever what was requested.
  - A Codex override persists in the thread, across later turns and `thread/resume` (capability report, 2026-11-10), which is one reason every turn passes the request.
- **Release** stops the runtime and means nothing more. If a turn or a request is outstanding it interrupts first, then closes input, and the conversation shows `stopping` until the process is seen to exit, when it records `none`. Claude Code 2.1.318 exits with status 1 when input closes after an interrupted turn; a requested release with no turn in flight is still recorded as `stopped`, with the status in the text. An exit nobody asked for, or one in the middle of a turn, is recorded as `error`. A release that ends a runtime in the middle of a turn, as with a pi dialog pending, reads as any exit in the middle of a turn: the turn has no recorded end, and nothing separates it from the next turn for paging and timing. The next prompt or Start resumes the same session. A `gap` flag on a stop in a log an earlier build wrote is ignored, and the row shows as any stop does.
- **Resume** acknowledges lost supervision for any Unsupervised conversation, including one whose session id never reached the registry. It clears Unsupervised in the registry. It starts no runtime, reads nothing from the session, and leaves the Unsupervised row in the timeline. Start or a later prompt launches the exact bound session. When the id is unknown, the conversation can be removed and **Adopt a session** is the route to recover the native session.
- **Shutdown** (SIGINT or SIGTERM) releases every runtime the same way and waits up to 30 seconds for each to exit. Each that exits records `none`; any still running stays `running`. A launch already under way when the shutdown begins is waited for too: the last check before the harness starts refuses it, recorded as a failed launch, or a harness it started is stopped as its launch returns, and the shutdown waits for that one to exit within the same bound. Once the service has closed, nothing more is written to the registry: a write then is refused as `unavailable`, and no settling of a stale runtime begins, so a late exit cannot rewrite what the shutdown recorded. Every read is refused as `unavailable` too, in the moment before the HTTP server stops (below).
- **Shutdown when idle** is a gate for finding a quiet window, for example to update the service. The operator arms it, and the service holds the armed flag and when it was armed in memory only. It is never stored, because the restart it announces is what ends it. Arming and cancelling are announced through `workspace_changed`; arming twice or cancelling an unarmed gate changes nothing.
  - **While armed, no new work starts.** A prompt (to a running or a stopped conversation), a launch, an adoption and a Start are refused with the code `shutdown_pending` (409) and a message naming the pending shutdown. Everything that lets work finish is unaffected: answering a pending request, Interrupt, Release, Resume, mode and model changes, and every read. Cancel lifts the gate at once.
  - **Idle is computed, never stored**, from each conversation as the service shows it: no turn in flight, no pending request, no background job, and nothing starting, in any conversation. Background jobs count because a release waits for them and Claude takes one more turn when one finishes. A launch still under way counts so that the stop never races one. That is judged from the service's own guard on the operation, not only the displayed state, since a runtime may report started before its launch returns. A warm runtime that is merely idle does not count; the shutdown releases it. Unsupervised conversations do not count either: the gate cannot see their execution, and the shutdown leaves them as they were.
  - **The gate never acts to reach idle.** It answers, approves, denies, interrupts and releases nothing. It only waits.
  - **Shut down** is refused as `conflict` unless the gate is armed and nothing is in the way at that moment. Accepted, it marks the service shutting down at once, so nothing new starts and Cancel is refused (`unavailable`) from then on. It then signals the process, which runs the one shutdown path in `cmd/mega/serve.go` that SIGINT and SIGTERM use: every runtime released and waited for, each conversation recorded with no runtime, subscriptions closed, the listener shut, exit status 0. A forced stop remains Ctrl+C in the terminal.
- **Service start** settles the previous run without replaying anything. Every unresolved request gets a `request_resolved` event with outcome `lost`. A conversation still recorded as `running` becomes Unsupervised and requires Resume. That includes one whose exit was logged but whose registry write failed, after a release as after any other stop: the logged `stopped` or `error` row does not count as a settled stop. It records one `unsupervised` row, unless the log already holds one since that runtime’s start, so a further restart adds no second row. An orderly shutdown and a browser disconnect record none.

**Remove** takes one conversation out of the workspace. It is refused as `conflict` while the conversation has a runtime in any state: starting, running, stopping, or unsupervised. An unsupervised conversation is resumed first, because its orphaned runtime may still be working. Removal deletes mega's own history and reading state for the conversation and nothing else: the checkout and the native session stay, and discovery offers the session for adoption again. The order is fixed. The registry write comes first and memory follows it once confirmed; the conversation's log directory (`conversations/<id>/`) is deleted only after the registry no longer names it, and its parent is then synced. A crash between the two leaves an orphan directory, never a registered conversation without its log. A directory that cannot be deleted is logged at error level and left behind the same way, and the removal stands.

Removing a project applies the same rules to every conversation in it. It is refused as `conflict`, naming the conversation, while any of them has a runtime in any of those states. The project and its conversations leave the registry in one confirmed write, and only then is each conversation's log directory deleted, in the same order and with the same failure handling as a single removal. The checkout and the native sessions stay.

## Attention

Attention is computed from confirmed facts every time the workspace is read, and never stored. In order:

- `request` when a question or approval is pending;
- `unsupervised` when the service restarted without seeing the runtime exit, an uncertain state never shown as running or idle;
- `running` while a turn is in flight, from the harness's start of it to its recorded end or the runtime's exit; a prompt the harness has not yet started is not running;
- `error` when the last runtime ended badly (an error, an exit during a turn, or a failed launch), until a runtime starts or stops cleanly. Failed imports recorded by older versions stay in the timeline and leave runtime error attention unchanged.
- `unread` when the newest recorded agent output is past `read_seq`;
- `idle` otherwise.

Every conversation read has an attention, even with no live state. An orderly stop closes each conversation's log and lets go of its live state while the HTTP server still answers the page that asked for it. Nothing is kept to answer a read from in that moment, so every read that passes its own input checks is refused as `unavailable`: the workspace, the version, history, an invocation, MCP servers, folders, paths, models, discovery, a look at a session and an approved version. A history or invocation read already reading its log when the service closes can fail as `internal` instead. A read during the release, before the close, is answered as ever. A command's reply is a read of the conversation too, so a command whose write landed just before the close can be answered `unavailable` although it took effect: a rename, say, or a new conversation, which the next start shows. No log is opened again either, so a read acknowledgment is refused the same way, though one naming a conversation the registry no longer holds is `not_found`.

The service follows the newest `assistant`, `tool_use` or `tool_result` event in memory, applying the same rule when it appends an event and when it opens a log. Output from adoption counts too. Prompts, native bookkeeping, runtime events and request bookkeeping leave it alone. The workspace gets an update when a turn ends or output lands outside a turn. During a turn, output alone sends no workspace update once the turn's settings are known. After a loss of supervision, Resume can reveal recorded unread output from an unfinished turn.

`last_seq` is read from the event log, never stored, so recording an event never rewrites the registry. `read_seq` is the reading position. Reading moves it forward to at most the last event, never back. It acknowledges what was read and nothing more: a pending request stays pending, and `request`, until it is answered. The page posts it only for what is on screen (the rest of the page, below): never while the view is scrolled up from the newest output, behind a dialog, or in a tab that is not visible. Only a read moves `read_seq`, and memory follows the confirmed registry write.

A project's mark in the UI ranks its conversations' attention in a different order: request, unsupervised, error, unread, running, idle. A conversation is `running` ahead of `error` and `unread` because a turn in flight is its current fact. A project ranks what needs the operator above what is merely busy, because its mark answers "does this project need me, and if not, is it busy". The page derives it, and the service computes nothing new for it.

The needs-you order lists every conversation in `request` or `unread`, requests first, then each group oldest first by the time of the fact that put it there: the oldest pending request, or the newest recorded agent output.

## Discovery and adoption

Discovery lists the native sessions stored for a project's checkout that no conversation holds yet: Claude through the shim's `list` (the SDK's `listSessions`, asked with no limit), Codex through `thread/list` on a short-lived app-server, read page by page to the end, and pi by scanning its session folder for the checkout, since its protocol lists none. Mega cuts none of these lists, so no session a harness lists is out of adoption's reach because of where it falls in the list. Codex lists only threads from interactive sources that are not archived, its defaults, so a thread `codex exec` made, or one archived in Codex, is not listed and cannot be adopted. Codex's list is read under discovery's one-minute deadline, so one that never ends fails and is never returned short. pi's scan is not bounded by it. Each session's `preview` is the harness's own (usually the first prompt) and is passed on whole. It never chooses one. It also says how many sessions it left out because a conversation already holds them, `held`. Adoption reads one snapshot of the exact chosen session in the approved project environment. It rechecks the project and the session claim, then writes the complete log before publishing the registry binding. The snapshot keeps the native origin and message ids, so a live replay of one of those ids is suppressed. Its agent output is unread until acknowledged. Adopting from the page opens the conversation at its newest output. If the read or snapshot write fails, the session stays available to adopt. If a registry save reports an error after rename, the complete log stays on disk. Close any terminal that holds the session first.

**Work done outside mega.** Mega neither marks nor shows work done on a session outside it, and does not fetch work a harness finished while mega was down. A session's own history comes into mega one way, by adoption: remove the conversation and adopt its session again, if discovery lists it. What only mega recorded does not come back: its runtime and request rows, what each turn ran with, the name and the label. An Unsupervised row separates turns for paging and timing.

**The look before adopting.** Picking a session in the adopt dialog reads how it began and how it left off: its first prompt, its last prompt where it has more than one, and the end of its last reply, with how many prompts it holds (`GET /api/projects/{id}/look`, `Service.Look`).
- **Read by its own adapter.** Each adapter reads its own native session, through the same read an import makes (`harness.Looker`): Claude Code's shim `messages`, Codex's `thread/read` on a short-lived app-server, pi's session file. `harness.LookOf` picks the parts from the events the adapter mapped, so the protocol stays in the adapters.
- **It changes nothing.** Nothing is imported, no conversation or registry entry is made, no attention moves, and no runtime starts.
- **It is a private transcript.** What it returns is bounded: the first prompt to 4,000 bytes from its start, the last to 2,000, the last reply to its last 2,000, each cut at a character, `cut` naming those cut short. It is shown only in the dialog that asked, and never logged; a failure's message names the session, never its text. The checks read only the fakes' sessions.
- **What it costs.** It is read when a row is picked, never for every row, and it reads the whole session: on a synthetic session of 2,000 turns, about 0.33 s for Claude Code (5.8 MB; 0.2 s of it the shim's read), 0.22 to 0.27 s for Codex (5.5 MB, an app-server started for it), and about 0.1 s for pi (4.5 MB). `probes/look/run.sh` measures it again.

## The Codex adapter

Each runtime is a private `codex app-server` child per conversation, driven over stdio JSON-RPC in its own process group, so its lifecycle matches Claude's (a runtime is a child process) and a crash stays local. It starts with `initialize` (client `mega`, `experimentalApi` on) and `initialized`, then `thread/start {cwd, model}` or `thread/resume {threadId, cwd, model}`, with the conversation's requested model; these calls take no effort (0.166.0 schema). The Go types are written by hand for the subset used, from the 0.166.0 schema checked in under `internal/harness/codex/schema/` with the command that generates it. A turn opens when Codex names it, by `turn/started` or by its reply to `turn/start`, whichever comes first. The adapter reports the start then, once per turn, and never for a turn whose `turn/completed` it has already read; it holds its lock across the report, so the turn's end cannot reach the service first. The turn closes at `turn/completed`, whose status becomes the `turn_end` status. It never sends an approval policy, a sandbox, or a config override, so the operator's codex configuration decides them. That includes per-project trust: a trusted checkout gets a workspace-write sandbox, where only a command reaching outside the checkout asks for approval. The runtime reports `started` once the thread starts, with the model and effort, the CLI version, the approval policy and sandbox, and the instruction sources.

- Every `turn/start`, which only a prompt sends, carries the requested `model` and `effort`. Codex treats each as an override for that turn and the ones after it, so sending them every turn keeps the request true across resumes. The config is never read to fill a launch or a turn. A change while running replaces the request and is sent with the next `turn/start`. `thread/settings/updated` is Codex's report of the model and effort it now runs; one that differs from the last report becomes a `model_changed` event.
- Discovery reads `thread/list {cwd, limit: 100, sortKey: updated_at}` on a short-lived app-server, following `nextCursor` to the end. It sends no `sourceKinds` and no `archived`, so Codex lists interactive threads that are not archived, its defaults. Codex returns at most 100 a page. Under its default sort, `created_at`, the cursor is a whole second, and a page that ends inside a second skips the rest of it. Under `updated_at` the fixture's list was read whole at every page size tried, which is observed, not promised (capability report, 2026-11-26). A thread already listed is not listed again. A thread updated while the list is read can move between pages and be missed, and reopening the dialog reads the list again.
- The model list comes from `model/list` on a short-lived app-server with no thread, hidden models left out, with the version from the `initialize` user agent. What a new conversation copies comes from `config/read {cwd}` the same way: `model` and `model_reasoning_effort`.

- A command whose `item/started` has no `item/completed` by its turn's `turn/completed` is background work: a terminal session Codex keeps (unified exec). The adapter reports such commands as the background list (`kind` `command`, the command without its `/bin/bash -lc` wrapper, first seen at `item/started`). When the command's `item/completed` arrives, after its turn, it leaves the list and is recorded as the usual tool call and result. They open no turn, since only Codex's start does, and a conversation with no turn in flight can show them as unread at once. So a background command that finishes, or fails, while the operator is away reads as unread, as a woken Claude turn's reply does. They keep the native identities a history import maps the same item to (the item id, and `id/result`), so a resume after a release records nothing twice. A command detached with `nohup … &` inside an ordinary call is invisible to Codex, so it is not on the list (capability report, 2026-11-10).
- The thread's MCP servers come from `mcpServerStatus/list` with the thread's id, every page read. The list is per thread, and without an id it gives only the user-level servers and no runtime status (capability report, 2026-11-12).
  - **When it lists.** Once the thread is loaded; again after `mcpServer/startupStatus/updated`, which Codex sends as each server starts, is ready or fails; and again at each `turn/started`, since a server that dies later is not announced. One list runs at a time, off the reader, and those wanted meanwhile become one more. Nothing is reported after the exit.
  - **What it reports.** Each server's `runtimeStatus` maps to mega's statuses: `connected` to connected; `notStarted` and `starting` to connecting; `authenticationRequired` to needs sign-in; `failed` and `cancelled` to failed; `disabled` to disabled. Another status is failed, naming it. With no runtime status, a server is needs sign-in if `authStatus` is `notLoggedIn`, failed if `toolsError` is set, and otherwise connecting. `toolsError` is the error.
  - **The tools.** A connected server's tools are each name with the first line of its description, or its title where there is none.
- Completed items map to events: a user message to `user` (its `clientId`, the service's prompt identity passed as `clientUserMessageId`, becomes its native identity, so the service can recognize its live echo); an agent message to `assistant`; a shell command, a file change or an MCP call to `tool_use` and `tool_result`; anything else to `native`. An item of a turn whose `turn/completed` Codex has already sent, in any status, is recorded and opens no turn. Its output follows the same unread rule as any other. Streaming agent text becomes deltas, except text for such a turn, which is dropped: its completed item records the whole message. Other notifications are transport chatter and are not recorded, except `error`.
- Command, file-change and permissions approvals become `permission` requests, mapped by the server's own request id inside the adapter. Allow answers `accept`, deny answers `decline`; a permissions request is granted exactly what it asked for, for the turn, or nothing. `serverRequest/resolved` aborts a request the server settled itself. Codex gives no acknowledgment of an answer, so an answer after that notice is refused as `not_pending`.
- An agent message carrying `questions[]` (the default-mode question, since `requestUserInput` is unavailable in 0.166.0) is also recorded as a `question` request while the turn that asked is running: only a question of the active turn raises a card, since only that turn can take its answer, and one naming any other turn is recorded as the message it is. Once an interrupt has marked the turn, no answer is steered into it. In the case the capability report observed, that turn does not end by itself: the model sleeps and waits, and the card is how the operator learns Codex is waiting. An answer goes into that turn with `turn/steer` while it is the active turn, and an answer never starts a turn. The check for a fenced stop and the sending of `turn/steer` are one step under the runtime's lock, which `Stopping` takes to fence and an interrupt takes to abort the turn's questions, so no steer is sent once the adapter has fenced a stop; the wait for Codex's reply holds no lock. The adapter settles a written steer itself, from Codex's reply, before the runtime's exit can be reported, so the exit's retirement never settles it another way: a reply is `answered`; a refusal, as when the turn has just ended, is `aborted`, and the answer `not_pending`; and no reply, by its one-minute deadline or before the app-server goes, is `unconfirmed`. A reply the connection has taken off the wire by the deadline is still the answer, never the deadline. That closes the card, and the answer is refused as `harness_failed` with "Codex did not confirm whether it received your answer", which the question's history row then says. Nothing is sent again, and nothing falls back to a turn. The turn ending, in any status, aborts the question, as do interrupt, release, as it fences, and the runtime's exit. A release's fence waits for any of these aborts still being reported, so `Release` never returns with an unanswered question listed. Its message stays in the conversation, and the reply box answers it like any other, with a prompt that starts the next turn. One that arrives once its turn has ended raises no request and is recorded as a message, opening no turn. The message counts toward unread when recorded. One that arrives in a turn the operator interrupted, or once the runtime is fenced for a stop, is never raised, since only an answer that lets work go on could settle it.
- `item/tool/requestUserInput`, which 0.166.0 does not send in default mode, is handled if it arrives: it becomes a `question` request answered by question id.
- `mcpServer/elicitation/request` is how Codex asks on behalf of an MCP server (capability report, 2026-11-09):
  - An elicitation whose `_meta.codex_approval_kind` is `mcp_tool_call` is a `permission` request:
    - The approval frame names the server but not the tool, so the tool is named `server/tool` from the `mcpToolCall` item started just before it. If no call is in flight, it comes from Codex's message ("…run tool \"echo\"?").
    - The payload carries the server, the tool, its description, its parameters as Codex displays them, and `allow_session` when Codex offers approval for the session.
    - Allow answers `{action: "accept"}`, and the tool runs.
    - Deny answers `{action: "decline"}`; Codex records the call as failed ("user rejected MCP tool call"). Its response has no field for a reason, so the operator's reason stays in mega's own record.
    - Where offered, "Allow this tool for the session" answers `{action: "accept", _meta: {persist: "session"}}`. Codex then does not ask again for that tool in that thread; another tool on the same server is still asked. No config file changes.
    - "Always" is never sent. Codex would write `approval_mode = "approve"` for the tool into the config file that defines the server, which mega never does on the operator's behalf.
    - Interrupting resolves a pending approval as it does every other approval: the turn ends `interrupted` and `serverRequest/resolved` follows, so the request is `aborted`, and a late answer gets `not_pending`.
  - A typed `form` elicitation of primitive fields (string, number, integer, boolean) and single-select enums is a `question` request. Its payload carries the server's message and the fields, required ones first. Each answer travels as text and is sent as typed `content`, leaving out an empty optional field.
  - Free-schema forms (`openai/form`, `openaiForm`), `url` and `openai/userVerification` modes, multi-select enums, forms with no fields, and frames the adapter cannot read are not answerable. They are recorded like any other unanswerable server request, naming the method, the MCP server, the mode and what was asked.
- A server request mega cannot put to the operator is not answered either way on their behalf. A `native` event says so, and the turn waits until the operator interrupts it.
- Interrupt is `turn/interrupt`. Release interrupts if needed, then closes stdin. At each interrupt and close the adapter notes every process running under the app-server, because the sandbox codex runs commands in starts its own session and so leaves the app-server's process group. After the exit it waits up to 10 seconds for those processes to go. If any are still running, the runtime is recorded as an `error` naming their pids, never as a clean stop. mega does not kill them. Where the processes cannot be listed, as with no `/proc` (macOS has none), or only in part, a process's entry there but unreadable, that is not taken to mean none survived (an entry that vanished mid-listing is a process that went, and is skipped; an unreadable one counts only where it could be one of the runtime's): the stop is recorded, without an error and without asking for attention, as "released, but whether processes the runtime started are still running could not be checked", with why (`harness.ErrUnchecked`). What could be read still counts: a survivor it can confirm is named, and the runtime recorded as an `error`, whatever else could not be read. The process gap on macOS is half closed by that: a real listing there still waits.

## The Claude shim

`shim/claude/shim.mjs` is a policy-free bridge between the service and `@anthropic-ai/claude-agent-sdk` 0.3.318, speaking one JSON object per line on stdio. The service runs `node shim.mjs run --cwd DIR (--session-id UUID | --resume UUID) --exec PATH [--permission-mode MODE] [--model MODEL] [--effort LEVEL] [--idle]`, with the executable from `claude.executable`. Without `--permission-mode`, `--model` or `--effort` the shim leaves that SDK option out, so Claude's own settings decide. `--idle` marks a launch with no prompt following (Start). Once Claude has answered initialize, the shim reports `ready` with Claude's version (`initializationResult()`) and the session's model (`getContextUsage({detail: 'summary'})`), each bounded at 30 seconds. Neither call runs a turn. The initialize answer is required: if it fails or times out, the shim reports an `error` frame and no `ready`. The adapter gives an idle launch one minute to report started. If neither `ready` nor a `system/init` has come by then, it keeps the reason and kills the shim's process group: the shim, Claude and anything Claude started. Nothing of the session was written, since Claude never answered. The exit is reported like any other: the service records `runtime error` ("claude did not answer within 1m0s of a start with no prompt") through the transition and leaves the conversation with no runtime, so it can be started again. A launch with a prompt coming has no such timeout. The model is a courtesy, empty if unanswered. `node shim.mjs models --cwd DIR --exec PATH` starts an idle session, asks `supportedModels()` and `initializationResult()`, prints `{version, models}` on one line, and ends input with no prompt sent; the session leaves no transcript and is not listed by discovery. The SDK's optional `claude-agent-sdk-linux-x64` package, which `npm ci` installs, is not used.

```text
shim to service
  {"type":"event","msg":<sdk message verbatim>}
  {"type":"request","id":<requestId>,"kind":"permission"|"question","tool":...,"input":{...},"toolUseId":...}
  {"type":"request_resolved","id":...,"outcome":"aborted"}
  {"type":"answer_accepted","id":...}      the answer reached the waiting request
  {"type":"answer_rejected","id":...}      nothing was waiting under that id
  {"type":"interrupted","response":{...}}
  {"type":"permission_mode_set","id":...,"mode":...}            the sdk switched
  {"type":"permission_mode_set","id":...,"mode":...,"error":...}  it did not
  {"type":"model_set","id":...,"model":...[,"error":...]}
  {"type":"effort_set","id":...,"effort":...[,"error":...]}
  {"type":"mcp_status","id":...,"servers":[...]}  mcpServerStatus(), verbatim
  {"type":"mcp_status","id":...,"error":...}
  {"type":"ready","version":...,"model":...}   --idle only: the session is up
  {"type":"error","message":...}
  {"type":"exit","code":N}
service to shim
  {"type":"prompt","uuid":<service-minted message uuid>,"text":...}
  {"type":"answer","id":...,"decision":"allow"|"deny","message":...}
  {"type":"answer","id":...,"answers":{"<question>":"<label>"}}
  {"type":"interrupt"}
  {"type":"set_permission_mode","id":...,"mode":...}
  {"type":"set_model","id":...,"model":...}
  {"type":"set_effort","id":...,"effort":...}
  {"type":"mcp_status","id":...}
  {"type":"close"}
```

The adapter asks for the session's MCP servers with `mcp_status`, which the shim relays to `mcpServerStatus()` and answers verbatim. Claude announces no change to its servers on the stream (capability report, 2026-11-12), so the adapter decides when to ask:
- once the runtime is up, at the idle launch's `ready` or the first `system/init`;
- every second while any server is still `pending`, up to sixty times in a row;
- whenever a turn's `system/init`, which lists each server with its status, disagrees with the last answer.

One ask is in flight at a time, and one wanted meanwhile follows the answer. An error answer leaves the last list standing. Claude's statuses map to mega's: `connected` to connected; `pending` to connecting; `needs-auth` to needs sign-in; `failed` to failed, with its `error`; `disabled` to disabled. Another status is failed, naming it. A connected server's tools come by name. Claude Code 2.1.318 gives no description, though the SDK's type has room for one, so none is shown; one that arrives would be. A server Claude still calls connected after its process died stays connected here, as Claude reports it.

Each `system/background_tasks_changed` (Claude sends one on every change, a whole snapshot down to an empty list) becomes the background list: `task_id`, `description` and `task_type` (`local_bash` for a backgrounded Bash call, `local_agent` for a backgrounded subagent). Each job keeps the time it was first seen across snapshots. The frame is still recorded as a `native` event, as are `task_started`, `task_updated` and `task_notification`. A job finishing after its turn wakes the agent for a turn nobody prompted (a fresh `system/init`, a reply, a `result`), which opens at its `system/init` like any other. Every `system/init` reports a turn's start, the first as well, which is also the runtime's `started` on a prompted launch. The adapter maps the first `system/init`, or an idle launch's `ready` if it comes first, to `runtime started`, `assistant` messages to `assistant` and `tool_use`, user tool results to `tool_result`, `result` to `turn_end` (`interrupted` if an interrupt was sent in that turn), streaming text to deltas, and everything else to `native`; a subagent's messages are `native` too. `AskUserQuestion` is a `question` request, and every other `canUseTool` a `permission` request. A user message with `is_meta` (or `isMeta`) is not the operator's. It is one Claude added itself, such as a subagent's hand-back, which the history reader synthesizes and the live stream never delivers. It maps to a `native` event named from its `origin` ("meta: hand-back from web-fetch"), or "user/meta" with none, keeping its identity, so an adoption snapshot shows it only under the native-events toggle. A user message with `isReplay` is not a prompt either: it is an echo on the live stream, such as the `<local-command-stdout>` Claude Code sends after a model switch, outside any turn (seen from 2.1.322 to 2.1.327). It maps to a `native` event, "user/replay", keeping its identity, so it never opens a turn that no `result` would end. A user message the SDK's history reader marks `isCompletedLocalCommand` is Claude's record of a local slash command or its output, never a prompt the model saw. The reader finds them by the transcript's own fields, after a local command caveat, before it drops those fields. It maps to a `native` event, "user/local-command", keeping its identity. The transcript holds such a record of the `/model` a switch runs, which is never sent live, and older builds could import it on Resume as a prompt from outside mega (capability report, 2026-11-19). The mark alone decides it: a prompt is a prompt whatever its text, even one made only of command tags. An assistant message whose `message.model` is `<synthetic>` was written by no model. It is either Claude's own bookkeeping or an API error, and only the transcript's top-level `isApiErrorMessage` and `error` tell them apart (capability report, 2026-11-15).
  - **Bookkeeping.** After an interrupted turn Claude writes "No response requested." to its transcript this way, when the next prompt reaches a run that resumed the session. The live stream never delivers it, so it is available when the adapter reads the stored session.
  - **An API error** arrives live with its `error`, such as `authentication_failed`.
  - **In stored history,** the SDK's history reader drops both fields. So the shim's `messages` reads the session's transcript as well: `<CLAUDE_CONFIG_DIR or ~/.claude>/projects/<the checkout's path, every other character a dash>/<session>.jsonl`, or any project folder holding that session. It passes each `<synthetic>` message's `isApiErrorMessage`, and `error` if any, on by uuid, from the transcript's entries of that session only. This reads Claude's own storage format, as the trust check reads `~/.claude.json`.
  - **The mapping.** A `<synthetic>` message whose `isApiErrorMessage` is present and false, with no `error`, is bookkeeping: a `native` event, "assistant/synthetic", keeping its identity, so it is never output and never attention. Anything else written by no model stays an `assistant` event: an API error, live or read back, and a message whose transcript could not be read. Unknown is shown, never hidden. `isQueuedCommand` alone stays a `user` event: a prompt typed ahead while a turn ran. History recorded before this rule is not rewritten. A backgrounded tool keeps the CLI alive after `close` until it finishes, so release has no deadline and shows `stopping` until the exit. `run` starts or resumes a session in the mode the service passes, and with default setting sources, so every approval the mode asks for reaches the operator and the checkout's instructions, hooks and permission rules load as in a terminal. `set_permission_mode` calls the SDK's `setPermissionMode` and reports the result; `set_model` calls `setModel` and `set_effort` calls `applyFlagSettings({effortLevel})`, each replying with the result. The shim chooses no mode, model or effort itself. Each request waits for the service's answer, and the shim confirms every answer as accepted or rejected, so an answer that lost a race with an abort is reported `not_pending` rather than as answered. A request becomes answerable only once its event is recorded. On `close` it waits for an interrupt in flight before ending input, because ending input with a request pending keeps Claude alive for minutes. `messages` wraps `getSessionMessages` and `list` wraps `listSessions`. The service runs the shim in its own process group, so a terminal interrupt aimed at the service does not cut short the orderly release.

## The pi adapter

pi (`@earendil-works/pi-coding-agent`) runs as one private `pi --mode rpc` child per runtime, speaking JSONL on stdio in its own process group, split on LF only, as pi's framing requires (pi 1.5.2, `docs/rpc.md`). `internal/harness/pi` holds everything protocol-shaped. The capability report's pi section and its follow-up of 2026-11-16 are the evidence.

- **What pi changes about mega's promises.** pi has no permission model. It runs its tools without asking unless an extension asks, and under mega that stays exactly so. The launch dialog and the conversation say it in plain words: "pi asks for nothing unless an extension asks: it runs its tools without asking, as it does in its own terminal. It runs its own MCP servers, which mega cannot list."
  - **No trust from mega.** mega never passes `--approve` and never writes pi's `trust.json`. A checkout with project resources (a `.pi/` settings, MCP file, extensions, skills, prompts, themes or system prompt, or `.agents/skills`) that pi's saved decisions do not trust runs without them. The runtime's start then says so, from reading `trust.json` and `defaultProjectTrust` in pi's settings, writing neither.
  - **No lock.** pi has none, so mega's one-writer rule is the only protection. Nothing in the interface suggests mega can tell a terminal is open on a session; the release dialog says that both would write to the file.
- **Launch.** A new session is `--session-id <uuid mega mints>`. A resume is `--session <file>`, found by scanning pi's session folders, since a bare id that matches only another checkout's session makes pi ask `[y/N]` on stdin before RPC starts. Before pi starts, mega verifies the selected file’s header against the bound id. It also checks the session id pi reports after launch. Each passes `--model provider/id` and, for a model that takes one, `--thinking <level>`. `get_state` must name the session asked for, and the start's facts carry the model, the thinking level, no permission mode, and the version from the pre-launch read, since RPC reports none.
- **Models and the request.** A short-lived `pi --mode rpc --no-session --no-mcp` answers the list and the copy, so nothing is written to a session file.
  - **The list** is `get_available_models`, the models whose provider has credentials, each named `provider/id`. A model with reasoning lists the thinking levels `set_model` then `get_available_thinking_levels` give. pi writes none of its settings for `set_model` over RPC, which leaves `settings.json` as it was.
  - **The copy** is what `get_state` reports before any change: pi's own `defaultProvider`, `defaultModel` and `defaultThinkingLevel`, as pi resolves them. A level the model does not take is clamped, and a model without reasoning takes no effort, so Michael's `ollama/qwen3.8-27b` copies none.
  - **A change** is `set_model` and `set_thinking_level`, reported as `model_changed` from `get_state`.
- **A turn.** `agent_start` opens it, and pi sends it again for each retry inside one run. A `prompt` sent while the adapter knows a run is active, from pi's `started` answer or its `agent_start`, goes as a `followUp`, as one typed ahead does. A prompt answered `handled` (an extension command) starts no run: `Prompt` returns `harness.Handled`, and the service records its row, as Prompt above says. The adapter reports no turn end for it. Events map as follows:
  - `message_end` messages map to `assistant`, `tool_use` and `tool_result` events, and `text_delta` to the live deltas;
  - `agent_settled` ends the turn: `success`, `interrupted` when aborted, or `error` with the failed response's message;
  - `system` messages, which pi writes before a user message, yield nothing;
  - thinking blocks, notifications, retries, compactions and extension errors are native events.
- **Live and stored messages.** pi’s RPC frames carry no entry ids. The adapter records live events in wire order and takes the outcome from pi. Its user echo is native bookkeeping because the service already recorded the prompt. Reads of pi’s session file use the entry id, with `/<index>` for an assistant content block.
- **A dialog’s timeout** runs from when the dialog arrived. The adapter settles it as expired at pi’s deadline and refuses an answer that arrives later.
- **Dialogs.** Every `extension_ui_request` dialog is a question, never an approval, with no allow for the session:
  - **The kinds:** `select` is a question with its options and no answer of one's own; `confirm` is Yes or No; `input` is a one-field form; `editor` is the same field over several lines, prefilled.
  - **Dismiss.** Each offers it (`"dismiss": true`): pi's own cancel, which the extension sees as no answer, as Escape does in pi's terminal. It is sent only when the operator presses it; the service accepts `dismiss` only where the payload offers it.
  - **A timeout.** A dialog with one is settled by pi on its own, sending nothing, so the adapter settles its record as `expired` when the time runs out.
- **Interrupt** sends `abort` without waiting: pi answers it only once the run is idle, and a pending dialog holds the run until it is answered or dismissed (R2). With a dialog pending, the history records a runtime event, `waiting`, naming it: "Interrupt waiting on a dialog: the interrupt waits on pi's dialog '…': pi stops once it is answered or dismissed". mega answers it for nobody. An extension that passed its dialog pi's abort signal lets the interrupt cancel it. The run then settles aborted, and a dialog still pending when a run settles aborted or failed is settled as `aborted`, with nothing sent to pi, so no later answer is taken for one pi no longer reads.
- **Release always works** (Michael, 2026-11-16).
  - **How.** Close closes pi's input. A pending dialog holds pi through that and a first SIGTERM (pi 1.5.2), so a pi still running is ended in steps: a SIGTERM 3 s after the close with a dialog pending (30 s without), a second SIGTERM 3 s later, which pi takes at once, then SIGKILL to the process group 3 s after that.
  - **The dialog** still pending is recorded as `unanswered`, and the command it gated does not run. The exit says mega ended the process, and anything left in the process group is named, as for Codex. A process group that cannot be listed is reported as could not be checked, as for Codex. Claude's exit is checked the same way: after the shim exits, anything still running in its process group within 5 seconds is named and the runtime recorded as an `error`, and a group that cannot be listed is reported as could not be checked. All three harnesses share one helper for the listing and the verdict (`internal/harness/procs.go`).
  - **Where.** mega's own exit takes the same path. The shutdown gate still waits while a request is pending.
  - **The warning.** Before the operator confirms, the release dialog says it: a pi dialog is waiting, pi cannot be stopped politely while it waits, releasing ends its process, and the command the dialog gates does not run.
- **History and discovery.** A session file is read directly: its conversation is the chain from the file's last entry back by `parentId`, as pi reopens it, so a file two writers branched follows the last writer. Discovery scans the checkout's folder in `PI_CODING_AGENT_SESSION_DIR`, else `sessions/` in pi's agent directory, named from the checkout's path, and lists every session in it, newest first, with each session's first prompt as its preview. pi's `sessionDir` setting is not read.
- **What pi lacks is absent, not pretended.**
  - **No permission mode:** a pi conversation has no mode control.
  - **No MCP list:** pi runs its own MCP servers and reports them only as free text answering `/mcp`, so the More menu has no MCP item.
  - **No background jobs.**
  - **`@path`** is not attached over RPC, so mentions are inserted as bare paths, as for Codex.
  - **A lone effort:** where the model takes one thinking level or none, there is no effort control.
- **The version** is `pi --version`, the bare version. pi's tested range is the one build probed, 1.5.2.

## HTTP surface

Everything is JSON with `snake_case` keys. Errors carry `{code, message}` with `code` one of `invalid` (400), `not_found` (404), `conflict` (409), `not_pending` (409, an answer to a request that is no longer pending), `shutdown_pending` (409, new work while a shutdown is armed), `checkout_missing` (409, work in a project whose checkout cannot be worked in), `executable_missing` (409, work for a harness whose executable cannot be found in the project's environment, or at the path the config names), `environment_unapproved`, `environment_changed`, `environment_invalid` and `environment_failed` (each 409, see project environments), `harness_failed` (502, the harness itself failed to start or answer: its first line of reason, never a stack, which goes to the log; or an answer it was sent and never confirmed, in the adapter's words), `unavailable` (503, the service is shutting down or has closed; once it has closed, every read below that passes its input checks is refused this way, where a malformed one is still `invalid` and one already reading a log as it closes can be `internal`, in the moment before the HTTP server stops, and the stream closes as it opens), or `internal` (500, detail logged rather than returned). A harness's own failure never reaches the page as `internal`.

A project is `{id, name, checkout, starred, untrusted, checkout_missing, environment}`, with `environment` on the workspace read (see project environments). `starred` is workspace state: a field on the project in `registry.yaml`, written only through the service (`UpdateProject`, which changes the name, the star or both in one registry write), so a star is the same in every browser. Memory moves only after the write is confirmed, and browsers learn of it through `workspace_changed`. An unstarred project writes no field, and a registry written before stars reads as unstarred, with its version unchanged. A `PATCH` with neither field is `invalid`. `checkout` must be an absolute path to an existing directory and may be registered once; an empty `name` becomes the directory name. Removing a project takes it and its conversations out of the workspace and deletes mega's history and reading positions for those conversations; the checkout and the native sessions stay where they are.

A conversation is `{id, project_id, name, label, harness, native_id, mode, state, turn_active, turn_started_at, attention, read_seq, last_seq, model, effort, version, permission_mode, permission_mode_choice, model_choice, effort_choice, turn_asked, turn_ran, turn_differs, pending, background, mcp, environment, environment_stale}`, where `model`, `effort`, `version` and `permission_mode` are what the running harness last reported, the `_choice` fields are the request, and the `turn_` fields are what the turn in flight asked for and ran with, absent with no turn in flight and `turn_ran` until its first output; and where `pending` is the current pending set as `{id, kind, payload, at}`. `at` is when the request was recorded, its request event's own time, held in memory beside the pending set and never stored. `background` is the work the runtime keeps running outside a turn, each job as `{id, description, kind, started_at}`. It is absent when there is none, and when there is no runtime to ask, which is the case for an unsupervised conversation, whose list is unknown. The adapter reports it whole each time it changes, through the sink's `Background`, never as an event. The service holds it in memory on the live record beside `turn_active`, never stores it, and clears it when the runtime exits, so a restart shows none. It is not attention: background work never puts a conversation in the needs-you list or changes its attention.

`mcp` counts the runtime's MCP servers as `{servers, connected, connecting, failed, needs_sign_in, disabled}`. It is absent until the runtime has reported them, and with no runtime; the servers themselves are on `GET /api/conversations/{id}/mcp`. Each adapter reports the whole list through the sink's `MCPServers`, never as an event, as plain data: each server's `name`, a `status` from one small set (`connected`, `connecting`, `failed`, `needs_sign_in`, `disabled`), its `error` if any, and its tools, each `{name, description}`, where the description is the first line of the harness's own. The service holds the list in memory on the live record beside the background list, never stores it, and clears it when the runtime exits. A list that is the same as the last announces nothing. It is not attention: a server that failed or needs signing in never puts a conversation in the needs-you list, changes its attention or holds the shutdown gate.

The background list's `kind` is the harness's (`local_bash`, `local_agent`; `command` for Codex). `started_at` is when the adapter first saw the job, since neither harness reports a start time. `turn_started_at` is when the turn in flight began: when the harness reported starting it, for the turn a prompt begins as for one the agent starts by itself, such as Claude's woken by a background job. It is held in memory beside `turn_active`, never stored, cleared when the turn ends or the runtime goes, and absent when no turn is in flight, so a restart never shows one. `instructed_at` is when the operator last instructed the conversation: the time of the newest prompt mega sent it, a launch's opening prompt or any after (below). `permission_mode` is the running mode, as Claude last reported it or the launch passed it, and `permission_mode_choice` the requested mode (Claude only). `model` is the model the harness last reported and `effort` the effort Codex last reported; `model_choice` and `effort_choice` are the request, always concrete (`effort_choice` is absent only for a model that takes no effort level, or a Claude effort still to be chosen). `turn_asked`, `turn_ran` and `turn_differs` are the turn in flight's record, as a `turn_end`'s `turn` carries a finished one. A request's payload is plain data for display: `tool` and `input` (plus `title`, `description`, `decision_reason`, `blocked_path` where Claude gives them, and `permission_mode`, the mode it was raised in) for a permission, `questions` for a question. An MCP tool approval adds `mcp_server`, `mcp_tool`, `parameters` (as Codex displays them) and `allow_session`. A typed form question carries `mcp_server`, `message` and `fields`, each `{name, type, title, description, required, options, default}`. `environment` is what the running runtime was launched with, `{source, activation, changed, fingerprint}`: names and fingerprints only, absent when no runtime runs. `environment_stale` says the runtime would start in another environment now. `harness` is `claude`, `codex` or `pi`. Accepted commands answer 202, and their effects arrive on the stream.

The path search lists names in a project's checkout and is read-only: it changes no workspace state and nothing in the checkout.
- **What it lists.** Files git tracks, plus untracked files git does not ignore, from `git ls-files -z --cached --others --exclude-standard` run in the checkout with `GIT_OPTIONAL_LOCKS=0`, so the index is never refreshed. The directories those files imply are added. Ignored files, such as build output and dependencies, never appear.
- **Where git cannot list it.** A checkout that is not a git repository, or where git fails, is walked instead. The walk skips directories whose names start with a dot and stops at 50,000 entries, as the git listing does.
- **Caching.** A checkout's listing is held for five seconds, so typing does not run git on every key, and a file created a moment ago appears within that.
- **Matching.** The query is split into fragments at slashes and spaces. Each fragment must appear, ignoring case, after the one before it. A path whose last fragment can fall in its last segment (a basename match) ranks above one matching only in its directories, then shorter paths come before longer, then by name. An empty query lists the shortest paths, with hidden ones (any segment starting with a dot, such as `.claude/`) after all the others.
- **What it never does.** It reads no file's contents. Git and the walk never descend a symbolic link. A path that is itself a link is offered only if it resolves inside the checkout, so nothing outside it is ever named. A path that no longer exists in the working tree is not offered: a file git still tracks but that was deleted, or a directory only such files imply. Each result is checked by name as it is picked.

**Beyond the checkout.** The operator may name directories in the config, `path_search.directories`, such as `~/Sandbox`, for the files an agent is pointed at that live nowhere in the project: a screenshot, a scratch file. None are named by default, and then the search is the checkout's, whatever is typed.
- **Reached by how the query starts.** A query starting with `~/` or `/` searches the named directories; any other searches the checkout as above. The directories are the operator's own, so they are the same in every project.
- **A directory typed is looked in.** Where what is typed up to its last slash, `~` expanded, names a directory that, resolved through every link, is still inside a named directory, that directory is read directly: its own entries, those whose names match what follows the slash. `@~/Screenshots/` lists that folder, and `@~/Sandbox/shots/` that one, however large anything else named is. Each is shown under the named directory as configured.
- **Anything else is a filter** over a listing of every named directory. It holds each named directory itself, then its entries level by level, so a directory's own files are always listed before anything deeper, and a deep tree cannot crowd out a file just dropped at the top. The listing has the checkout walk's limits: names and modification times only, never a file's contents; directories whose names start with a dot skipped; no symbolic link followed, and a link that resolves outside the directory it is in, or nowhere, not listed. Each named directory has its own bound of 50,000 entries, so one cannot use up another's. The listing is held for five seconds, as a checkout's is.
- **Nothing else.** A path outside every named directory is never listed, however it is typed. A typed directory that resolves outside every named directory, through `..` or a link, is not looked in, and falls to the filter, which lists only what is inside. This is not a browser for the whole machine.
- **Matching and order.** The filter matches a query starting with `~` against each path as the list shows it, with `~` for the home directory, and one starting with `/` against the absolute path; fragments match as in the checkout. Either way, files come before directories, since the file wanted is nearly always the one just made and adding a file makes its directory as new; then a directory's own files before deeper ones; then newest first. At most twenty.
- **Stopping short is said.** A listing that reached its bound, a named directory's or a directory looked in, names that directory in `stopped`, and the list says "Listed only part of ~/Sandbox/, which holds more than the search reads. Type a folder's path to look in it.", so a missing file is not taken to be absent. That came from Michael's own: with `~/Sandbox`, about 76,000 entries, named before `~/Screenshots`, one bound shared in config order once left `@~/Screenshots/` listing the folder and none of its files (`a-large-named-directory-starves-the-path-search`).
- **What is inserted**, from the capability report's 2026-11-16 follow-up:
  - **for Claude,** the path as the list shows it, as a mention, `@~/Sandbox/shot.png`, quoted when it holds whitespace (`@"~/Sandbox/shot one.png"`). Claude Code 2.1.325 attached `@~/…` and `@/…` alike, outside the checkout as inside it, and only quoted with a space;
  - **for Codex and pi,** the bare absolute path, which needs no agent to expand a `~`: Codex 0.166.0 and pi 1.5.2 read both forms, but in Codex it is the model that expands `~`.
- **What a harness asks** is unchanged, and mega adds and removes nothing. A Claude mention attaches the file with no request, as the operator's own naming of it. An agent's own read outside the checkout asks, or not, as the harness and the operator's settings say: Claude's `Read` asked from a checkout with no rule allowing it; Codex's workspace-write sandbox read without asking; pi asks nothing unless an extension does.

A history read returns a stretch, `from` through `through`, through the log's index.
- **Native events are not sent** unless `native=1` asks for them. The stretch still covers them: `through` is the newest event it covers, sent or not, so a reader holding it has been given everything up to there.
- **A read by turns** starts at a turn's first event (the index's rule, above). A turn therefore comes whole, with its prompt, every tool call and its result, its requests and its replies.
  - At the end of the log, a newest turn that has not ended is always included and not counted among the `N`. That covers the turn in flight, and the events after a turn that open the next.
  - It carries `earlier`, `{turns, events}`: how many turns start before `from`, and how many events lie before it, native ones included.
  - The newest seq is taken under the same lock as the turn lookup, so a stretch never starts after its own `through`.
- **`since`** combines with neither `turns` nor `before`.

Every request that takes longer than a second is logged at warning level with its method, its path and query, how long it took, its response size and status (`internal/server/slow.go`). The stream, long-lived by design, is not timed.

Every write is a command to the service, the one writer of the registry and the logs; the server holds no state. A launch runs outside the service's lock, because Codex reports its start before the launch call returns; other operations on that conversation stay refused until it settles, and a runtime that exits while launching is settled like any other exit.

Every other path serves the embedded UI, falling back to `index.html`.

The stream carries `{conversation_id, event}` for each recorded event, `{conversation_id, delta}` for streaming text (never stored), `{workspace_changed: true}` after any confirmed change to the workspace (the registry, a runtime's state, a pending set), `{heartbeat: <time>}` every 20 seconds so a page can see that a quiet stream is alive, and `{shutdown_finished: true}` as the last frame an orderly shutdown sends before the stream closes. It replays nothing: a client that reconnects re-reads confirmed state. A client that falls 256 updates behind is disconnected rather than allowed to slow the service.

`shutdown` is the gate as `{armed, armed_at, idle, blockers}`, where `armed_at` is absent while unarmed and each blocker is `{conversation_id, project_id, name, turn, requests, background, settling}`: whether a turn is in flight, how many requests are pending, how many background jobs run, and `starting` while a launch is in progress. It is computed at every read, armed or not. `shutdown_pending` (409) is the gate's refusal of new work.

Requests are refused with 403 unless their `Host` is loopback and any `Origin` matches that `Host`. The loopback bind keeps the network out; this keeps out web pages in the operator's own browser, which could otherwise reach `127.0.0.1` through DNS rebinding or a cross-site request.

## Project environments

A project's work runs in that project's own shell environment, never in the one mega was started in. Michael's Go projects are kept apart by `devprj`, which gives each its own `GOPATH` and puts that project's bin first on `PATH`. The house Makefile convention relies on that: `make clean` clears the whole Go bin, because that bin belongs to one project. Before this, every agent got mega's own environment, so an agent's `make clean` in one project cleared another's bin, and a project's own bin was not on `PATH`.

### Resolution

`internal/environ` resolves a project's environment for each runtime start, and for mega's helpers that run in the project's name: reading native history, discovery, the model list, path search. It is never stored.
- **The base.** It starts from a base scrubbed of mega's own environment. The base keeps only `HOME`, `USER`, `LOGNAME`, `SHELL`, `LANG`, `LANGUAGE`, `TZ`, the `LC_*` variables, the desktop session's display, D-Bus, runtime-directory and session variables, and `SSH_AUTH_SOCK`. `PATH` is the system default, `/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin`. Nothing of an activated terminal survives (`GOPATH`, `_DEVPRJ_*`, `CLAUDE_CONFIG_DIR`), so a mega started from an activated terminal resolves the same as one started from the launcher. A fresh base also avoids `devprj`'s refusal when an environment is already active, which exits 0 and changes nothing (capability report, 2026-11-12).
- **The shell.** The operator's shell (`SHELL`, else `/bin/sh`, or `environment.shell`) runs as a login and interactive shell (`-l -i -c`) in the checkout, in a session of its own with no controlling terminal. As a login shell it reads the profile scripts (`/etc/profile` and `/etc/profile.d`, `~/.profile` or the shell's own), where tools such as cargo, Homebrew on Linux, Nix and snaps set their variables. As an interactive shell it reads the interactive start-up files. Tests that resolve many times and are not about the profile may set `SkipProfile`; mega never does. An interactive shell put in a background process group of the terminal mega runs from would try to take that terminal, and be stopped until the timeout. It writes the environment before the activation to fd 3, runs the activation, and writes the environment after it to fd 4. Neither comes from the shell's output, which start-up files and activations write to. The activation's last command decides its status, as in a terminal. A non-zero status, an activation that ends the shell, or one that runs past the timeout (ten seconds by default; the shell's process group is killed) is a failure. About 170 ms with Michael's bash and `devprj`, most of it `/etc/profile.d`; 55 ms without the login scripts.
- **Checked again when it is used.** A resolution is used only while the project's file or override is still the activation it resolved. Mega checks that when resolution finishes. It checks again immediately before launch, after reading the harness version, and before reading a native transcript for adoption (`harnessGateLocked`). A changed file produces `environment_changed`. Once shutdown begins, the same check returns `unavailable`. A launch refused at this check records `error`.
- **What is passed on.** Everything the shell had after the activation, except `_`, `SHLVL` and `OLDPWD`, goes in full to every process mega starts for the project: the shim and the `claude` it starts, the Codex app-server, and `git` for path search. An empty environment is never left nil, which exec would fill with mega's own.
- **Where mega finds its own programs.** It locates them on the `PATH` of the environment before the activation (fd 3), never the activated one: `node` for the shim, the `claude` executable when it is configured as a bare name (a path is used as configured), the `codex` binary, and `git` for path search. The `claude` executable must be a native build, as the installer's builds and its `claude` link are. The SDK starts a script through an interpreter it finds by name on the process's activated `PATH`. So a configured `claude` that is a script (a `#!` line, or a `.js`, `.mjs` or `.cjs` file) is refused as a missing executable, saying why and what to set. Each runs by absolute path (`harness.Program`). A script's whole interpreter chain is followed the same way, up to four interpreters deep, and mega builds the command line itself. That covers `#!/usr/bin/env PROG`, `#!/usr/bin/env -S PROG ARGS` (such as Codex's npm wrapper and its `node`), and an absolute interpreter, which gets the rest of its line as one argument as the kernel gives it and may itself be a script. Anything it cannot resolve is refused as a missing executable rather than run: another `env` option, an assignment, `env` naming `env`, `env PROG` with more words and no `-S`, a relative interpreter, or a deeper chain. `env` would look the next program up on the activated `PATH`. So an activation can change what an agent's commands see, inside the harness's permission model, but never which program mega itself executes. An activation, or a file it reads, that puts a directory in the checkout first on `PATH` cannot get its own `node` or `git` run by mega. The harness and service pass both environments as `harness.Place{Cwd, Env, Find}` and `Spec.Env` and `Spec.Find`.
- **What the harnesses do with it.** Claude Code 2.1.318 and 2.1.322 pass it to their commands with the `PATH` order intact. Codex 0.166.0 passes it too, but runs each command in a login shell, so its own helper directory and `~/.profile`'s entries come before the project's bin. The `GOPATH` is still the project's. A resumed session picks up whatever its new start is given (capability report, 2026-11-12).
- **Claude's settings.** The Claude settings lookup (what a new conversation copies: the mode, model and effort) reads `CLAUDE_CONFIG_DIR` and `HOME` from the project's latest resolution, since that is where the `claude` it launches looks.

### The definition, in the repository

`.mega/environment.yaml` in the checkout has one key, `activate`, a short shell snippet run in the checkout, such as `devprj`. Other keys are ignored, for later. No file means the shell's own environment in the checkout and nothing more. The file is read with `dd` on every workspace read and every start. One that cannot be read, is not a regular file, or does not bind (`activate` not a string, YAML that does not parse) is malformed. Its fingerprint is the first 16 hex digits of the SHA-256 of its bytes, written `sha256:…`.

### Approval, in the workspace

mega runs an activation in the operator's shell, outside any harness's permission model, from a file that agents and other people's repositories can write. So it runs the file's activation only once the operator has approved it, as `direnv allow` does.
- **Approving the file approves its text.** The approval covers the exact content of `.mega/environment.yaml`, nothing else. An activation that reads other files in the repository, as `devprj` reads `.devprj`, or a snippet that sources a script, is trusting those files, and an agent can usually write a file in its checkout without asking. Two things limit what such a file can do. mega finds its own programs before the activation (above), and the approval remembers the names the activation changed (below).
- **What is stored.** The approval is workspace state on the project, `env_approved: {digest, at, changed, names_known}`, written through the service under the registry's durability rules.
  - `digest` is the full SHA-256 of the approved text, `sha256:` and 64 hex digits, and the binding a file is compared against. The page shows its short form, the first 16 hex digits.
  - `changed` is the names of the variables the activation changed when it was approved. `names_known` says they have been recorded.
  - The content is never kept, since it can hold a literal value, and no value is either.
- **Approving.** It takes the full digest of the version the page showed, so an approval never covers a version the operator did not see. A file that changed since is refused with `conflict`, a malformed one with `environment_invalid`, and anything but a full digest with `invalid`. Approving then resolves at once, running the approved activation, and records the names it changes with the approval. A resolution that fails leaves the approval without names, and the next successful one records them. A new approval, even of the same text, forgets the old names and records them afresh.
- **The names hold.** A later resolution of the approved file whose activation changes another set of names is refused with `environment_names_changed`. The resolution's added and removed names are kept in memory, never values, and shown on the project page. A new `LD_PRELOAD` or `GIT_SSH_COMMAND` from a file the activation reads then needs a human. The refusal is about that resolution, not the file: launches, prompts and Starts still resolve again, and a resolution that changes the approved names lifts it, as approving again does. The override's own activation, and no file, have no names to hold to.
- **A changed file** is not run until it is approved again. The project page shows the approved version beside the current one. The approved version is found by its digest in the checkout's git index and the file's last 50 commits (`GET …/environment/approved`), with `git` run from the scrubbed base, since the project's own environment cannot be resolved while its file waits. A version that was never staged or committed is named by its fingerprint and cannot be shown.
- **An old registry.** A registry written before approvals reads as nothing approved and no override. An approval stored before the full digest (`env_approved: {fingerprint, at}`, sixteen hex digits) is read but counts for nothing. It refuses as `environment_unapproved`, and the page says the file was approved under the short fingerprint, which is not binding enough, and needs approving again. The registry's version does not change.

### The override

`env_override` on the project is the operator's local choice, also workspace state, and needs no approval. `{ignore: true}` ignores the repository's file, leaving the shell's own environment. `{activate: "…"}` runs that snippet in its place. It exists so that someone who clones a repository whose file names a tool they do not have can still work there. Clearing it lets the file decide again.

### Refusals

Each refuses a launch, a prompt (to a running or a stopped conversation) and a Start with its own code (409). The message says which it is and names the file, the override or the checkout.
- `environment_unapproved`: a file never approved.
- `environment_changed`: a file whose digest differs from the approved one.
- `environment_invalid`: a malformed file.
- `environment_failed`: a failed or timed-out activation. Its message carries the activation's own last lines of output, for the operator.
- `environment_names_changed`: an approved activation that now changes another set of variables than it did when approved. Its message names what it now also changes and no longer changes.

The first three are known without running anything, and refuse before anything is recorded. A new conversation's environment is resolved before the conversation exists, so a failed activation leaves only the refusal. For an existing conversation, a failed resolution ends the start recorded as `error`, as any failed launch is. Adoption, discovery, the model list and path search use the project environment and can receive the same refusals. Resume acknowledges lost supervision in the registry. Workspace reads, rename, star and removal keep working.

### What is recorded, and what never is

An environment carries credentials, so no value is ever written to the event log, the registry, or the server's log.
- **Each runtime start** records, on its `started` event's facts, `environment: {source, activation, changed, fingerprint}`. That is where the activation came from (`none`, `file`, `ignored` or `override`), the activation's fingerprint, the names of the variables it changed against the shell's environment before it, and the fingerprint of the whole resolved environment.
- **A failed resolution's event** says that it failed and where, never what the activation printed.
- **In memory.** The service keeps each project's latest resolution (its time, names, fingerprint or failure, and the variables themselves), never stored.
  - **Nothing resolves a project in the background.** Not start-up, not a registration, and not a workspace read, however often the page or the tray reads. A project is resolved only by something that needs its environment, and the resolution it makes is the one held: a runtime start, a helper that runs a harness in the project's name, an approval, and the operator's Resolve on the project page. The helpers are the model list, which the launch dialog asks the service for as it opens, and which a conversation's controls and turn lines ask for when it is opened, stopped or not, unless the page still holds the list from earlier in its life; discovery, which the adopt dialog reads; reading native history for an adoption; and path search. The service resolves the operator's shell once at start-up for the harnesses (below), never a project's. A project whose file is unapproved, changed or malformed is never resolved. Its refusal is known from the file alone, so its page shows it at once.
  - **A resolution counts only while it came from the activation that would run now.** One from another activation, after the override changed or the file appeared or went, reads as none until something resolves the project again. The page says "Not resolved yet", nothing is listed missing from it, and it refuses no start: the start resolves afresh. A failure is kept until the next resolution of the same activation.
  - **After a restart** every project reads as not resolved yet, and lists nothing missing, until something resolves it. The first thing that needs a project's environment waits while its activation runs: about 0.2 s of login shell for Michael's profile on `fortyfive`, plus what the activation takes. Helpers asked together with no fresh resolution each resolve on their own, as the adopt dialog's discovery does for each harness, so one dialog can run the activation more than once. A running conversation's "started in an older environment" mark for a changed fingerprint appears only once the project has been resolved again, since until then there is nothing to compare its start with. A changed activation, or a file that now refuses, marks it at once, since that is known without running anything.
- **The file watch.** A goroutine looks at every project's file every two seconds and announces a change when one appears, changes or goes, so the page follows an edit made in a terminal or by an agent.

### The preflight

Each project's latest resolution carries what each harness cannot find in it: `node`, the `claude` executable and the shim for Claude, and the configured `codex` (and the interpreter its `#!/usr/bin/env` line names) for Codex. A bare name is looked up the same way mega runs it, on the `PATH` before the activation. A configured path is checked as it stands: one that does not exist, or is not an executable file, is missing, and its reason names the path and says what to do, naming the config file mega read or the one it looked for: "'codex' cannot run: '/opt/codex/bin/codex' does not exist; install Codex, or set codex.binary in '…/mega.yaml', the config file mega read, to where it is". Claude Code's reasons, with the bare name and with a pruned versioned path, are under "Finding Claude Code" above. A Codex that is not installed whole is missing too (below). It is computed on every read. A harness that cannot run refuses launch, prompt, Start and its model list with `executable_missing` (409). Each start also checks the harness in the environment it just resolved. A harness failure caused by a missing executable is reported as that condition. Any other failure of the harness itself, such as the shim exiting with an error, is `harness_failed`, with its first line; neither is ever "internal error", and a stack goes only to the log. A launch failure's event in the history records the same summary. The launch dialog offers such a harness disabled, marked "(cannot run)", with the reason; a reason for a configured path already says what to do, and one for a name on `PATH` adds that mega cannot start it until it is found in the project's environment. A harness whose model list is refused as `executable_missing` is marked the same way, even before the project's resolution lists it. Before a project has resolved, or since its activation changed, there is nothing to check, and its next start checks what it resolves.

### The start-up check of the harnesses

At start-up, in the background, the service resolves the operator's shell in the home directory with no activation, the environment a project without one gets, and checks each harness there. A shell that cannot be resolved leaves mega's own environment to look in, and the log says so. Each harness gets one log line: "harness 'claude' can run, in the operator's shell environment: claude code '…', node '…', shim '…'; version '2.1.325', of the '2.1.318 to 2.1.326' mega was tested with", or "harness 'codex' cannot run: 'codex' was not found on your shell's PATH (looked for in the operator's shell environment)". A newer build's line says "version '2.1.330', newer than the '2.1.318 to 2.1.326' mega was tested with", at info. An older build, or a version that could not be read, makes the line a warning carrying the sentence for it (below). The environment it found is kept, and the workspace read carries `harnesses`, each `{name, found, where, path, reason, version, tested, standing, note}`, re-checked on every read, so an install shows without a restart; it is absent until the check has run. That is what the empty workspace's page shows. The versions are read at start-up and kept by where each harness was found and by the identity of its own program's file: the path it resolves to, links followed, with its device, inode, size, and modification and change times. A read that finds a harness somewhere else, or its program another file, answers with the location at once and reads its version in the background. That covers Claude Code's updater moving `~/.local/bin/claude` to a new build, and an npm update of Codex or pi replacing the program under the same name: a new file, a new inode and change time, even with the modification time npm's tarballs carry. The environment-file watch looks at the harnesses' programs on each of its two-second looks too, and the read that follows announces a workspace change, so the first page and the version panel follow an update within seconds with no restart and nothing else changing. The panel takes the harnesses from the workspace, so an open one follows too.

### Harness versions and the tested ranges

A harness's **tested range** is the lowest and highest build between which every build that harness's probe ran passed its steps: for Claude Code and Codex the version probe, a fixed list of mega's calls that `probes/versions/README.md` names; for pi, which has no version probe, the one build its own probe (`probes/pi`) and round trips ran. It covers the builds the capability report lists, and is not a promise that every call mega makes was seen to work on every build in it. A call the probe did not make can still break inside the range, as the model switch on an idle runtime did until the probe made it on 2026-11-19. The ranges are Claude Code 2.1.318 to 2.1.326, with the shim's pinned Agent SDK 0.3.318, Codex 0.163.0 to 0.169.0, installed whole (capability report, follow-up of 2026-11-14), and pi 1.5.2 (follow-up of 2026-11-16). They live in one place, `harness.Tested` in `internal/harness/versions.go`.
- **Reading a version.** mega runs the harness's own `--version`, as it would run the harness: Claude Code's executable, with `DISABLE_AUTOUPDATER=1` for that call, and Codex through the interpreters its wrapper names. It takes the first `x.y.z` from output that names the harness, "2.1.325 (Claude Code)" or "codex-cli 0.169.0", so another program at the configured path is not read as the harness. The call runs in its own process group and is killed with its children after two seconds (`harness.VersionTimeout`); every build seen answers in about 10 ms.
- **When.** At the start-up check of the harnesses, by `mega version`, and before each launch, in the project's environment. A version that cannot be read is `unknown`, and the launch goes on.
- **Standing.** `tested` inside the range, `newer` above it, `older` below it, `unknown` unread. Nothing is refused for its version.
  - **A newer build is the normal state.** Claude Code releases every day or two, so an installed build is above the range almost always, and a notice for it would be permanent and meaningless. It has no sentence (`note` is empty) and is said in plain words wherever versions are shown, never in the notice colour or at warning level.
  - **An older build needs a look,** and is worded strongly, since the SDK's documentation expects the Claude Code of its own patch or later: "Claude Code '2.1.300' is older than the builds mega was tested with, '2.1.318 to 2.1.326'; the Agent SDK mega runs expects Claude Code '2.1.318' or later, so some calls may fail". So does a version that cannot be read: "the version of Claude Code could not be read, so mega cannot say whether it was tested; mega was tested with '2.1.318 to 2.1.326'".
- **On the runtime-started line.** The `started` event's facts carry the version the runtime reported (Claude's `system/init` or `ready`, Codex's CLI version), or the pre-launch read when it reported none, with `standing`, `tested` and `version_note`. The history marks that line, and adds no other, only for a build older than the range: in the notice colour with a solid edge, " · older than the 2.1.318 to 2.1.326 mega was tested with" after the version, and the sentence as its title. A build inside the range or newer, or an unknown one, is not marked and gains no words; the version is already there.
- **Elsewhere.** The start-up log line per harness, the first page's list, `mega version` ("found '2.1.330', newer, claude code '…'"), and `GET /api/version` with the panel the footer's version opens ("Version 2.1.330; tested 2.1.318 to 2.1.326, so this build is newer.") each say the version found and the tested range, and the sentence, in the notice colour, for an older or unread one.
- **Extending a range** for Claude Code or Codex is running `probes/versions/` against the new build, which makes the e2e round trips' calls that its README lists through a scratch mega on the disposable fixtures, then recording what it saw, with the version, in the capability report and widening `harness.Tested`. Its README says how.

### Codex installed whole

A Codex is checked for the helper programs its package installs beside it. The release's lone `codex-<target>.tar.gz` holds only the binary; one run from it answers a turn but cannot run a shell command, and the turn ends `success` with the model saying the execution tool's host was not found (0.169.0, capability report, 2026-11-14). The check, `codex.Harness.helpers`, reads `codex-package.json`, which the release's `codex-package-<target>.tar.gz` and npm's platform package lay out the same way:
- **Where the manifest is.** Beside a native binary, in its own directory or its parent, when the manifest's `entrypoint` is that binary. For npm's `codex.js`, in `node_modules/@openai/codex-*/vendor/*/`, nested under the codex package or hoisted beside it.
- **What must be there.** The `entrypoint`, the `execServer` when the manifest names one (0.163.0's names none), and `codex-code-mode-host` beside the entrypoint, which every package seen has.
- **What it says.** A binary with no manifest is missing: "'codex' at '…' is a lone binary; install Codex with npm or from the release's codex-package archive, whose helper programs it needs". A named program that is not there is missing, naming it: "'…/bin/codex-exec-server', a helper program the codex at '…' needs, is missing; reinstall Codex whole, with npm or from the release's codex-package archive". Either is shown wherever another missing executable is: the start-up line, the first page, the project's page, the launch dialog and `executable_missing`.

## A missing checkout

A checkout is validated when the project is registered, but it can move, be removed, or be set wrong by hand in `registry.yaml`. So every read of a project checks it again: `checkout_missing` is `does not exist`, `not a directory` or `not readable` (it exists, but the service's user cannot list or enter it), and is absent when the checkout can be worked in. Like the trust notice it is computed on every read and never stored, since the directory can come back at any time. The check reads names and modes only.
- **Nothing starts there.** A launch, an adoption, a prompt (to a running or a stopped conversation) and a Start are refused with `checkout_missing` (409), "the checkout is missing: '<path>' (<reason>)", the path quoted,, before any harness is asked. A directory moving away announces nothing, so a refusal also announces `workspace_changed`, and every page reads the notice at once.
- **Everything else keeps working.** Reads, rename, star, removal, and the project and conversation pages still work, so the operator can see what is registered, then put the checkout back or remove the project. Path search and discovery return nothing for such a project, quietly.
- **What the page shows.** The project page has a notice naming the path and the reason, and says what still works and how to fix it. The project's row in the tree has an error mark whose title is the refusal, and its rail mark has an error ring with the same title. Send, Start, New conversation and Adopt a session are disabled with the refusal as their reason. A pending shutdown's reason comes first when both apply. The Claude trust notice is not shown for a checkout that is not there.
- **When the page sees it.** At its next workspace read: on any change, on reconnect, or at once after a refusal. Nothing polls the filesystem.

## The trust notice

`untrusted` is computed from `~/.claude.json` on every read and never persisted, so a terminal visit clears it without a restart. It looks up `projects[<key>].hasTrustDialogAccepted`, where the key is the checkout's enclosing git root, or its real path outside a repository. That mirrors the check Claude Code 2.1.318 uses to gate project permission rules; it is an observation of that version, not a documented contract, and a linked worktree may read as untrusted. A missing file reads as untrusted, and an unreadable one shows no notice and logs a warning.

The service only ever reads this file. Trust is granted by the operator opening the checkout in `claude` interactively. While Claude Code cannot run in the project (the project's resolution lists it missing, or, before one, the start-up check found it missing), the project page does not tell anyone to run it. It says instead that Claude Code cannot run here yet, so there is nothing to trust, and that once it can run it asks once, in a terminal, whether to trust the checkout. With a resolution, it says the environment section lists what is missing. Before one, as after every restart, the section lists nothing, so the notice gives the start-up check's own reason in its sentence and points nowhere.

## The UI

A left column, the side panel, with the needs-you list at the top, then the projects with their conversations, each marked with its attention: a square for a request, a filled red dot for supervision lost, a red ring for an error, a filled dot for unread output, a rotating arc in the accent colour while running, all 11px, and when idle a small grey dot, 5px, centred in the same 11px box so names stay aligned. Nothing moves that is not live: under `prefers-reduced-motion`, and while the page shows last-known state, the running mark is a still half-filled ring. A conversation with a turn in flight shows how long the turn has run after its name, in the tree and in the needs-you list, in the mono register: `45s`, `4m`, `1h 12m`. A conversation waiting on a request shows instead how long its oldest pending request has waited, counted from that request's `at`, since on a row waiting for the operator the number reads as the wait. One timer serves every label on the page, ticking once a second while any shows, so a label can trail real time by up to a second; it stands still from the moment the page goes stale. Background work changes how a conversation looks, never its attention. An otherwise idle conversation with background jobs shows the working arc in the muted colour, titled "2 background jobs running", never the idle dot; it stands still, as a muted half-filled ring, under reduced motion or when stale. A conversation whose mark is anything else keeps it and carries a small mono label after its name, `2 bg`, in the tree and the needs-you list. The project rollup counts a background-only conversation as running. The needs-you list never holds a running conversation, because attention puts `request` above `running` and `running` above `unread`. Each project line carries one mark of the same kind: the most urgent attention among its conversations, in the order request, unsupervised, error, unread, running, idle, so what needs the operator outranks working. Its title names the state and how many share it ("2 working", "1 waiting for your answer"). The page derives it from the conversations' attention, and nothing new is stored. Each needs-you entry names its project and opens the conversation inside it.

**Where the operator left off.** In each project, the conversation the operator last instructed carries a small muted arrow after its name, Material's `west`, pointing back at it, in the tree and in the project page's list. So someone moving between a planning agent and implementers can come back and see which one he last told to do something.
- **What instructs.** A prompt sent through mega: a launch's opening prompt, and every prompt after it. Nothing else counts:
  - not an answer to a request, a start, a mode or model change, or opening the conversation;
  - not a prompt a harness reported itself;
  - not one imported from outside mega, whose time is when mega imported it.
- **Where the time comes from.** The prompt's own event is the record, and nothing else is stored, so sending can neither fail nor slow for it. The service moves `instructed_at` as `send` records a prompt. As it opens a conversation's log, which start-up's recovery does for every conversation, reading each event already, it takes the time of the newest user event mega recorded itself: one with the `managed` origin and no harness payload (`instructs`). So the time survives a restart, and older conversations have one from their last prompt through mega.
- **The marker.** One per project: the conversation with the newest `instructed_at`, reckoned on the page from the workspace read, so when it is removed the next most recent in its project takes it. A project where nothing was instructed shows none. The glyph comes after the name and before a running turn's elapsed time. Its title says when, in the service's zone, with the date when it was another day: "You last instructed this conversation in its project, at 2:02 PM".
- **Not attention.** It takes no mark from the attention set, raises nothing, counts nothing and reorders nothing. What an agent does never moves it. It is not on the rail, which shows attention only, nor in the needs-you list.

The projects are arranged in this browser:
- **Order.** Projects are sorted by name, ignoring case, with the id breaking a tie, so every browser agrees. Starred projects form their own group at the top, sorted the same way, above a hairline; the rest follow. Conversations inside a project keep their order.
- **Rows.** Project names are at weight 600 whether selected or not; conversations keep the body weight. A conversation row is indented one level, so its mark starts under its project's name rather than under the project's mark; the row, and with it the selection and hover background, still spans the panel. The needs-you list stays flush. Selection is the row's background alone (`--selected`), and hover is a lighter wash of it, so the selected row stands apart in both themes.
- **Folding.** Each project row has a fold control (a chevron, `aria-expanded`), the project, and a star toggle (`aria-pressed`, in the notice colour when on, and shown on an unstarred row only under the pointer or with focus). A folded project hides its conversations and keeps its rollup mark. A starred project is unfolded and any other folded, until the operator folds or unfolds it himself. That choice wins and is kept in this browser, so a star or an unstar changes how a project shows only while no choice has been made for it. Selecting a conversation, from the needs-you list, the next-waiting shortcut or a link, unfolds its project, so navigation never lands on something hidden. That is viewing, not a choice: nothing is recorded, and after a reload the project shows as its choice or its star says.
- **Width.** A handle on the panel's right edge (also Left and Right when focused) sets its width, from 200px to 480px; the default is 280px.
- **The footer.** The connection status, then the mega's name (below), then the build's version, which opens what the service says of its build when pressed (below). Then the control that arms the shutdown, and the control that collapses the panel. The name is the last of them to give way: it never shrinks, and only a name longer than 12em is cut short. In a narrow footer the status wraps, as "Shut down from here, retrying" does, and the version is cut short first, its title naming it whole.
- **The rail.** The footer's control, or Ctrl+', collapses the panel to a thin rail. The rail holds the control to expand, the needs-you count (in the notice colour when not zero, titled with what it counts), one mark per project in tree order (starred first) titled with the project's name, a control titled with the mega's name and its build ("mega fortyfive, v0.0.x, a developer build: show the build") that opens the same panel as the footer's version, and a dot for the connection (red while reconnecting). Each mark is the project's rollup, working arc included, so collapsing hides nothing that signals attention or activity. Clicking a mark expands the panel with that project selected.
- **Which mega this is.** A page names the mega it shows, so megas open side by side, each reached on its own loopback port through a private share, are not mistaken for each other. The name is the config's `name`, else the machine's hostname up to its first dot (`config.MegaName`), read when the service starts. It travels on `GET /api/version` as `name` and `name_from` (`config` or `hostname`), which the page reads on each connection. It then shows:
  - in the tab title, after the product's name: "mega · fortyfive", "(2) mega · fortyfive", "Ready to shut down · mega · fortyfive";
  - in the shutdown gate's notification title, the same way;
  - in the footer, beside the connection status;
  - in the rail's build control's title, and the footer version's;
  - in the version panel, as "Name", saying whether the config set it or it is the hostname;
  - in `mega version`.

  Until the service has said it, or where the hostname cannot be read and none is set, the title is "mega" and nothing is shown. The name is shown only to someone who can already reach the page, and the browser checks name their megas themselves (`mega-check`, `side-check`), so no machine's hostname lands in a screenshot or a step.
- **The build.** `GET /api/version` answers from the service's build information: the version (the developer base version, `v0.0.x`, on an unstamped build), whether it is a developer build, the commit, build time and branch when stamped, the Go version and target, the log file's path and whether this mega writes to it, the Claude Agent SDK version installed beside the shim (read from its `package.json` at start-up, or why it could not be), the identity of the interface it embeds, and each harness's tested range with the version found. The panel the footer's version opens shows those, each harness as "Version 0.166.0; tested 0.163.0 to 0.169.0." with the sentence after it, in the notice colour, for one older than the range or unread, when the newest configuration snapshot was taken and where the snapshots are ("Newest …, at start-up; 3 kept, in …/snapshots"), and whether this page runs that interface. Nothing in it is workspace state. It is read again on each connection, since a service that came back may be another build, and again as the panel opens, since a snapshot may have been taken since. Its harnesses come from the workspace when it has them, which follows a harness's update while the panel is open.
- **Times in the service's zone.** Every time the page says, the turn line's and the prompt's, the shutdown banner's clock, a snapshot's, a discovered session's and an environment's, is formatted in the zone the service runs in, not the browser's: a hardened browser such as LibreWolf may tell a page it is in UTC, hours off the operator's clock. The workspace read carries `time_zone`, the IANA name (`America/New_York`) the server reads once at start: `TZ` when set (a bare name, `:name`, a zoneinfo path, or empty for UTC), else the zone the `/etc/localtime` link names, else `/etc/timezone`, a name kept only where it loads and agrees with the local offset (`server.timeZone`). The page formats with `Intl.DateTimeFormat` in that zone (`ui/src/zone.ts`), in the browser's own locale; with no name, or one the browser cannot use, it falls back to the browser's zone.
- **A page older than the service.** The page's code is embedded in the binary that served it, so after a rebuild and restart an open page runs the previous build's interface against the new service. Directly above the reply box, an activity line says what the conversation is doing now, and is absent when nothing is:
- with a turn in flight, a spinner, what is happening, and how long the turn has run (`8s`, `1m 12s`, `1h 12m`): `Writing` while text streams; `Working · Bash go test ./...`, the summary of the newest tool call without a result since the last turn end or runtime line, which can be one the harness reported late for the turn before; otherwise `Working`;
- while starting or stopping, that word with the spinner;
- with a request pending, `Waiting for your approval`, or `Waiting for your answer` for questions, in the notice colour and with no spinner, since nothing moves until the operator acts;
- with supervision lost, `Supervision lost · execution uncertain` in the error colour, without motion;
- with no turn in flight but background jobs running, the working spinner in the muted colour, how many, what they are, and how long the oldest has run: `2 background jobs · npm test, sleep 300 · 4m`. During a turn, a request or a transition, the line stays what it is, with `· 2 in background` appended;
- with supervision lost, the background list is unknown, and the line says so: `Supervision lost · execution uncertain · background jobs unknown`;
- while stale, the last known text prefixed `Last known:`, dimmed, with no spinner.

The ticking time is left out of what a screen reader announces. An action in flight in the history shows the same small spinner in place of the word `running`.

Buttons are icons wherever a control's meaning is conventional. The icons are Material Icons, filled, from `@material-design-icons/svg` 0.14.15, pinned exactly. Each is imported as `?raw` SVG text into one `Icon` component (`ui/src/components/Icon.tsx`), so it builds into the bundle: no icon font, no runtime fetch. That component inlines the package's own SVG, never message content. Every button carries a `title` and an `aria-label` naming its action, and the icon takes the text colour around it.
- Icon only: Send, Interrupt, Copy (which shows a check once copied), the more menu, the code block's expand and collapse, dialog close and cancel, Register, New conversation and Launch, Adopt, and Undo.
- Icon and word: Allow, Deny and "Allow this tool for the session", since an approval is the one place where a misread glyph has a cost; Answer; Apply; Save; Rename; Release and Remove, which keep their confirmations; the menu's entries; "Newer activity below"; and Show earlier and Show all, above the history.
- The sidebar's tree rows are navigation, named by their text, and carry no icon.

The history is set as blocks, told apart by tone rather than borders, the same in both themes:
- the agent's replies sit on the `--panel` tone, and the operator's prompts (from outside mega too) on the `--selected` tint, both with a 6px radius and 8px by 12px padding. The operator's own prompts carry no label, since the tint says whose they are; a prompt from outside mega is labelled "outside mega", and a reply imported from outside "From outside mega";
- the reply still streaming is rendered in the history's own list as the block it will land as, from its first character, so nothing moves when it lands;
- inside a block, fenced code, its header, tables' header cells and inline code take the page background with their existing hairline, so they read as set in;
- blocks stand 16px apart. The dashed turn separator keeps its own margin, and runtime and turn status lines stay unboxed, mono and muted;
- a run of actions between two pieces of speech is one group: tool rows, request rows (`Approval for Bash: answered`) and native rows when shown. A group is indented 20px with a hairline down its left edge and no background, its rows 4px apart. Speech, runtime lines, turn separators and failed-turn lines end a group;
- an action, collapsed, is one line: the summary its adapter recorded, capped at 200 bytes and cut to the row's width with an ellipsis. After it:
  - " failed", in the error colour, for a result its harness marked as an error: Claude's `is_error`, a Codex command that exited non-zero or did not complete, a file change or MCP call that failed, pi's `isError`;
  - a spinner while it runs in the turn in flight: while a turn is open, an action with no result after the last turn end or runtime line. An action a harness reports after its own turn ended shows none when it arrives with no turn open, and one when it arrives inside the next turn, since nothing tells it from that turn's own;
  - "waiting on a dialog" instead, for pi while one of its dialogs is pending: pi raises an extension's dialog before the tool it gates executes, and runs nothing else of that batch until it is settled (`agent-loop.js`, 1.5.2), so no action without a result has run;
  - "no result recorded", or "running when last seen" on a stale page.
- an action, expanded, shows what it invoked, in full, under the label "Command" or "Invoked TOOL", then what came back, under "Result":
  - **A shell command** is the command, whole, as the harness ran it, then any other input it was given, such as Claude's `description` or the `cwd` a Codex command ran in.
  - **Any other tool** is its input, field by field: the name over the value, a string as it is and anything else as indented JSON. The fields that say what it acts on come first (`file_path`, `path`, `pattern`, `old_string`, `new_string` and the like), then the rest by name. A Codex file change is its files, each under what was done to it (`update`, `add`, `delete`); its diff is the result.
  - **Where it comes from.** Each adapter reads it from the event it recorded, whose payload already holds it (`harness.Invoker`): Claude's `tool_use` block, by the event's id, in the SDK message; Codex's thread item; pi's `toolCall` block. It is read when the row is first expanded, by `GET …/events/{seq}/invocation`, never stored a second time, and the page never reads a payload itself. A read seeks to the log's nearest index point and parses at most 256 events: on a 20,000-event, 54 MB log, a mean of 0.4 ms and at most 1.8 ms per action.
  - **An action with nothing to read,** such as one from a generated history, shows the one line it was recorded with and says that is all there is.
  - **Bounds.** Each box is bounded at 320px as any `pre` is and scrolls inside, the whole text in the page, as a result always was; nothing caps a result's text. The invocation has its own copy control, "Copy the command" or "Copy the input", which takes all of it: the command, or the tool and each field as `name: value`;
- request cards are unchanged, in their notice colours, and stay the loudest thing in the column;
- every message block, prompt or reply, has two copy controls at its top right, shown on hover or when one has focus. Copy as markdown copies the message's text exactly as recorded. Copy as plain text copies what is rendered, read from the rendered block, without markdown syntax:
  - headings and emphasis as their words;
  - lists with the markers plain text writes them with: each item on its own line, `1.` counting from the list's start for an ordered list, `-` for an unordered one, `[x]` or `[ ]` after the marker for a task item, and two spaces of indent per level of nesting;
  - code as its text;
  - a link as its text followed by its address in parentheses (the address alone when the text is the address);
  - a table as tab-separated rows;
  - a soft line break as a space.

  A code block's own header and controls are left out. The reply still streaming has none, so a half message is never copied. An expanded tool result has one control that copies the whole output, whatever its box shows. Each control is an icon (`code` for markdown, `notes` for plain text, `content_copy` for output) with a `title` and an `aria-label`. After a copy, its icon turns to a check for a moment (an error mark if the copy failed), with no toast. Code blocks keep their own Copy.

A conversation opens with its recent tail, never its whole history. Opening or switching to it reads the newest ten turns and the turn in flight (`?turns=10`), each turn whole from its first event, without native events. The page holds one conversation's stretch at a time.
- **The bar above the history** says how much lies before it ("404 earlier turns (19560 events)"). It offers Show earlier (`arrow_upward`), which loads the ten turns before what is shown, and Show all (`vertical_align_top`), which loads everything before it. Either keeps the view where it was: the first row in view is noted before the read, and the view moves by however far that row moved once the rows above it are in. Nothing loads on scroll. While a read is out, both are disabled and the bar says what it waits for. Each row carries its `data-seq`, and an action group is keyed by its first event, so rows added above leave every group, and the rows open in it, as they were.
- **Find in page** sees only what is loaded; the start of a long conversation is one press on Show all away.
- **Native events are not sent.** The native events toggle in the menu refetches the stretch shown, with them included (`?since=<from - 1>&native=1`). Turning it off drops them, fetching nothing. While it is off, native events arriving on the stream are dropped by the page. The toggle is disabled until the opening read lands, and resets with the selection.
- **Loading says what it waits for.** Until the opening read lands, the history says "Loading history:", then the request, how long it has waited, the attempt and the last error, for example `GET /api/conversations/…/events?turns=10 · 3s · attempt 2 · last error: …`. A failed read is tried again after 1 s, doubling to at most 8 s. The same line names a reconnect's read of what the page missed, once that read has failed, until it succeeds.

The page's stretch starts at `from`, a turn's first event, and is known unbroken through `through`. That is the newest event in one run since the opening read: events the read covered but did not send, native events dropped from the stream, and events received are all counted. An event received past a gap waits for the gap to fill.

A conversation opens at the top, so no scroll position carries over from what was shown before. Once its opening read has landed, and what it covers reaches the newest event held, it moves to the newest event; pending request cards are docked in the panel, always in view. After that, new activity (an event, streaming text, a new request) is followed only while the view follows the bottom. A reader who has scrolled up stays where they are and gets a "Newer activity below" control, floating just above the panel, which returns them to the newest activity; scrolling back to the bottom also clears it. The panel at the foot also changes height with no new activity: the activity line appears as a turn starts, a request docks or leaves, the reply box opens or grows. While the view follows the bottom, any change in the panel's size, or in the column's, keeps the newest content above the panel, re-pinned by a resize observer before the frame is painted. Whether the view follows is reckoned once, from scrolling alone, so it holds the state from before the panel changed. A reader who has scrolled up is never moved by it.

Leaving the bottom is a move up that was not mega's own (`ui/src/latest.ts`):
- **It ends** when a scroll event finds the view higher than where it was left last, by a scroll the page read or by mega's own move, and not at the bottom. Whatever moved it up ends following: a wheel, a key, the scrollbar (drawn as an overlay or not), a touch, the browser's find bar, or a script setting the position.
- **mega's own moves are marked.** Every one goes through `place`, which records where it left the view: the pins to the end, the reset to the top as a conversation opens, `fit`'s pin and its keep-my-place adjustment, and the earlier-history anchor. A scroll event queued by one of them finds the view where mega left it.
  - **Why it must mark them.** A pin to the end of a column whose content has shrunk lands higher than the view was. That happens when the box closes on a send from the bottom, or when a docked request leaves.
  - **What marking prevents.** Before the marking, the queued event could find that pin higher than the last scroll. If the content grew before it was read, the view was also off the bottom, which would have ended following.
- **It never ends** because the content under the view grew, since growth moves nothing.
  - **The fault this fixed.** A scroll event queued by mega's own pin and read after the content grew once found the view off the bottom and ended following for good. A send from above then went to the end and stayed there, with the prompt and reply below the fold, about one time in four.
  - **When it came in.** It arrived with 6839018, whose in-flight turn's unseen separator grows the content as the turn starts, with nothing to re-pin it.
- **It begins** whenever a scroll finds the view at the bottom, within 32 pixels, however it got there: the reader's own scroll, "Newer activity below", a send, or opening the conversation.

The UI is set in two embedded faces. Neither is fetched from anywhere but the service: both come through the Vite build into `ui/dist` and the binary's `go:embed`, and the page makes no request off 127.0.0.1.

- Source Serif 4 is the variable face from `@fontsource-variable/source-serif-4` 5.2.9, pinned exactly, with its optical-size axis, Latin subset only. `ui/src/index.css` declares the two Latin rules of the package's `opsz.css` and `opsz-italic.css` (normal and italic, with their unicode ranges) instead of importing those files, so only those two woff2 files build into `ui/dist/assets`, about 250 KB. Non-Latin text falls back to Georgia.
- Nordwand Mono 1.3.3 is self-hosted in `ui/public/fonts/nordwand-mono/`: six woff2 files (Regular, Medium and Bold, with their italics) and `LICENSE-FONT.txt`, the SIL Open Font License 1.1 (source `https://github.com/tywr/Nordwand-Mono/releases/tag/1.3.3`). It is declared with six `@font-face` rules in `ui/src/index.css` and served at `/fonts/nordwand-mono/` as `font/woff2`.
- `--serif` is for everything that speaks: message bodies, dialog prose, headings and button labels. It is the body face, at 15px, with message prose at a 1.6 line height.
- `--mono` is for everything that labels, at 12px: the header's fact line and runtime state, the needs-you project names and shortcut hint, the connection status, runtime and turn status lines, the speaker label, tool and native event summary lines, request parameter names, the code block's language, conversation labels, and the adopt dialog's session timestamps. Inline code is 13px and fenced code 12px.
- Weights are 400 and 600 only, with bold text pinned at 600, and italics are available in both faces. A face is fetched only when text uses it, so mono at 600 resolves to Nordwand's Bold file and the Medium files, though declared, are never loaded.
- The sizes above are the base. The conversation pane's type is 10% larger: every font size in `ui/src/index.css` is a multiple of `--fs`, which is 1 everywhere and 1.1 inside `.conversation`. There, prose is 16.5px, the mono labels 13.2px, fenced code 13.2px, inline code 14.3px and the title 22px; the sidebar and dialogs keep the base sizes.
- Light and dark use the same faces and sizes.
- The conversation column is capped at 960px and sits in the middle of its pane. The header, the history, the docked requests, the activity line, the input panel and the control bar share it, and so do the banners that span it; the show-earlier bar and the newer-activity control are aligned to it, not to the pane. It re-centres when the side panel collapses to the rail and the pane widens. On a window narrower than about 1300px with the panel open the cap is not reached, and the column takes the width left after the panel and padding. The project page (720px) and the connecting and unreachable views (640px) are centred the same way, so the main pane has one alignment.

Message text renders as markdown: assistant replies, managed or imported, the operator's prompts, and the streaming text of a turn in flight. All three go through one renderer (`ui/src/components/Markdown.tsx`), so a reply looks the same while it arrives and after it lands. Partial input is fine: an unclosed fence runs to the end as code until it closes. Tool results, native events, request payloads and runtime text stay verbatim. The dialect is CommonMark with the GitHub extensions the agents use: tables, task lists, strikethrough and autolinks. There are no footnotes and no math.

Message text is untrusted model output, so the renderer follows four safety rules:

- Raw HTML is dropped, not shown. An HTML block disappears whole. An inline tag disappears, but the text between an opening and a closing tag is ordinary text, so `<script>x</script>` leaves an inert `x`.
- A link keeps its target only for an absolute `http`, `https` or `mailto` URL, and opens in a new tab with `rel="noopener noreferrer"`. Any other link, relative and fragment links included, renders as plain text.
- An image renders as a link to its URL, labeled with its alt text, and is never fetched.
- The output is React elements, never injected HTML, so nothing in a message can make the browser load a resource or run a script.

Headings step down to `h3` to `h6`, so an agent's `#` sits below the page's own headings. Tables scroll sideways inside the column, and long words and URLs wrap. A fenced block shows its language, if the fence names one, and a copy control. A block longer than 40 lines shows only its first 40, by height alone, with an expand control titled "Show all N lines" and, once expanded, a collapse control titled "Show only the first 40 lines". The whole block is always in the page, and Copy always copies all of it. An expanded block stays expanded when its reply lands and is rendered afresh: the page remembers expanded blocks by language and first 40 lines, which are final once a block is long enough to collapse. Syntax highlighting is deferred to a later roadmap card, because it is the piece that would add real weight to the bundle; the two libraries add about 50 KB gzipped. Soft line breaks follow CommonMark, so a single newline inside a paragraph renders as a space.

The UI re-reads the workspace whenever the stream connects or reports a change. Re-reads are numbered and coalesced: at most one is in flight, changes reported meanwhile get one follow-up, and only the newest response sent is applied, so an older response can never bring back a request the service no longer lists. On every reconnect it also fetches the selected conversation's events after the stretch's `through` (`?since=`), only what it missed, so two browsers converge on the service's confirmed state. A fetch that fails is tried again on that connection, after 1 s and then doubling to at most 8 s, with the history's "Loading history:" line saying what it waits for, until one succeeds, the connection changes, or the conversation is no longer the open one. A refusal by a service that has closed is not tried again (see "Shut down" below). A conversation still waiting for its opening read gets it from that read's retry instead. From the moment the stream drops, or a workspace refresh fails, until a refresh sent on the current connection succeeds, runtime state on the page is labeled last known: the header adds `(last known)`, marks dim, an in-flight tool reads `running when last seen` with no motion, the activity line says `Last known:` without its spinner, and elapsed labels stand still. A refresh still out when its connection dropped cannot mark a later connection up to date. A workspace read that fails while the stream is up is tried again, after 1 s and then doubling to at most 8 s, until one succeeds; otherwise nothing would ask again until the service announced a change. `make test` builds and lints it; `npm --prefix ui run dev` serves it on port 5173 against a running service.

The page distinguishes three states of its own knowledge, and shows an empty workspace ("No projects yet.", "Nothing waiting.", and the first page) only when a successful read returned one.

The first page, with no project registered:
- **Where to begin.** "mega runs Claude Code, Codex and pi conversations in the checkouts you register. To begin, press **Register a project**, the folder button at the top of the side panel, and give it a checkout's absolute path."
- **What mega needs.** One short line per harness, from the workspace read's `harnesses`: the build, where it was found and the range in plain words, "Claude Code can run: version 2.1.330, at '…/versions/2.1.330', newer than the 2.1.318 to 2.1.326 mega was tested with." (or "within the" range), or "Codex cannot run: 'codex' was not found on your shell's PATH", the missing ones on the notice tone. Where it was found is the harness's own program (`path`); node and the shim are the start-up log's to name. A found harness older than its range, or whose version could not be read, says "can run: at '…'." with the sentence for it, on the notice tone too. Until the start-up check has run, it says it is looking for them.
- **Where it looked.** It says the harnesses are looked for in the shell's environment as a project with no activation of its own gets it, and that a project's page says what its own environment is missing.
- **Words on the controls.** While there is no project, Register carries the word "Register" beside its icon. While the workspace has no conversation, a project's New conversation carries "New conversation".

The page's states of knowledge:
- **Never loaded.** Before the first successful workspace read, the page knows nothing and says so. It is connecting until a read or the stream fails. It is then unreachable when nothing answered: the stream is down, or the read reached no service. It is unreadable when the service answered the read with an error.
  - The main column says "Connecting", "The service is unreachable", or "The service could not read the workspace", naming the address it is trying (the one the page was served from) and that it keeps trying. The error shows below.
  - The side panel's needs-you and projects sections each say "Not known yet: connecting", "Not known: the service at … is unreachable", or "Not known: the service at … could not read the workspace". Register waits, disabled, and the footer reads "Unreachable, retrying" or "Read failed, retrying".
  - The rail's count reads `?` with a dashed outline, not zero. Its connection dot is red when unreachable or unreadable, and an empty ring while connecting.
  - The retry is the same in both failing states.
  - Below that it lists what the page is waiting for, one line each: the stream (`the stream at ws://…/api/stream · 12s · attempt 4 · last error: the connection closed (code 1006)`) and the workspace read (`GET /api/workspace · 3s · attempt 3 · last error: …`). Each is timed on a clock that keeps going while the page is stale. Once the workspace has been read, the footer's connection label carries the same line as its title while the stream is down or a read is failing.
  - Recovery needs no reload: when the stream connects and a read succeeds, the workspace appears.
- **Loaded and current.** What the service last confirmed, as everywhere above.
- **Loaded but stale.** Everything the page last read, labelled last known, as described above, until a read on the current connection succeeds.
  - **Catching up.** After a reconnect, the stream is up before the workspace read on it has landed. Until it lands, the footer says "Catching up" and the rail's connection dot is an empty ring, never "Live" or the filled dot; nor does either say a newer mega is running, which only a current read can tell. On a first load the same moment says "Connecting". Live is only for a connected stream whose workspace read has landed with no other queued behind it: a change announced during that read queues another, and the page is caught up only once a read lands with none waiting. Both are `connectionOf` in `ui/src/stream.ts`.
  - **Requests are held.** A docked request's answers are disabled, with the card saying "Held until the page has caught up with mega: what it shows is only last known, and an answer waits for the workspace to be read again.", and the allow keys answer nothing, as the mode, model and effort controls are already held while stale. Once the read lands, the cards are answerable again, from the pending set it brought.
  - **A stop holds what would let work go on.** While an interrupt or a release is under way (`interrupting`, or `stopping`), a docked request's Allow, Allow for the session and a question's Answer are disabled, and the card says "The turn is stopping, so answers that would let work go on are held. Deny or Dismiss can still be pressed." Deny and Dismiss stay live. The allow keys answer nothing. The service refuses those answers then too.

The shutdown gate shows in these phases:
- **Unarmed.** The side panel's footer holds a power control, "Shut down when every agent is idle", which arms the gate. It is disabled until the page has a current workspace. The press also asks for notification permission, once.
- **Armed, waiting.** A banner across the top of the main column, sticky as it scrolls, says "Waiting to shut down" with counts by kind. Below that it names each conversation in the way, each name a link that opens it, with what holds it: "a request for you to answer" (marked, since nothing else clears it; the turn it holds open is not named again), "a turn in flight", "N background jobs", or "starting". The footer shows the same counts and names above its row, with Cancel. The rail shows a power badge with the number of conversations in the way, their names and kinds in its title; a press expands the panel. Send, Start, New conversation and Adopt a session are disabled, with the pending shutdown as their title, and so is the reply box's placeholder. Every page sees the same, since the gate is the service's.
- **Idle.** The banner becomes "Every agent is idle", with Shut down and Cancel, and the footer and rail say so too. Each page marks its tab title "Ready to shut down · mega · fortyfive" and raises one browser notification, titled "mega · fortyfive", when the gate turns idle while it watches. A page opened on an idle gate is already showing it, so it raises none. The gate keeps holding until the operator chooses.
- **Last known.** While the page shows only what it last read (the stream down, or a read failed), the banner, footer and rail prefix the gate with "Last known:". Shut down is withheld and Cancel disabled, and the tab title loses its ready mark. A notification is raised only from a current read. All of it returns once a read on the current connection succeeds.
- **Shut down.** The page that asked shows "Shutting down" while runtimes are released and its workspace is current, then, once it has heard the stream's `shutdown_finished`, "mega was shut down from this page at" the time, in the service's zone (below), says it keeps trying, and its footer and the rail's dot read "Shut down from here, retrying". A page that asked but lost contact without hearing it claims no more than it saw: "A shutdown was asked for from this page at" the time, "and contact was lost", that mega did not say whether it finished, and that it keeps trying; its footer and the rail's dot read "Shutdown asked, contact lost, retrying". Its controls give that as their reason, and the expected failed reads are not shown as errors. It recovers by itself: the first workspace read that finds that gate gone clears it: unarmed, or armed afresh with another `armed_at`, which only a new service can show. A new service armed from another page is shown as its own gate, never as the old shutdown. Back in touch before that read lands, it does not report the old shutdown as under way: the banner says a shutdown was asked for from this page, and that the page is reading the workspace, which says whether that shutdown is still under way. Other pages show the service gone as any loss of connection does: last known, "Reconnecting". A workspace read or a reconnect's catch-up refused as `unavailable`, which the closed service answers in the moment before it stops, is the shutdown and no failed read: a page keeps what it last read, its shutdown banner included, shows it as last known, and shows no read error. A refused catch-up ends the connection as a dropped stream does, so a workspace read sent on it cannot mark the page current.

The page's mark is the hub: one gold centre with five light points around it, on the dark tone, for many agents and one operator. It is `ui/public/favicon.svg`, linked from `ui/index.html` as `image/svg+xml`. Its proportions are set to read at 16 pixels, where each point lands as a clean two-pixel dot clear of the centre. The tab has two states:
- **Nothing needs you.** The mark, and the title "mega · fortyfive", the mega's name after the product's (above).
- **Something needs you.** While the needs-you list is not empty, the mark inverts: `ui/public/favicon-needs-you.svg`, the same mark on the notice gold with a dark centre and points. The title gains the count, "(2) mega · fortyfive". The list holds requests and unread output alike, so an answered request still counts until its reply is read.

The page swaps the icon link between the two as `data:` URLs built into its bundle, so a swap fetches nothing. The shutdown gate's "Ready to shut down · mega · fortyfive" title takes precedence while it applies; the icon still follows the list. While the page shows only last-known state (the stream down, or no read yet), it shows the plain mark and no count, since neither can be said to be live.

PNG renderings of both states, for the daemon's tray and desktop integration, are checked in under `cmd/mega/`: `desktop-icon-{32,48,192,512}.png` and a 128-pixel `tray-icon.png`, each with a `-needs-you` twin. `cmd/mega/render-icons.mjs` renders them through headless Chromium, and `cmd/mega/icons.md` records the command. They are renderings of the SVGs, never edited by hand.

## Not built, and what to watch

- Refinements named but not built: SQLite if queries outgrow scanning a file (the registry stays a readable file regardless); contract-first generation of the API and its TypeScript types once the surface settles; one shared Codex app-server per environment, which would also allow live `codex --remote` attach.
- Deferred by the spec: pi, per-turn runtimes, suspension, the re-entry briefing, the central application, and more than one environment. The UI has no side-by-side view, no themes, and no mobile layout.
- Each Codex conversation costs an app-server process. That is fine for a handful; the shared server is the answer when it is not.
- A version change shows in the conversation header, which carries the harness version each runtime reported at its start.
- Mega does not support working a session in a terminal while a conversation holds it. The rule for the operator is to leave the session alone outside mega to keep it intact inside mega. Nothing detects a terminal holding a session, and resuming a Claude session that a terminal still has open forks its transcript silently.

## Tests

`make test` runs the shim's protocol test against a fake SDK, the Go unit tests, and the UI lint and build. It never starts a browser.

`make checks` runs the browser checks in `checks/`, each suite a Playwright script against its own scratch service, using `shim/claude/fake/shim.mjs` in place of the shim so they cost no model turns. It is its own target, run by hand, and `checks/README.md` says what each suite covers. The suites are `conversation`, `dialogs`, `environment`, `firstrun`, `panel`, `readme`, `requests`, `shutdown` and `side`; `make checks SUITE=<name>` runs one. Playwright is pinned in `checks/package.json`, and `make checks-browser` installs its Chromium once. A missing browser stops the run with that command and exit status 3, before any service starts. `checks/lib/mega.mjs` is the plumbing every suite shares. It builds or takes the binary and empties the suite's scratch directory under `$TMPDIR/mega-checks/<suite>`. It writes a config pointing at the fakes, with `environment.shell` `/bin/bash`. It starts the service on 18470 (or `MEGA_CHECK_PORT`, never 6342, the default, nor 8470, the old one, which a mega not yet restarted may still serve) with `HOME` and the XDG directories in scratch, and stops it with SIGINT. Its scratch `HOME` has a `.profile` putting the check's `node` on `PATH`. Since project environments resolve through a login shell from that `HOME`, no project reads the operator's shell start-up files or Claude settings. Each project it registers gets an override activation setting `CLAUDE_CONFIG_DIR` to scratch, unless the suite tests the project's environment itself. The scratch Claude settings, there and in the scratch `HOME`, name `effortLevel: medium` and nothing else, so a new Claude conversation copies the list's default model, `medium` and the manual mode. Every wait is on a condition, checked every 50 ms, never a delay. `checks/lib/gen.mjs` appends seeded, generated turns to a scratch log for the long-conversation steps. `checks/lib/scene.mjs` appends hand-written turns for the README's picture, which `make readme-image` makes from the `readme` suite. A scene's tool calls carry the message the fake shim sends for one, built by the shim's own helper, `shim/claude/fake/messages.mjs`, so the Claude protocol stays with the shim.

The fake shim speaks the same frames as the shim, acts on the text of each prompt (`burst`, `drip`, `ask`, `askq`, an `AskUserQuestion` question with two choices, `echo`, `stream`, `tool`, a Bash call that runs for a while before its result, `ask2`, two permission requests at once, `hold`, a turn that starts and says nothing until it is interrupted, `output N`, a Bash call whose result is N lines, and `background N MS`, N backgrounded Bash calls, job i finishing after i×MS with the frames Claude sends and a woken turn, `busy`, a sentence, three tool calls, a reply with a code block, then a permission request, and `actions`, a Bash command of several lines longer than an action's summary keeps, an Edit, and a Bash call that fails), and records its sessions in the directory it runs in; its header says how to set one up. For Codex, `internal/harness/codex/fake/codex` stands in for `codex app-server` when a scratch service's `codex.binary` points at it. It speaks the subset of the app-server protocol the adapter uses, with the frames codex-cli 0.166.0 sends, and acts on the turn's text: `mcp TEXT` raises an MCP tool approval, `form` a typed form, `actions` a long command, a file change and a command that fails, `background MS` a command left running as a terminal session that completes MS after its turn, `askq` a question in the agent's message whose turn waits for a steer, which it answers and then ends the turn, `askq lose` the same question with the fake exiting on the steer without replying, `late-search` a reply of `ok` and its turn's end, then a web search of that turn reported after its end, `late-stream` streaming text for the turn before and for its own while its own turn waits to be interrupted, and anything else replies `ok`. It appends each `turn/steer` it receives to `steers.jsonl` beside its thread store. It pages `thread/list` as 0.166.0 does: at most 100 a page, and under `created_at`, its default, a cursor of the last thread's second that skips the rest of that second. It lists two models and a hidden one, names `fake-large` at `medium` in `config/read`, and reports a turn's model or effort override with `thread/settings/updated`. The fake shim lists `default`, `fake-opus`, `fake-sonnet` and an effortless `fake-haiku`, reports the resolved model in `system/init`, and answers `set_model` (refusing an id it does not offer) and `set_effort`. Its `fallback MODEL` turn reports MODEL in that turn's `system/init` in place of the model requested, as Claude falling back to another model would, so a turn's line can be seen to name both. It sends no `system/init` until a prompt starts a turn, as Claude does, and run with `--idle` it reports `ready` instead, as the shim does. It reports the Claude Code version a file named `claude-version` in its directory holds, else `fake`, so a check can start a runtime inside or outside the tested range. The fake Codex is laid out as a whole package, with `codex-package.json` and a `codex-code-mode-host` beside it, and answers `--version` with the manifest's version, 0.166.0. `internal/harness/claude/fakebuild` stands in for a native Claude Code build: built into a versions folder, it answers `--version` with the version its file is named for, links followed, so one run through a link says the build the link names, and nothing else.

The fake pi, `internal/harness/pi/fake/pi`, stands in for `pi --mode rpc` when a scratch service's `pi.binary` points at it, and the pi adapter's Go tests run it through node. It speaks the subset of pi's JSONL RPC the adapter uses, with the records pi 1.5.2 sends, writes session files as pi does, and acts on a prompt's text:
- `ask` is a bash call gated by an extension's select;
- `choose`, `confirm`, `input` and `editor` are the other dialogs;
- `timed` is a select that expires;
- `hold` is a call that runs until it is aborted;
- `fail` is a failed response, `notify` a notification, and `echo TEXT` a reply;
- `actions` is three tool calls: a bash command of several lines, longer than an action's summary keeps, a read, and a bash call that fails.

Like pi 1.5.2, a pending dialog holds an abort until it is answered or dismissed, and holds the process through its input closing and a first SIGTERM. It offers `fake/large`, which takes thinking levels, and `fake/small`, which takes none. The browser checks' scratch services name it in `pi.binary`, since node's directory, where a real pi may live, is on their `PATH`.

Both fakes report MCP servers, shaped as each harness shapes them (capability report, 2026-11-12):
- **The fake shim** answers `mcp_status` with three servers. `fixture` is `pending` at the first ask and `connected` after, with two tools by name and no description, as Claude gives none. `notes` is a claude.ai connector that is `needs-auth` until a turn whose prompt starts `mcp-sign-in`. `broken` has `failed` with an error. Its `system/init` lists the three with their statuses.
- **The fake Codex** announces each server's startup with `mcpServer/startupStatus/updated` on `thread/start` and `thread/resume`. It answers `mcpServerStatus/list`, for the thread's own id only, with three servers: `fixture`, connected, with two described tools; `docs`, `authenticationRequired` until an `mcp-sign-in` turn; and `broken`, failed with a `toolsError`.

The adapters' MCP tests use recorded answers: the Claude adapter's from the spike's `mcpServerStatus()` replies, and the Codex adapter's from its `mcpServerStatus/list` reply, both under `testdata/`. The fake Codex needs nothing for a start: `thread/resume` with no `turn/start` holds the thread idle. The service is tested against a fake harness whose request numbers restart in every runtime; the Codex adapter against hand-written JSON-RPC frames over an in-memory wire. The Claude trust tests put their checkouts under the user cache directory, because codex 0.166.0 creates an empty `/tmp/.git` while any of its sandboxed commands runs on the machine, which would make every checkout under `/tmp` resolve to it as a git root.

`make e2e` runs `internal/e2e` with the real harnesses and the operator's logins, and is run by hand. Each test takes its fixture checkout from `MEGA_E2E_CLAUDE_FIXTURE` or `MEGA_E2E_CODEX_FIXTURE` and is skipped when that is unset; `internal/e2e/doc.go` says what a fixture holds, and `AGENTS.md` records the operator's values. `make e2e` also reads those settings from `e2e.local.mk`, an optional, git-ignored file of make assignments beside the `Makefile`, and passes on only those set, so a value in the environment still wins. Claude Code is what mega runs by default, `config.DefaultClaudeExecutable`, found as mega finds it, unless `MEGA_E2E_CLAUDE` names another, so the round trips cannot drift from the product's default. CI never runs them.

- Claude, against `claude-rt1`: an interrupted turn, with its approval pending and never answered, then a release, a prompt in a resumed run (which is when Claude writes "No response requested." to its transcript), a release, and the conversation removed and its session adopted again. The snapshot's speech holds the known replies and not that bookkeeping. The model list through an idle session, and a marker turn launched with `sonnet` at `low` whose `system/init` must report the resolved model. Then a marker turn, a question, a delayed approval, a release that ends in `stopped`, every message of the session's own history found in the log, and a resumed turn that recites every marker. Then, separately, a conversation launched in auto mode whose `sleep` turn, held back by the fixture's `ask` rule, must still arrive as a request raised in auto mode and wait for an answer. And a conversation launched in `default` that is switched to `auto` mid-turn, while its `sleep` approval is pending: Claude must confirm, the live mode must follow from that report, the request must survive and be answerable, and the next turn's `system/init` must report the same mode.
- Codex, against `codex-rt1`: discovery and history with no model turn; the model list and what a new conversation copies from the config, and a marker turn launched with `gpt-6-luna` at `low`, which Codex must report as running, with exactly one `model_changed` event as the turn starts; then a marker turn, a delayed approval for a write outside the checkout, the async question steered into its turn, a clean release, every message of the thread's own history found in the log, and a resumed turn; and a release during a running command, which must report what the sandbox left running. Then a turn that calls the fixture's MCP `echo` tool (`mcp/fixture-server.mjs`, named in the fixture's `.codex/config.toml`): the approval must arrive as a permission card for `fixture/echo` with its parameter, the tool must not run while the card waits (the server logs each call to `mcp/mcp-calls.log`), and it must run after Allow. The discovery test reads the fixture's newest thread and expects a user and an assistant message in it, so a probe that leaves an interrupted thread newest in `codex-rt1` makes it fail until a complete one is newer.
- Each harness, an idle model switch: a released conversation started with no prompt has its model switched to another listed one, which must leave it idle, with no message and no turn recorded over five seconds. The next prompt's turn must ask for the new model and run on it. Claude confirms the switch at once, and its echo arrives as a native event; Codex stores it for the next prompt; pi applies it at once. An interrupt with the gate pending records what it waits on and ends only once the dialog is dismissed.
