# Roundhouse as built

This describes what exists now: the whole first slice, whose work order was retired when its last stage gated (git history holds it; the spec is `docs/future/roundhouse.md`). That is the environment service with projects; Claude Code and Codex conversations launched, prompted, answered, interrupted, released for a terminal, and resumed; native sessions discovered and adopted; and attention, with a needs-you list, reading positions, and a next-waiting shortcut. Polish since then: conversations can be removed, and a conversation opens at its latest activity.

## Shape of the code

One Go binary, `roundhouse`, in the module `git.hq.quigley.com/research/roundhouse`, with `github.com/michaelquigley/df/dl` for logging and `df/dd` for YAML and JSON. Both the product name and the module path are provisional: the repository moves to the `products/` tree when the name settles, so the name stays out of data and identifiers, except the binary and the XDG directory names, which are a single-constant rename. TypeScript appears only in the Claude shim and the UI.

```text
cmd/roundhouse/          cobra root; serve (the default) and version
internal/config/         roundhouse.yaml; defaults; path expansion
internal/model/          Project, Conversation, Event, Request, attention states; no I/O, no protocol
internal/registry/       registry.yaml, ids, the synced atomic write, the data-directory lock
internal/events/         the per-conversation event log
internal/durable/        SyncDir and a parent-syncing MkdirAll
internal/harness/        the Harness, Runtime and Sink interfaces, and a fake for tests
internal/harness/claude/ the shim process, its protocol, mapping, history, discovery, trust
internal/harness/codex/  the app-server child, JSON-RPC, mapping, questions, MCP elicitations, history,
                         discovery, and a fake app-server for browser checks
internal/service/        the single authority: registry, logs, runtimes, pending sets, attention
internal/server/         the HTTP API, the stream, the embedded UI
shim/claude/             the Node shim, its pinned SDK, its test, and a fake shim for browser checks
ui/                      the Vite, React and TypeScript UI, with no state library and plain CSS;
                         react-markdown and remark-gfm, pinned, render message text;
                         Source Serif 4 and Nordwand Mono are embedded
```

Dependencies point inward. `server` depends on `service`; `service` on `harness`, `registry`, `events` and `model`; the adapters on `model` and `harness` only; `registry` and `events` on `durable`; `model` on nothing. Everything protocol-shaped (SDK messages, JSON-RPC methods, the shim's frames) lives inside its adapter package or the shim.

## Running it

`make` builds the UI, installs the Claude shim's pinned dependencies (`npm ci` in `shim/claude`), and installs the `roundhouse` binary into the project's `GOBIN`, stamped with the shim's location in the checkout. `roundhouse` (or `roundhouse serve`) runs the service; `roundhouse version` prints build information. `make clean` removes only what the project builds: `ui/dist`, `ui/node_modules`, `shim/claude/node_modules`, and the binaries in the project's `GOBIN`. `--config PATH`, `--data DIR` and `--verbose` apply to both forms.

| Item | Default | Override |
| --- | --- | --- |
| Config file | `$XDG_CONFIG_HOME/roundhouse/roundhouse.yaml` (`~/.config/...`), optional | `--config`, which must exist |
| Data directory | `$XDG_DATA_HOME/roundhouse/` (`~/.local/share/...`) | `data` in the config, then `--data` |
| Listener | `127.0.0.1:8470` | `listen` in the config |
| Node | `node` on `PATH` | `claude.node` |
| Claude shim | `shim/claude` in the checkout `make` ran in | `claude.shim` |
| Claude Code | `~/.local/share/claude/versions/2.1.318` | `claude.executable` |
| Codex | `codex` on `PATH` | `codex.binary` |

```yaml
listen: 127.0.0.1:8470
data: ~/.local/share/roundhouse
claude:
  node: node
  shim: ~/Repos/q/research/roundhouse/shim/claude
  executable: ~/.local/share/claude/versions/2.1.318
codex:
  binary: codex
```

The executable defaults to 2.1.318 because the shim pins Agent SDK 0.3.318, which was matched against that build; `claude` on `PATH` may be newer.

`listen` must be a loopback address; the service refuses to start otherwise, because this slice has no login. The service binds its port before reading any data, so a second instance on the same port exits without writing. It then takes an exclusive hold on `<data>/lock` before loading the registry, so a second instance on another port that shares the data directory also exits, and the directory has one writer. The hold is released by the kernel when the process exits; the file itself stays.

## Data

The data directory holds `registry.yaml`, the authority for projects and conversations, and `conversations/<id>/events.jsonl`, one append-only event history per conversation. Only the service writes either, and only removing a conversation or a project deletes a log. Both are private to the operator (mode `0600`, directories `0700`).

The registry is plain YAML, readable with the service stopped. It is written to a temporary file, synced, and renamed, and the service's in-memory state only advances once that succeeds, so what a browser sees is what a restart would read. A registry with an unknown `version` is refused rather than guessed at. If the directory sync after the rename fails, the change was never confirmed: memory keeps the last confirmed document and reads continue, the condition is logged once at error level, nothing is announced to browsers, and every later change is refused as `unavailable` with `registry durability uncertain after a failed directory sync, restart required`. The file may hold that one unconfirmed change until a restart reads whatever reached the disk. A failure before the rename changes nothing and can be retried. Every directory the service creates under the data directory, including the data directory itself, has its parent synced, so a new workspace or conversation cannot vanish in a crash while its synced contents would have survived.

An event log assigns each event the next `seq`. An append returns only after the line is synced, and a failed write or sync is truncated back with the `seq` unchanged, so an event a browser has been sent survives a crash. If that truncate also fails, the log keeps serving every confirmed event, since reads never go past the confirmed length, but refuses every later append with `event log durability uncertain after a failed rollback, restart required`, logged once at error level. The leftover bytes stay on disk until a restart reopens the log, where an unterminated remainder is dropped as a torn tail. Creating a log also syncs the directory that names it. Only completed events are logged; streaming text is never written, so this costs a few syncs per turn. On open, an unterminated final line is a write torn by a crash and is dropped; any other unreadable line stops the open and leaves the file alone.

An event is `{seq, at, kind, origin, text, native_id, status, tool, tool_use_id, req, facts, raw}`. `kind` is `runtime` (with `status` starting, started, not_started, stopping, stopped, unsupervised, resuming, resumed, error, mode_changed or model_changed; a `started` event carries the runtime's `facts`: session, model, effort where the harness reports it (Codex), version, permission mode, whether that mode was inherited, cwd; a `mode_changed` event carries the new permission mode; a `model_changed` event carries the model, and for Codex the effort, as the harness reported them), `user`, `assistant`, `tool_use`, `tool_result`, `request`, `request_resolved`, `turn_end` (`status` success, error or interrupted), or `native` (anything else the harness emits, kept in `raw`). `origin` is `managed` for what a runtime managed by the service produced, `native` for what an import read from the harness's own history, and `service` for the service's own bookkeeping. `native_id` is the harness's identity for the message an event came from; an event whose `native_id` the log already holds is never recorded again, which is how an import adds only what is missing.

`text` is recorded whole for user prompts, assistant text, tool results and native events, in both adapters. The one bounded text is a `tool_use` summary line, such as `Bash sleep 3` or `shell printf x > f`, which is a title: it is cut at 200 bytes, on a character boundary, with an ellipsis, and the full call stays in `raw`. Logs written before this cut every `text` at 4000 bytes, and they are not rewritten: events already recorded keep their clipped `text`, with the whole message in `raw`.

## Conversations and runtimes

A conversation is bound to one native session. Launching starts a runtime for a new session, records the session id, and sends the opening prompt. A conversation holds exactly one native session for its whole life. A harness may only reveal the id after launch (Codex always does), so a session the conversation created is held in memory until the registry has it, and is seeded from the log's last `started` event when a conversation is opened. The next launch saves it in the same registry write that records the runtime running, and resumes it; if that write fails, the launch is refused. A fresh session starts only on proof that none exists: the log shows no earlier launch, or every earlier `starting` was followed by a recorded `not_started`, the status of a launch that failed before any session could exist. Only the adapter can know that, so a launch error records `not_started` only when it wraps `harness.ErrNotStarted`, which each adapter applies at the failure sites it can prove came first: for Claude, failing to start the shim; for Codex, failing to start the app-server, a failed `initialize`, or an explicit JSON-RPC error reply to `thread/start`. The service's own failures before any process starts (the registry write, an unknown harness) also record `not_started`. Anything unclassified, such as a timeout or a lost connection while `thread/start` was outstanding, records `error` and counts as session unknown. Any other conversation with no known session refuses prompts and says so, pointing at "Adopt a session" to pick the orphan up into a new conversation; a resume does not lift that. The accepted cost is a conversation whose launch failure itself could not be recorded: it stays refused although no session exists, which is the closed side of the failure. Every later runtime resumes exactly that id; nothing picks a session by recency, forks one, or starts a fresh one in its place. A runtime that reports a different session than the one it was launched for is recorded as an error and stopped.

Runtimes are long-lived: a runtime starts at launch, or with the first prompt after an adoption, a release, a clean restart or a resume, and stays up between turns until the operator releases it, the service stops, or the harness exits by itself. There is no per-turn mode and no suspension operation; restarting the service is the way to put everything down. The service never looks for or kills processes it did not start, or ones it lost track of: an orphaned runtime after an unclean restart, or a sandboxed command that outlived Codex, is reported, not stopped.

The registry records each conversation's `runtime` as the service last confirmed it: `none`, `running` (written before the process starts), or `unsupervised`. The service also reports transient states: `starting` until the runtime reports the session it holds, `stopping`, and `resuming` while it reads native history.

Every change to the displayed runtime state is a recorded `runtime` event, and the change is shown and announced only once that event is recorded. If the log cannot record it, the last confirmed state stays on screen. Whatever the change does to the process happens anyway: a release, a shutdown, or the stop of a runtime bound to the wrong session still stops the process, because a storage fault must never trap a running agent, and the next start settles what the log could not record. There are no exceptions: a launch that failed shows no runtime once its `not_started` event is recorded, and if the log cannot record it, the last confirmed `starting` stays on screen, the conversation stays recorded `running` so a restart settles it, and the log's refusal of later writes (`unavailable`, restart required) is what tells the operator. Operations are guarded internally, apart from what is displayed, so a start or a resume that ended unrecorded never blocks the next one, and a runtime is asked to stop at most once, however many releases or shutdowns ask.

- **Prompt** records the text as a `user` event with a service-minted uuid and passes that uuid to the harness, which records it as the message's identity (observed with Agent SDK 0.3.318), so an import recognizes the prompt. One turn at a time: a prompt while a turn is in flight is refused. A prompt to a conversation with no runtime first imports native history, then resumes the session by its id.
- **Requests** (a permission or an `AskUserQuestion`) get a service-minted id, unique across every runtime the conversation has had, and join the conversation's pending set, which lives only in memory. The harness's own request id stays inside the adapter, so a stale card can never match a newer request that reused a native number (Codex's restart at 0 for every app-server). A request ends `answered`, `aborted` (the harness settled it, or its runtime exited), or `lost` (the service restarted while it was pending). An answer takes the request out of the pending set before it is delivered, so the first answer from any browser wins and every later one gets `not_pending`. An answer the harness has already settled, for example on an interrupt, also gets `not_pending`. A denial without a reason is sent as `the operator denied this in roundhouse`.
- **Interrupt** stops the active turn; the harness aborts any pending request.
- **Permission mode** (Claude only) is the operator's choice for the conversation: `default`, `auto` (a classifier approves routine calls), `acceptEdits` or `plan`. The bypass modes, `bypassPermissions` and `dontAsk`, are never offered, and the service refuses them. The choice is made at launch and recorded on the conversation, and every later launch passes it again, so it survives a release, a resume and a restart. A terminal visit never changes it.
  - An empty choice is roundhouse's own default. If the operator's Claude settings name a `permissions.defaultMode`, no mode is passed and Claude inherits that one, and the header says "inherited". Otherwise `default` is passed explicitly, because Claude's own fallback when no mode is given may become `auto` in a later version. The settings are read, never written, the way Claude Code 2.1.318 resolves them for a session in the checkout (observed; capability report, 2026-11-09). Highest precedence first:
    - managed settings (`/etc/claude-code/managed-settings.json`);
    - `.claude/settings.local.json` at the git repository's root, then the checkout's own;
    - the checkout's `.claude/settings.json` (never the repository root's, which Claude does not read for a session below the root);
    - the user's `settings.json` (`$CLAUDE_CONFIG_DIR`, else `~/.claude`).

    The local file stays in the checkout instead of the root when the checkout is outside a repository or is a worktree (Claude would use the main checkout's root, which roundhouse does not resolve), when the root is the home directory, or when the root, its `.git` or its `.claude` belongs to another user. `auto` and `bypassPermissions` named in a project or local file are skipped, as Claude ignores them there. The lookup then continues to the lower layers. That is an assumption, not an observation: what Claude does when a project file names `auto` and the user's settings name another mode was not probed. An unreadable layer is skipped with a warning. Any remaining difference from Claude's own lookup can only fail toward the manual mode: roundhouse then finds no mode Claude would find, and passes `default` explicitly. It never passes nothing where Claude would find no mode, which would leave the choice to Claude's fallback.
  - The operator can set the mode for any Claude conversation that is not unsupervised. One that is starting, stopping or resuming is refused until it settles. With no runtime, the choice is all there is to change: one registry write, no harness call and no runtime event, with the outcome `stored`. There is no live mode to report, and the next launch's `system/init` is the report.
  - While the runtime runs, the request is intent: the choice is written on the conversation first, as the mode the next launch passes, and then the harness is asked. The reply carries the harness's answer, and the service records no mode change of its own:
    - confirmed: Claude has switched, and the adapter has already reported it;
    - refused: the choice goes back to its previous value, which may be no choice at all, in one registry write;
    - unconfirmed: Claude did not answer within 30 seconds; the choice stands, the live mode is whatever Claude last reported, and the header shows the two apart.

    One switch runs at a time. The new mode applies from the next tool call, even within the turn in flight. A pending request stays pending and answerable; nothing in a switch touches the pending set.
  - The live mode has exactly one writer: what the adapter reports, in the order Claude reported it. That covers a confirmed switch (reported before the switch call returns), a confirmation that arrives after the timeout, and a different mode in the `system/init` that Claude re-sends at the start of every turn, such as plan mode being left. Each is a `mode_changed` runtime event, recorded through the same transition as every other state change, and shown only once recorded. None of them changes the recorded choice. A report the log cannot record leaves the last confirmed mode on screen, as any unrecorded transition does; nothing switches the harness back, and a restart settles it.
  - In auto mode, the requests that still arrive are the residue: calls that a checkout `ask` rule holds back, or that the classifier did not approve on its own. Each request's payload carries the mode it was raised in.
- **Model and effort** are the operator's choice for the conversation, for either harness, recorded beside the permission mode and passed on every launch of it, so they survive a release, a resume and a restart. An empty choice inherits the operator's own settings. For Claude nothing is passed. For Codex the config's current values are passed, read afresh at every launch and every turn, because Codex keeps a thread's last override and passing nothing would keep it. The model lists come from the harness and are cached per harness for the service's life, with the version they came from; asking for them starts no conversation and costs no turn (capability report, 2026-11-10). A launch or a change is checked against the cached list when there is one: a model the harness does not offer, or an effort the chosen model does not take, is refused as `invalid`. What inherit means is read afresh on every ask. For Claude it is the first `model` and `effortLevel` in the same settings layers the permission mode reads. Per-model `modelSettings` overrides and environment variables are not read, so this is what the settings files name, not necessarily what Claude runs, and the UI labels it that way. For Codex it is its own effective config for the checkout through `config/read`, which can differ from the catalog's `isDefault` model.
  - With no runtime, a change is stored and nothing else, with the outcome `stored`, and inherit can be chosen.
  - While the runtime runs, the choice is intent, written first as it is for the permission mode, and for Claude inherit cannot be chosen again once left; that is refused as `invalid`, because Claude's reset calls go to Claude Code's built-in defaults, not the operator's settings. Codex can return to inherit while running: its adapter sends the config's current values on every turn, so inherit is stored and applied at the next prompt like any other Codex change, and the header shows "next prompt: inherit". The one Claude exception is a model that takes no effort level (Claude's `claude-haiku-4-5-20251001`), which leaves the effort unchosen. Claude switches at once through the SDK (`setModel`, then `applyFlagSettings({effortLevel})`, each sent only if it differs) and the outcome is `confirmed`, `refused` (the choice goes back) or `unconfirmed` (no answer within 30 seconds; the choice stands). If Claude accepts the model and then refuses the effort, the outcome is `refused`: the new model stays the stored choice, the stored effort reverts to the last accepted one, and the header shows what Claude reports. Codex takes a model and an effort per turn, so the change, inherit included, replaces the stored choice for the next `turn/start` and nothing is sent now, with the outcome `next_prompt`. One change runs at a time, sharing the guard with the permission mode.
  - A change asked for while running is shown as the next prompt's until a turn begun after it ends; a release drops it, since the next launch passes the stored choice anyway.
  - The live model has one writer: the harness's report. Claude reports the resolved id (`claude-sonnet-5-5` for `sonnet`) in the `system/init` it sends at every turn start; the first is the `started` fact, and a later one with another model is a `model_changed` event. Codex reports the model and effort in the `thread/start` or `thread/resume` response, and both again in `thread/settings/updated` when a turn's override takes effect, which is a `model_changed` event. Claude never reports effort on the stream, so its effort is only ever what was requested.
  - A Codex override persists in the thread, across later turns and `thread/resume` (capability report, 2026-11-10). That is why inherit sends the config's values: a thread that ran an explicit choice and is set back to inherit returns to the config at its next launch and turn, and follows later changes to the config.
- **Release** is the terminal handoff. If a turn or a request is outstanding it interrupts first, then closes input, and the conversation shows `stopping` until the process is seen to exit, when it records `none`. Claude Code 2.1.318 exits with status 1 when input closes after an interrupted turn; a requested release with no turn in flight is still recorded as `stopped`, with the status in the text. An exit nobody asked for, or one in the middle of a turn, is recorded as `error`.
- **Resume** imports native history, appending what the log lacks (for example turns made in the terminal) as `native`-origin events, records `resumed` with how many it added, and clears `unsupervised`. It starts no runtime; the next prompt does. A resume whose `resuming` event cannot be recorded is refused before anything is read.
- **Shutdown** (SIGINT or SIGTERM) releases every runtime the same way and waits up to 30 seconds for each to exit. Each that exits records `none`; any still running stays `running`.
- **Start** settles the previous run without replaying anything: every request the log shows unresolved gets `request_resolved` with outcome `lost`, and every conversation still recorded `running` gets a `runtime unsupervised` event and becomes `unsupervised`, because its runtime was never seen to exit and may still be working. Its history is not imported until the operator resumes it, and prompts are refused until then.

**Remove** takes one conversation out of the workspace. It is refused as `conflict` while the conversation has a runtime in any state: starting, running, stopping, resuming, or unsupervised, and also while a stop the log could not record leaves it recorded `running` until a restart settles it. An unsupervised conversation is resumed first, because its orphaned runtime may still be working. Removal deletes Roundhouse's own history and reading state for the conversation and nothing else: the checkout and the native session stay, and discovery offers the session for adoption again. The order is fixed. The registry write comes first and memory follows it once confirmed; the conversation's log directory (`conversations/<id>/`) is deleted only after the registry no longer names it, and its parent is then synced. A crash between the two leaves an orphan directory, never a registered conversation without its log. A directory that cannot be deleted is logged at error level and left behind the same way, and the removal stands.

Removing a project applies the same rules to every conversation in it. It is refused as `conflict`, naming the conversation, while any of them has a runtime in any of those states. The project and its conversations leave the registry in one confirmed write, and only then is each conversation's log directory deleted, in the same order and with the same failure handling as a single removal. The checkout and the native sessions stay.

## Attention

Attention is computed from confirmed facts every time the workspace is read, and never stored. In order:

- `request` when a question or approval is pending;
- `unsupervised` when the service restarted without seeing the runtime exit, an uncertain state never shown as running or idle;
- `running` while a turn is in flight;
- `error` when the last runtime ended badly (an error, an exit during a turn, or a launch that did not start), until a runtime starts or stops cleanly;
- `unread` when `output_seq` is past `read_seq`;
- `idle` otherwise.

`output_seq` advances only on agent output (`assistant`, `tool_use` and `tool_result`) recorded during a turn, and only when that turn ends; output still being produced is `running`. The one exception is output an adapter marks as arriving after its turn ended: a Codex background command finishing. With no turn coming to end it, it advances `output_seq` as it is recorded, and opens no turn. `native` events never count: they are the harness's own bookkeeping, such as the `system/init` Claude re-sends at the start of every turn, and status and lifecycle frames. They are recorded, and shown behind the native-events toggle, but never create unread. Runtime and request bookkeeping and recovery never advance it. Imported history counts by how the import happened. Resuming after an unclean restart advances `output_seq` to the newest agent output anywhere in the log, cached or imported, because the orphaned runtime may have finished turns nobody saw, including the one it was in when the service died; the reading position then decides whether that output is unread. Output of a turn the harness reports still in progress is left out: `harness.History` names those events, and Codex marks the items of an `inProgress` turn in `thread/read`. Claude's history carries no turn status, so it counts as complete, and resuming beside a live orphan is the operator's hazard the resume text already warns about. Resuming after a release, and adopting, leave `output_seq` where it is, because the operator was the one in the terminal or chose the session. So reading a conversation and then releasing it, restarting the service cleanly, or resuming after a terminal visit all leave it `idle`.

`last_seq` is read from the event log, never stored, so recording an event never rewrites the registry. `read_seq` is the reading position. Reading moves it forward to at most the last event, never back. It acknowledges what was read and nothing more: a pending request stays pending, and `request`, until it is answered. Both registry writes, `output_seq` at a turn's end and `read_seq` on reading, follow the registry's rule that memory moves only after the write is confirmed.

A project's mark in the UI ranks its conversations' attention in a different order: request, unsupervised, error, unread, running, idle. A conversation is `running` ahead of `error` and `unread` because a turn in flight is its current fact. A project ranks what needs the operator above what is merely busy, because its mark answers "does this project need me, and if not, is it busy". The page derives it, and the service computes nothing new for it.

The needs-you order lists every conversation in `request` or `unread`, requests first, then each group oldest first by the time of the fact that put it there: the oldest pending request, or the unread output.

## Discovery and adoption

Discovery lists the native sessions stored for a project's checkout that no conversation holds yet: Claude through the shim's `list` (the SDK's `listSessions`), Codex through `thread/list` on a short-lived app-server. Each session's `preview` is the harness's own (usually the first prompt) and is passed on whole; the adopt dialog shows its first three lines. It never chooses one. Adoption binds the session the operator picked, which must be one discovery lists, to a new conversation, imports its history as `native`-origin events between `resuming` and `resumed` runtime events, and starts no runtime; the first prompt resumes the session by its id. Close any terminal that holds the session first; an idle terminal is still a writer.

## The Codex adapter

Each runtime is a private `codex app-server` child per conversation, driven over stdio JSON-RPC in its own process group, so its lifecycle matches Claude's (a runtime is a child process) and a crash stays local. It starts with `initialize` (client `roundhouse`, `experimentalApi` on) and `initialized`, then `thread/start {cwd, model}` or `thread/resume {threadId, cwd, model}`. The model is the chosen one, or with none chosen, the one `config/read {cwd}` returns at that moment; these calls take no effort (0.166.0 schema). The Go types are written by hand for the subset used, from the 0.166.0 schema checked in under `internal/harness/codex/schema/` with the command that generates it. A turn is in flight from `turn/started` (or the `turn/start` response) to `turn/completed`, whose status becomes the `turn_end` status. It never sends an approval policy, a sandbox, or a config override, so the operator's codex configuration decides them. That includes per-project trust: a trusted checkout gets a workspace-write sandbox, where only a command reaching outside the checkout asks for approval. The runtime reports `started` once the thread starts, with the model and effort, the CLI version, the approval policy and sandbox, and the instruction sources.

- Every `turn/start`, from a prompt or from an answer that starts the next turn, carries a `model` and an `effort`: the stored choice, or for an unchosen field the config's current value, from a `config/read {cwd}` on the runtime's own connection just before the turn. Codex treats each as an override for that turn and the ones after it, so sending them every turn keeps the stored choice true across resumes, and keeps inherit following the config. If the config cannot be read (logged as a warning) or names no value, that field is not sent. A change while running replaces the stored choice and is sent with the next `turn/start`. `thread/settings/updated` is Codex's report of the model and effort it now runs; one that differs from the last report becomes a `model_changed` event.
- The model list comes from `model/list` on a short-lived app-server with no thread, hidden models left out, with the version from the `initialize` user agent. What inherit means comes from `config/read {cwd}` the same way: `model` and `model_reasoning_effort`.

- A command whose `item/started` has no `item/completed` by its turn's `turn/completed` is background work: a terminal session Codex keeps (unified exec). The adapter reports such commands as the background list (`kind` `command`, the command without its `/bin/bash -lc` wrapper, first seen at `item/started`). When the command's `item/completed` arrives, after its turn, it leaves the list and is recorded as the usual tool call and result, marked as after their turn (`AfterTurn`, a signal through the sink, never written to the log). The service opens no turn for them, since none is coming to end it, and counts the result as unread at once. So a background command that finishes, or fails, while the operator is away reads as unread, as a woken Claude turn's reply does. They keep the native identities a history import maps the same item to (the item id, and `id/result`), so a resume after a release records nothing twice. A command detached with `nohup … &` inside an ordinary call is invisible to Codex, so it is not on the list (capability report, 2026-11-10).
- Completed items map to events: a user message to `user` (its `clientId`, the service's prompt identity passed as `clientUserMessageId`, becomes its native identity, so an import recognizes it); an agent message to `assistant`; a shell command, a file change or an MCP call to `tool_use` and `tool_result`; anything else to `native`. Streaming agent text becomes deltas. Other notifications are transport chatter and are not recorded, except `error`.
- Command, file-change and permissions approvals become `permission` requests, mapped by the server's own request id inside the adapter. Allow answers `accept`, deny answers `decline`; a permissions request is granted exactly what it asked for, for the turn, or nothing. `serverRequest/resolved` aborts a request the server settled itself. Codex gives no acknowledgment of an answer, so an answer after that notice is refused as `not_pending`.
- An agent message carrying `questions[]` (the default-mode question, since `requestUserInput` is unavailable in 0.166.0) is also recorded as a `question` request. An answer goes into its turn with `turn/steer` while that turn is active, or starts the next turn if the turn completed with the question unanswered. Interrupt, release, a turn ending `interrupted` or `failed`, and the runtime's exit all abort it.
- `item/tool/requestUserInput`, which 0.166.0 does not send in default mode, is handled if it arrives: it becomes a `question` request answered by question id.
- `mcpServer/elicitation/request` is how Codex asks on behalf of an MCP server (capability report, 2026-11-09):
  - An elicitation whose `_meta.codex_approval_kind` is `mcp_tool_call` is a `permission` request:
    - The approval frame names the server but not the tool, so the tool is named `server/tool` from the `mcpToolCall` item started just before it. If no call is in flight, it comes from Codex's message ("…run tool \"echo\"?").
    - The payload carries the server, the tool, its description, its parameters as Codex displays them, and `allow_session` when Codex offers approval for the session.
    - Allow answers `{action: "accept"}`, and the tool runs.
    - Deny answers `{action: "decline"}`; Codex records the call as failed ("user rejected MCP tool call"). Its response has no field for a reason, so the operator's reason stays in roundhouse's own record.
    - Where offered, "Allow this tool for the session" answers `{action: "accept", _meta: {persist: "session"}}`. Codex then does not ask again for that tool in that thread; another tool on the same server is still asked. No config file changes.
    - "Always" is never sent. Codex would write `approval_mode = "approve"` for the tool into the config file that defines the server, which roundhouse never does on the operator's behalf.
    - Interrupting resolves a pending approval as it does every other approval: the turn ends `interrupted` and `serverRequest/resolved` follows, so the request is `aborted`, and a late answer gets `not_pending`.
  - A typed `form` elicitation of primitive fields (string, number, integer, boolean) and single-select enums is a `question` request. Its payload carries the server's message and the fields, required ones first. Each answer travels as text and is sent as typed `content`, leaving out an empty optional field.
  - Free-schema forms (`openai/form`, `openaiForm`), `url` and `openai/userVerification` modes, multi-select enums, forms with no fields, and frames the adapter cannot read are not answerable. They are recorded like any other unanswerable server request, naming the method, the MCP server, the mode and what was asked.
- A server request roundhouse cannot put to the operator is not answered either way on their behalf. A `native` event says so, and the turn waits until the operator interrupts it.
- Interrupt is `turn/interrupt`. Release interrupts if needed, then closes stdin. At each interrupt and close the adapter notes every process running under the app-server, because the sandbox codex runs commands in starts its own session and so leaves the app-server's process group. After the exit it waits up to 10 seconds for those processes to go. If any are still running, the runtime is recorded as an `error` naming their pids, never as a clean stop. Roundhouse does not kill them.

## The Claude shim

`shim/claude/shim.mjs` is a policy-free bridge between the service and `@anthropic-ai/claude-agent-sdk` 0.3.318, speaking one JSON object per line on stdio. The service runs `node shim.mjs run --cwd DIR (--session-id UUID | --resume UUID) --exec PATH [--permission-mode MODE] [--model MODEL] [--effort LEVEL]`, with the executable from `claude.executable`. Without `--permission-mode`, `--model` or `--effort` the shim leaves that SDK option out, so Claude's own settings decide. `node shim.mjs models --cwd DIR --exec PATH` starts an idle session, asks `supportedModels()` and `initializationResult()`, prints `{version, models}` on one line, and ends input with no prompt sent; the session leaves no transcript and is not listed by discovery. The SDK's optional `claude-agent-sdk-linux-x64` package, which `npm ci` installs, is not used.

```text
shim to service
  {"type":"event","msg":<sdk message verbatim>}
  {"type":"request","id":<requestId>,"kind":"permission"|"question","tool":...,"input":{...},"toolUseId":...}
  {"type":"request_resolved","id":...,"outcome":"aborted"}
  {"type":"answer_accepted","id":...}      the answer reached the waiting request
  {"type":"answer_rejected","id":...}      nothing was waiting under that id
  {"type":"interrupted","response":{...}}
  {"type":"permission_mode_set","id":...,"mode":...}            the sdk switched
  {"type":"permission_mode_set","id":...,"mode":...,"error":...}  it did not
  {"type":"model_set","id":...,"model":...[,"error":...]}
  {"type":"effort_set","id":...,"effort":...[,"error":...]}
  {"type":"error","message":...}
  {"type":"exit","code":N}
service to shim
  {"type":"prompt","uuid":<service-minted message uuid>,"text":...}
  {"type":"answer","id":...,"decision":"allow"|"deny","message":...}
  {"type":"answer","id":...,"answers":{"<question>":"<label>"}}
  {"type":"interrupt"}
  {"type":"set_permission_mode","id":...,"mode":...}
  {"type":"set_model","id":...,"model":...}
  {"type":"set_effort","id":...,"effort":...}
  {"type":"close"}
```

Each `system/background_tasks_changed` (Claude sends one on every change, a whole snapshot down to an empty list) becomes the background list: `task_id`, `description` and `task_type` (`local_bash` for a backgrounded Bash call, `local_agent` for a backgrounded subagent). Each job keeps the time it was first seen across snapshots. The frame is still recorded as a `native` event, as are `task_started`, `task_updated` and `task_notification`. A job finishing after its turn wakes the agent for a turn nobody prompted (a fresh `system/init`, a reply, a `result`), which the service records like any turn the runtime opens. The adapter maps the first `system/init` to `runtime started`, `assistant` messages to `assistant` and `tool_use`, user tool results to `tool_result`, `result` to `turn_end` (`interrupted` if an interrupt was sent in that turn), streaming text to deltas, and everything else to `native`; a subagent's messages are `native` too. `AskUserQuestion` is a `question` request, and every other `canUseTool` a `permission` request. A user message with `is_meta` (or `isMeta`) is not the operator's. It is one Claude added itself, such as a subagent's hand-back, which the history reader synthesizes and the live stream never delivers. It maps to a `native` event named from its `origin` ("meta: hand-back from web-fetch"), or "user/meta" with none, keeping its identity, so an import records it once and shows it only under the native-events toggle. `isQueuedCommand` alone stays a `user` event: a prompt typed ahead while a turn ran. History recorded before this rule is not rewritten. A backgrounded tool keeps the CLI alive after `close` until it finishes, so release has no deadline and shows `stopping` until the exit. `run` starts or resumes a session in the mode the service passes, and with default setting sources, so every approval the mode asks for reaches the operator and the checkout's instructions, hooks and permission rules load as in a terminal. `set_permission_mode` calls the SDK's `setPermissionMode` and reports the result; `set_model` calls `setModel` and `set_effort` calls `applyFlagSettings({effortLevel})`, each replying with the result. The shim chooses no mode, model or effort itself. Each request waits for the service's answer, and the shim confirms every answer as accepted or rejected, so an answer that lost a race with an abort is reported `not_pending` rather than as answered. A request becomes answerable only once its event is recorded. On `close` it waits for an interrupt in flight before ending input, because ending input with a request pending keeps Claude alive for minutes. `messages` wraps `getSessionMessages` and `list` wraps `listSessions`. The service runs the shim in its own process group, so a terminal interrupt aimed at the service does not cut short the orderly release.

A project is `{id, name, checkout, starred, untrusted, inherited_permission_mode}`. `starred` is workspace state: a field on the project in `registry.yaml`, written only through the service (`UpdateProject`, which changes the name, the star or both in one registry write), so a star is the same in every browser. Memory moves only after the write is confirmed, and browsers learn of it through `workspace_changed`. An unstarred project writes no field, and a registry written before stars reads as unstarred, with its version unchanged. A `PATCH` with neither field is `invalid`. In the project, `inherited_permission_mode` is the Claude mode the operator's settings name for the checkout, read on every read like the trust notice, or empty. `checkout` must be an absolute path to an existing directory and may be registered once; an empty `name` becomes the directory name. Removing a project takes it and its conversations out of the workspace and deletes Roundhouse's history and reading positions for those conversations; the checkout and the native sessions stay where they are.

A conversation is `{id, project_id, name, label, harness, native_id, mode, state, turn_active, turn_started_at, attention, read_seq, last_seq, output_seq, model, effort, version, permission_mode, permission_mode_inherited, permission_mode_choice, model_choice, effort_choice, model_next, effort_next, model_next_inherit, effort_next_inherit, pending, background}`, where `pending` is the current pending set as `{id, kind, payload, at}`. `at` is when the request was recorded, its request event's own time, held in memory beside the pending set and never stored. `background` is the work the runtime keeps running outside a turn, each job as `{id, description, kind, started_at}`. It is absent when there is none, and when there is no runtime to ask, which is the case for an unsupervised conversation, whose list is unknown. The adapter reports it whole each time it changes, through the sink's `Background`, never as an event. The service holds it in memory on the live record beside `turn_active`, never stores it, and clears it when the runtime exits, so a restart shows none. It is not attention: background work never puts a conversation in the needs-you list or changes its attention. `kind` is the harness's (`local_bash`, `local_agent`; `command` for Codex). `started_at` is when the adapter first saw the job, since neither harness reports a start time. `turn_started_at` is when the turn in flight began: the time its first event was recorded, a prompt or the first message of a turn the runtime opened itself, such as an answer starting the next turn. It is held in memory beside `turn_active`, never stored, cleared when the turn ends or the runtime goes, and absent when no turn is in flight, so a restart never shows one. `permission_mode` is the running mode, `permission_mode_inherited` whether the operator's settings chose it, and `permission_mode_choice` the recorded choice (empty for roundhouse's default). `model` is the model the harness last reported and `effort` the effort Codex last reported; `model_choice` and `effort_choice` are the recorded choice (absent inherits), and `model_next` and `effort_next` a change asked for while running that the next prompt carries; `model_next_inherit` and `effort_next_inherit` say that change returns the field to inherit (Codex only). A request's payload is plain data for display: `tool` and `input` (plus `title`, `description`, `decision_reason`, `blocked_path` where Claude gives them, and `permission_mode`, the mode it was raised in) for a permission, `questions` for a question. An MCP tool approval adds `mcp_server`, `mcp_tool`, `parameters` (as Codex displays them) and `allow_session`. A typed form question carries `mcp_server`, `message` and `fields`, each `{name, type, title, description, required, options, default}`. `harness` is `claude` or `codex`. Accepted commands answer 202, and their effects arrive on the stream.

The path search lists names in a project's checkout and is read-only: it changes no workspace state and nothing in the checkout.
- **What it lists.** Files git tracks, plus untracked files git does not ignore, from `git ls-files -z --cached --others --exclude-standard` run in the checkout with `GIT_OPTIONAL_LOCKS=0`, so the index is never refreshed. The directories those files imply are added. Ignored files, such as build output and dependencies, never appear.
- **Where git cannot list it.** A checkout that is not a git repository, or where git fails, is walked instead. The walk skips directories whose names start with a dot and stops at 50,000 entries, as the git listing does.
- **Caching.** A checkout's listing is held for five seconds, so typing does not run git on every key, and a file created a moment ago appears within that.
- **Matching.** The query is split into fragments at slashes and spaces. Each fragment must appear, ignoring case, after the one before it. A path whose last fragment can fall in its last segment (a basename match) ranks above one matching only in its directories, then shorter paths come before longer, then by name. An empty query lists the shortest paths.
- **What it never does.** It reads no file's contents. Git and the walk never descend a symbolic link. A path that is itself a link is offered only if it resolves inside the checkout, so nothing outside it is ever named.

Every write is a command to the service, the one writer of the registry and the logs; the server holds no state. A launch runs outside the service's lock, because Codex reports its start before the launch call returns; other operations on that conversation stay refused until it settles, and a runtime that exits while launching is settled like any other exit.

Every other path serves the embedded UI, falling back to `index.html`.

The stream carries `{conversation_id, event}` for each recorded event, `{conversation_id, delta}` for streaming text (never stored), `{workspace_changed: true}` after any confirmed change to the workspace (the registry, a runtime's state, a pending set), and `{heartbeat: <time>}` every 20 seconds so a page can see that a quiet stream is alive. It replays nothing: a client that reconnects re-reads confirmed state. A client that falls 256 updates behind is disconnected rather than allowed to slow the service.

Requests are refused with 403 unless their `Host` is loopback and any `Origin` matches that `Host`. The loopback bind keeps the network out; this keeps out web pages in the operator's own browser, which could otherwise reach `127.0.0.1` through DNS rebinding or a cross-site request.

## The trust notice

`untrusted` is computed from `~/.claude.json` on every read and never persisted, so a terminal visit clears it without a restart. It looks up `projects[<key>].hasTrustDialogAccepted`, where the key is the checkout's enclosing git root, or its real path outside a repository. That mirrors the check Claude Code 2.1.318 uses to gate project permission rules; it is an observation of that version, not a documented contract, and a linked worktree may read as untrusted. A missing file reads as untrusted, and an unreadable one shows no notice and logs a warning.

The service only ever reads this file. Trust is granted by the operator opening the checkout in `claude` interactively.

## The UI

A left column, the side panel, with the needs-you list at the top, then the projects with their conversations, each marked with its attention: a square for a request, a filled red dot for supervision lost, a red ring for an error, a filled dot for unread output, a rotating arc in the accent colour while running, all 11px, and when idle a small grey dot, 5px, centred in the same 11px box so names stay aligned. Nothing moves that is not live: under `prefers-reduced-motion`, and while the page shows last-known state, the running mark is a still half-filled ring. A conversation with a turn in flight shows how long the turn has run after its name, in the tree and in the needs-you list, in the mono register: `45s`, `4m`, `1h 12m`. A conversation waiting on a request shows instead how long its oldest pending request has waited, counted from that request's `at`, since on a row waiting for the operator the number reads as the wait. One timer serves every label on the page, ticking once a second while any shows, so a label can trail real time by up to a second; it stands still from the moment the page goes stale. Background work changes how a conversation looks, never its attention. Selecting a conversation, from the needs-you list, the next-waiting shortcut or a link, unfolds its project, so navigation never lands on something hidden.

The rail holds the control to expand, the needs-you count (in the notice colour when not zero, titled with what it counts), one mark per project in tree order (starred first) titled with the project's name, and a dot for the connection (red while reconnecting). A folded project that no longer exists is forgotten once the workspace has been read. Ctrl+/ moves the selection to the next waiting conversation in that order, and only the selection, so a reply in progress keeps its place; a bare n does the same while focus is outside any input, textarea, select or editable element, so typing never moves it. The selection lives in the URL hash. A project shows its trust notice, conversation list, rename and remove.     - Up and Down move the pick, and Enter or a press takes it. Picking replaces the word with the path relative to the checkout and a space, and leaves focus in the box.
    - The inserted path keeps the leading `@` for Claude, which attaches a mentioned file, and is bare for Codex, which takes `@path` as literal text (the capability report's 2026-11-10 follow-up).
    - Escape closes the list and leaves the text as typed; that word stays closed as it grows. A space ends the word, which closes the list too.
    - Ctrl+Enter always sends, list or no list, and the list never closes the panel: a press on it keeps focus in the box.
    - A search with no match says so. A failed search says it could not search the checkout.
  - **Sending closes the panel and goes to the end.** Ctrl+Enter or Send sends the prompt, clears the draft, moves focus out of the box, and closes it to its one line. Once it has closed, the view goes to the newest activity and follow-at-bottom engages, so the reply streams into view. A send the service refuses changes nothing: the box stays open and focused with the draft intact, and the error shows. A drag handle on its top edge (also Up and Down when focused) sets the remembered height: one size for every conversation, kept in this browser's `localStorage` as a preference, not workspace state. Drafts are per conversation in the browser and survive closing the box, switching conversations and reconnects. The placeholder reads `Reply (Ctrl+Enter to send)` when a prompt can be sent, and otherwise the activity line's own words (`Waiting for your approval`, `Working · Bash go test ./...`, `Starting`), so the two never disagree.
- **The control bar**, always visible. On one side, Send, and Interrupt while a turn is in flight or a request is pending. On the other, the mode selector (Claude), the model and effort control, and the more menu. The menu holds Release, Resume when it applies, Name and label, Remove from workspace, and the native events toggle. It takes focus when it opens, and closes on Escape, on a choice, or on a press outside it.
- **Release** opens a confirmation instead of releasing at once. When background jobs are running it names them and says what release does with them. Claude waits for them before it stops, and takes one more turn on its own when they finish, so the release lasts until then. Codex is not asked to wait, and any still running when it exits are reported. It says the runtime stops and the session is freed, and that a turn in flight is interrupted first. It shows the exact `cd <checkout> && claude --resume <id>` or `codex resume <id>` command with a copy control, and the rule: close the terminal before resuming or prompting here again, since an idle terminal still holds the session. The handoff paragraph that used to sit on the page is gone. Name and label, and Remove, open their own dialogs. A dialog hands focus back to what opened it when it closes.

Directly above the reply box, an activity line says what the conversation is doing now, and is absent when nothing is:
- with a turn in flight, a spinner, what is happening, and how long the turn has run (`8s`, `1m 12s`, `1h 12m`): `Writing` while text streams; `Working · Bash go test ./...`, the summary of the newest tool call of the turn without a result; otherwise `Working`;
- while starting, stopping or resuming, that word with the spinner;
- with a request pending, `Waiting for your approval`, or `Waiting for your answer` for questions, in the notice colour and with no spinner, since nothing moves until the operator acts;
- with supervision lost, `Supervision lost · execution uncertain` in the error colour, without motion;
- with no turn in flight but background jobs running, the working spinner in the muted colour, how many, what they are, and how long the oldest has run: `2 background jobs · npm test, sleep 300 · 4m`. During a turn, a request or a transition, the line stays what it is, with `· 2 in background` appended;
- with supervision lost, the background list is unknown, and the line says so: `Supervision lost · execution uncertain · background jobs unknown`;
- while stale, the last known text prefixed `Last known:`, dimmed, with no spinner.

The ticking time is left out of what a screen reader announces. An action in flight in the history shows the same small spinner in place of the word `running`.

Buttons are icons wherever a control's meaning is conventional. The icons are Material Icons, filled, from `@material-design-icons/svg` 0.14.15, pinned exactly. Each is imported as `?raw` SVG text into one `Icon` component (`ui/src/components/Icon.tsx`), so it builds into the bundle: no icon font, no runtime fetch. That component inlines the package's own SVG, never message content. Every button carries a `title` and an `aria-label` naming its action, and the icon takes the text colour around it.
- Icon only: Send, Interrupt, Copy (which shows a check once copied), the more menu, the code block's expand and collapse, dialog close and cancel, Register, New conversation and Launch, Adopt, and Undo.
- Icon and word: Allow, Deny and "Allow this tool for the session", since an approval is the one place where a misread glyph has a cost; Answer; Apply; Save; Rename; Release and Remove, which keep their confirmations; the menu's entries; and "Newer activity below".
- The sidebar's tree rows are navigation, named by their text, and carry no icon.

The history is set as blocks, told apart by tone rather than borders, the same in both themes:
- the agent's replies sit on the `--panel` tone, and the operator's prompts (from outside Roundhouse too) on the `--selected` tint, both with a 6px radius and 8px by 12px padding;
- the reply still streaming is rendered in the history's own list as the block it will land as, from its first character, so nothing moves when it lands;
- inside a block, fenced code, its header, tables' header cells and inline code take the page background with their existing hairline, so they read as set in;
- blocks stand 16px apart. The dashed turn separator keeps its own margin, and runtime and turn status lines stay unboxed, mono and muted;
- a run of actions between two pieces of speech is one group: tool rows, request rows (`Approval for Bash: answered`) and native rows when shown. A group is indented 20px with a hairline down its left edge and no background, its rows 4px apart. Speech, runtime lines, turn separators and failed-turn lines end a group;
- request cards are unchanged, in their notice colours, and stay the loudest thing in the column;
- every message block, prompt or reply, has two copy controls at its top right, shown on hover or when one has focus. Copy as markdown copies the message's text exactly as recorded. Copy as plain text copies what is rendered, read from the rendered block, without markdown syntax:
  - headings and emphasis as their words;
  - lists with the markers plain text writes them with: each item on its own line, `1.` counting from the list's start for an ordered list, `-` for an unordered one, `[x]` or `[ ]` after the marker for a task item, and two spaces of indent per level of nesting;
  - code as its text;
  - a link as its text followed by its address in parentheses (the address alone when the text is the address);
  - a table as tab-separated rows;
  - a soft line break as a space.

  A code block's own header and controls are left out. The reply still streaming has none, so a half message is never copied. An expanded tool result has one control that copies the whole output, whatever its box shows. Each control is an icon (`code` for markdown, `notes` for plain text, `content_copy` for output) with a `title` and an `aria-label`. After a copy, its icon turns to a check for a moment (an error mark if the copy failed), with no toast. Code blocks keep their own Copy.

A conversation opens at the top, so no scroll position carries over from what was shown before. Once its history has loaded, on the same gate the reading position uses (the unbroken run of events from the first reaches the newest one held), it moves to the newest event; pending request cards are docked in the panel, always in view. After that, new activity (an event, streaming text, a new request) is followed only while the view is at the bottom, within 32 pixels. A reader who has scrolled up stays where they are and gets a "Newer activity below" control, floating just above the panel, which returns them to the newest activity; scrolling back to the bottom also clears it.

The UI is set in two embedded faces. Neither is fetched from anywhere but the service: both come through the Vite build into `ui/dist` and the binary's `go:embed`, and the page makes no request off 127.0.0.1.

- Source Serif 4 is the variable face from `@fontsource-variable/source-serif-4` 5.2.9, pinned exactly, with its optical-size axis, Latin subset only. `ui/src/index.css` declares the two Latin rules of the package's `opsz.css` and `opsz-italic.css` (normal and italic, with their unicode ranges) instead of importing those files, so only those two woff2 files build into `ui/dist/assets`, about 250 KB. Non-Latin text falls back to Georgia.
- Nordwand Mono 1.3.3 is self-hosted in `ui/public/fonts/nordwand-mono/`: six woff2 files (Regular, Medium and Bold, with their italics) and `LICENSE-FONT.txt`, the SIL Open Font License 1.1 (source `https://github.com/tywr/Nordwand-Mono/releases/tag/1.3.3`). It is declared with six `@font-face` rules in `ui/src/index.css` and served at `/fonts/nordwand-mono/` as `font/woff2`.
- `--serif` is for everything that speaks: message bodies, dialog prose, headings and button labels. It is the body face, at 15px, with message prose at a 1.6 line height.
- `--mono` is for everything that labels, at 12px: the header's fact line and runtime state, the needs-you project names and shortcut hint, the connection status, runtime and turn status lines, the speaker label, tool and native event summary lines, request parameter names, the code block's language, conversation labels, and the adopt dialog's session timestamps. Inline code is 13px and fenced code 12px.
- Weights are 400 and 600 only, with bold text pinned at 600, and italics are available in both faces. A face is fetched only when text uses it, so mono at 600 resolves to Nordwand's Bold file and the Medium files, though declared, are never loaded.
- The sizes above are the base. The conversation pane's type is 10% larger: every font size in `ui/src/index.css` is a multiple of `--fs`, which is 1 everywhere and 1.1 inside `.conversation`. There, prose is 16.5px, the mono labels 13.2px, fenced code 13.2px, inline code 14.3px and the title 22px; the sidebar and dialogs keep the base sizes.
- Light and dark use the same faces and sizes.
- The conversation column is capped at 960px beside the 280px sidebar. On a window narrower than about 1300px the cap is not reached, and the column takes the width left after the sidebar and padding.

Message text renders as markdown: assistant replies, managed or imported, the operator's prompts, and the streaming text of a turn in flight. All three go through one renderer (`ui/src/components/Markdown.tsx`), so a reply looks the same while it arrives and after it lands. Partial input is fine: an unclosed fence runs to the end as code until it closes. Tool results, native events, request payloads and runtime text stay verbatim. The dialect is CommonMark with the GitHub extensions the agents use: tables, task lists, strikethrough and autolinks. There are no footnotes and no math.

Message text is untrusted model output, so the renderer follows four safety rules:

- Raw HTML is dropped, not shown. An HTML block disappears whole. An inline tag disappears, but the text between an opening and a closing tag is ordinary text, so `<script>x</script>` leaves an inert `x`.
- A link keeps its target only for an absolute `http`, `https` or `mailto` URL, and opens in a new tab with `rel="noopener noreferrer"`. Any other link, relative and fragment links included, renders as plain text.
- An image renders as a link to its URL, labeled with its alt text, and is never fetched.
- The output is React elements, never injected HTML, so nothing in a message can make the browser load a resource or run a script.

Headings step down to `h3` to `h6`, so an agent's `#` sits below the page's own headings. Tables scroll sideways inside the column, and long words and URLs wrap. A fenced block shows its language, if the fence names one, and a copy control. A block longer than 40 lines shows only its first 40, by height alone, with an expand control titled "Show all N lines" and, once expanded, a collapse control titled "Show only the first 40 lines". The whole block is always in the page, and Copy always copies all of it. An expanded block stays expanded when its reply lands and is rendered afresh: the page remembers expanded blocks by language and first 40 lines, which are final once a block is long enough to collapse. Syntax highlighting is deferred to a later roadmap card, because it is the piece that would add real weight to the bundle; the two libraries add about 50 KB gzipped. Soft line breaks follow CommonMark, so a single newline inside a paragraph renders as a space.

The UI re-reads the workspace whenever the stream connects or reports a change. Re-reads are numbered and coalesced: at most one is in flight, changes reported meanwhile get one follow-up, and only the newest response sent is applied, so an older response can never bring back a request the service no longer lists. It also fetches the selected conversation's events after the last seq it holds on every reconnect, so two browsers converge on the service's confirmed state. From the moment the stream drops, or a workspace refresh fails, until a refresh sent on the current connection succeeds, runtime state on the page is labeled last known: the header adds `(last known)`, marks dim, an in-flight tool reads `running when last seen` with no motion, the activity line says `Last known:` without its spinner, and elapsed labels stand still. A refresh still out when its connection dropped cannot mark a later connection up to date. A workspace read that fails while the stream is up is tried again, after 1 s and then doubling to at most 8 s, until one succeeds; otherwise nothing would ask again until the service announced a change. `make test` builds and lints it; `npm --prefix ui run dev` serves it on port 5173 against a running service.

The page distinguishes three states of its own knowledge, and shows an empty workspace ("No projects yet.", "Nothing waiting.", "Register a project from an existing checkout to begin.") only when a successful read returned one:
- **Never loaded.** Before the first successful workspace read, the page knows nothing and says so. It is connecting until a read or the stream fails. It is then unreachable when nothing answered: the stream is down, or the read reached no service. It is unreadable when the service answered the read with an error.
  - The main column says "Connecting", "The service is unreachable", or "The service could not read the workspace", naming the address it is trying (the one the page was served from) and that it keeps trying. The error shows below.
  - The side panel's needs-you and projects sections each say "Not known yet: connecting", "Not known: the service at … is unreachable", or "Not known: the service at … could not read the workspace". Register waits, disabled, and the footer reads "Unreachable, retrying" or "Read failed, retrying".
  - The rail's count reads `?` with a dashed outline, not zero. Its connection dot is red when unreachable or unreadable, and an empty ring while connecting.
  - The retry is the same in both failing states.
  - Recovery needs no reload: when the stream connects and a read succeeds, the workspace appears.
- **Loaded and current.** What the service last confirmed, as everywhere above.
- **Loaded but stale.** Everything the page last read, labelled last known, as described above, until a read on the current connection succeeds.

## Not built, and what to watch

- Refinements named but not built: SQLite if queries outgrow scanning a file (the registry stays a readable file regardless); contract-first generation of the API and its TypeScript types once the surface settles; one shared Codex app-server per environment, which would also allow live `codex --remote` attach.
- Deferred by the spec: pi, per-turn runtimes, suspension, the re-entry briefing, the central application, and more than one environment. The UI has no side-by-side view, no themes, and no mobile layout.
- Each Codex conversation costs an app-server process. That is fine for a handful; the shared server is the answer when it is not.
- A version change shows in the conversation header, which carries the harness version each runtime reported at its start.
- Nothing detects a terminal holding a session. Resuming a Claude session that a terminal still has open forks its transcript silently, so the handoff rule (release, use the terminal, close it, then resume) is the operator's to keep.

## Tests

`make test` runs the shim's protocol test against a fake SDK, the Go unit tests, and the UI lint and build. The UI has no test runner yet; browser checks are scratch Playwright scripts against a scratch service, using `shim/claude/fake/shim.mjs` in place of the shim so they cost no model turns. The fake speaks the same frames, acts on the text of each prompt (`burst`, `drip`, `ask`, `echo`, `stream`, `tool`, a Bash call that runs for a while before its result, `ask2`, two permission requests at once, `output N`, a Bash call whose result is N lines, and `background N MS`, N backgrounded Bash calls, job i finishing after i×MS with the frames Claude sends and a woken turn, and `busy`, a sentence, three tool calls, a reply with a code block, then a permission request), and records its sessions in the directory it runs in; its header says how to set one up. For Codex, `internal/harness/codex/fake/codex` stands in for `codex app-server` when a scratch service's `codex.binary` points at it. It speaks the subset of the app-server protocol the adapter uses, with the frames codex-cli 0.166.0 sends, and acts on the turn's text: `mcp TEXT` raises an MCP tool approval, `form` a typed form, `background MS` a command left running as a terminal session that completes MS after its turn, and anything else replies `ok`. It lists two models and a hidden one, reads an inherited `fake-large` at `medium` from `config/read`, and reports a turn's model or effort override with `thread/settings/updated`. The fake shim lists `default`, `fake-opus`, `fake-sonnet` and an effortless `fake-haiku`, reports the resolved model in `system/init`, and answers `set_model` (refusing an id it does not offer) and `set_effort`. The service is tested against a fake harness whose request numbers restart in every runtime; the Codex adapter against hand-written JSON-RPC frames over an in-memory wire. The Claude trust tests put their checkouts under the user cache directory, because codex 0.166.0 creates an empty `/tmp/.git` while any of its sandboxed commands runs on the machine, which would make every checkout under `/tmp` resolve to it as a git root.

`make e2e` runs `internal/e2e` with the real harnesses and the operator's logins, and is run by hand:

- Claude, against `claude-rt1`: the model list through an idle session, and a marker turn launched with `sonnet` at `low` whose `system/init` must report the resolved model. Then a marker turn, a question, a delayed approval, release, an import that must add nothing, and a resumed turn that recites every marker. Then, separately, a conversation launched in auto mode whose `sleep` turn, held back by the fixture's `ask` rule, must still arrive as a request raised in auto mode and wait for an answer. And a conversation launched in `default` that is switched to `auto` mid-turn, while its `sleep` approval is pending: Claude must confirm, the live mode must follow from that report, the request must survive and be answerable, and the next turn's `system/init` must report the same mode.
- Codex, against `codex-rt1`: discovery and history with no model turn; the model list and the config's inherited model and effort, and a marker turn launched with `gpt-6-luna` at `low`, which Codex must report as running, with exactly one `model_changed` event as the turn starts; then a marker turn, a delayed approval for a write outside the checkout, the async question steered into its turn, a clean release, an import that must add nothing, and a resumed turn; and a release during a running command, which must report what the sandbox left running. Then a turn that calls the fixture's MCP `echo` tool (`mcp/fixture-server.mjs`, named in the fixture's `.codex/config.toml`): the approval must arrive as a permission card for `fixture/echo` with its parameter, the tool must not run while the card waits (the server logs each call to `mcp/mcp-calls.log`), and it must run after Allow. The discovery test reads the fixture's newest thread and expects a user and an assistant message in it, so a probe that leaves an interrupted thread newest in `codex-rt1` makes it fail until a complete one is newer.

Each Claude run costs a few model turns, and the Codex runs together about five.
